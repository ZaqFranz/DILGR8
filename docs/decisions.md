# Architecture Decisions

## 2026-08-07 — Manual DI via composition root instead of a DI framework

**Context:** `CLAUDE.md` mandates Dependency Injection as an architecture principle. Options were a framework (`tsyringe`, `inversify`) or manual constructor injection wired in one file.

**Decision:** Manual constructor injection, wired in `backend/src/container.ts`.

**Pros:** No extra dependency or decorator/reflection setup; fully readable without tooling; trivial to fake collaborators in tests by calling `new Service(fakeRepo)` directly.

**Cons:** Doesn't auto-scale — as the module count grows, `container.ts` will grow linearly and someone has to remember to wire new modules in by hand.

**Future impact:** If the module count roughly doubles (i.e. once Sifting, PQE, Evaluation, etc. are built out), revisit whether a lightweight DI container is worth the tradeoff. Not needed yet.

**Reference:** [patterns.md § Dependency Injection](./patterns.md#dependency-injection-manual-via-composition-root).

## 2026-08-07 — Prisma as the ORM, MySQL as the database

**Context:** The brief specified MySQL and "database migration, models, CRUD automation" without naming an ORM. Candidates: Prisma, TypeORM, Sequelize.

**Decision:** Prisma.

**Pros:** Strong generated TypeScript types (matches the "strict typing" coding standard), a first-class migration CLI (`prisma migrate dev`), a readable single-file schema that doubles as documentation.

**Cons:** Prisma's query API is less flexible than raw TypeORM query builders for very complex joins; generated client needs a build step (`prisma generate`) that must run after `npm install` and after every schema change.

**Future impact:** Complex reporting queries needed later (e.g. CompAss ranking matrices) may need raw SQL via `prisma.$queryRaw` rather than the query builder. Acceptable tradeoff for now.

**Reference:** [database.md](./database.md).

## 2026-08-07 — Documents stored on local disk, not object storage

**Context:** Applicants upload eligibility proof, IPCR, and Designation Order files. Needed a storage backend for the first pass.

**Decision:** Local disk (`backend/uploads/`, via Multer's `diskStorage`), with only file metadata in the `documents` table.

**Pros:** Zero external dependency/cost for local development and demoing.

**Cons:** Doesn't survive container restarts or scale past a single server instance; not production-ready as-is.

**Future impact:** Before any real deployment, swap `documents.upload.ts`'s storage engine for S3-compatible object storage (e.g. via `multer-s3` or a manual upload-then-record flow). The `Document` model's `filePath` field is storage-engine-agnostic (just a string), so this swap shouldn't require a schema change — only the multer storage config and the (not-yet-built) file-serving/download endpoint.

**Reference:** [database.md § documents](./database.md#documents).

## 2026-08-07 — IPCR/Designation/Eligibility-proof documents are applicant-level, not application-level

**Context:** The domain spec ties IPCR and "Designation to a Higher Position" documents to promotional *applications*, and eligibility proof to the applicant's eligibility checklist. A document can't be linked to an `Application` until the `Application` row exists, but the application-submission validation needs to check the documents exist *before* creating that row — a chicken-and-egg problem if documents were required to reference an application at upload time.

**Decision:** `Document.applicationId` is optional. IPCR, Designation Order, and Eligibility Proof documents are uploaded against the applicant (no `applicationId`) during registration, and `ApplicationsService.submit()` checks for their *existence and type* on the applicant, not for a specific link to the application being created.

**Pros:** Avoids the ordering problem entirely; also lets an applicant reuse the same IPCR/Designation Order across multiple promotional applications submitted within the same 10-day window, which matches "may apply for different positions at once."

**Cons:** If an applicant later needs *different* IPCR documents for two different promotional applications, this model can't distinguish which document backs which application — it only checks "does at least one exist." Not a requirement in the current spec, so left unhandled.

**Future impact:** If per-application document requirements become necessary, `Application.submit()` would need to accept explicit document IDs instead of inferring from type, and the frontend would need to prompt for that during the apply flow.

**Reference:** [database.md § documents](./database.md#documents), `backend/src/modules/applications/applications.service.ts`.

## 2026-08-11 — Bulk panel assignment is add-only, and operates on postings, not applicants

**Context:** Client request: let an admin select multiple applicants on `PanelAssignmentsPage` and assign a panel to all of them at once, instead of repeating the single-applicant "Assign Panel" modal one row at a time. `PanelAssignment` is keyed on `(jobPostingId, panelUserId)` — every applicant under a posting already shares one panel — so "assign N applicants at once" only has a sound meaning once translated into "add these panelists to the postings behind the selected applicants." Two follow-on questions this raised: (1) should the bulk action *replace* each posting's panel roster (mirroring the single-assign modal's add+remove diff) or only *add* to it, and (2) should a selection spanning several distinct postings be allowed at all.

**Decision:** Add-only, multi-posting. New `POST /api/panel-assignments/bulk` (`{ jobPostingIds: string[], panelUserIds: string[] }`, max 200 × 50) creates every `(posting, panelist)` pair not already assigned and silently skips the rest (`skippedCount` in the response) — it never removes an existing assignment. A selection is allowed to span any number of distinct postings; the bulk modal states the posting count and titles up front and repeats the single-assign modal's "every panelist checked will see every applicant under this posting" warning, generalized to "under each of those postings."

**Pros:** Add-only means the action can never surprise-unassign a panelist from an applicant the admin didn't select (a real risk with a replace-style diff once a selection is a subset of a posting's applicants) — the failure mode of doing too little is much safer than doing too much for a bulk action. Cartesian pair generation plus a single skip-existing pass keeps the operation naturally idempotent (re-running the same bulk action is always safe) and lets one bulk call reasonably cover "assign this new panelist to every posting currently missing them," not just a single posting.
- Each newly-created pair still gets its own audit log entry (`PANEL_ASSIGNED`) in the exact format `create()` already uses (`Assigned {email} to interview panel for "{title}"`) — a bulk action's trail reads identically to N manual assigns, so `History of Logs` needed no changes to display it.

**Cons:** There's no bulk-unassign counterpart — removing a panelist from several postings at once still requires the single-applicant modal's checkbox-diff, once per posting. A large selection (many postings × many panelists) can log a proportionally large number of audit rows in one action, though this is consistent with — not worse than — doing the same assignments manually.

**Future impact:** If a bulk-remove need materializes, it would need an explicit "remove" bulk endpoint rather than repurposing this one as a diff, precisely to keep the "add-only, never surprises" guarantee this decision relies on.

## 2026-08-12 — Regret letters need their own statuses per stage, not a reused `NOT_QUALIFIED`

**Context:** Client request: send a "regret letter" whenever an applicant fails to move to the next step. Before this, `NOT_QUALIFIED` was the *only* rejection-type status in the pipeline, settable only from `UNDER_SIFTING` via `sift()` - an applicant who scored poorly in the panel evaluation, or who never completed Compliance to Requirements, had no formal rejection path at all: `FOR_INTERVIEW`'s only exit was `move-to-compliance`, and `FOR_COMPLIANCE`'s only exit was `oath-taking`. The natural-looking fix - reuse `NOT_QUALIFIED` for these two new rejection points too - breaks `ApplicationStageTracker.tsx`: that component hardcodes `NOT_QUALIFIED` as resolving in place on the Sifting node specifically, so an applicant rejected after their interview would incorrectly show as rejected back at Sifting, several stages earlier than what actually happened.

**Decision:** Two new terminal statuses, one per stage: `NOT_SELECTED` (`FOR_INTERVIEW` → regret, via new `PATCH /:id/not-selected`) and `DISQUALIFIED` (`FOR_COMPLIANCE` → regret, via new `PATCH /:id/disqualify`). Both stamp one shared pair of columns, `Application.rejectedAt`/`rejectionRemarks`, rather than two near-identical field sets - they're the same kind of one-shot admin call, just from a different stage. The stage tracker's rejection check was generalized from a single hardcoded `isSifting` condition to a `REJECTION_STATUS_BY_STAGE` lookup (`UNDER_SIFTING → NOT_QUALIFIED`, `FOR_INTERVIEW → NOT_SELECTED`, `FOR_COMPLIANCE → DISQUALIFIED`), so each rejection resolves on the node it actually happened at. All three rejection paths (including the pre-existing sifting one) now send the same `regretEmail()` template from `applicationEmailTemplates.ts`, worded per stage - `decisionEmail()`'s `NOT_QUALIFIED` branch was refactored to call it too, so every "you weren't selected to continue" letter speaks with one consistent voice instead of three independently-worded emails.

**Pros:** The applicant-facing tracker stays accurate regardless of which stage ends in rejection. Reusing one `rejectedAt`/`rejectionRemarks` pair (instead of `notSelectedAt`/`notSelectedRemarks` + `disqualifiedAt`/`disqualifiedRemarks`) keeps the schema and the `EvaluationRow` display logic simple - `application.rejectedAt !== null` is the one check needed to know "show the rejection card," with the status itself (`NOT_SELECTED` vs `DISQUALIFIED`) picking the wording. `Disqualify` deliberately has no "every compliance item must be reviewed first" precondition (unlike `oath-taking`'s "every item verified" gate) - an admin can disqualify as soon as it's clear a requirement won't be met, rather than being forced to wait out every pending item first.

**Cons:** Two more terminal `ApplicationStatus` values means more places that enumerate the full status set have to stay in sync (`APPLICATION_STATUS_LABELS`, the Dashboard's `APPLICATION_STATUS_META`/`_ORDER`, badge CSS) - TypeScript's `Record<ApplicationStatus, ...>` catches the first two at compile time, but the CSS class list is unchecked. Sharing one `rejectedAt`/`rejectionRemarks` pair means an application can't (today) carry a record of *both* a not-selected and a disqualified outcome, though that's not a real scenario since both are terminal - once set, no later action can change `status` again.

**Future impact:** If a rejection point is ever needed even earlier or later in the pipeline (e.g. a formal reject at `FOR_OATH_TAKING`), follow the same pattern: one new terminal status, one new `REJECTION_STATUS_BY_STAGE` entry, one new service method reusing `rejectedAt`/`rejectionRemarks` and `regretEmail()`.

**Reference:** [api.md § Applications](./api.md#applications--apiapplications-all-require-auth), [database.md § applications](./database.md#applications), `backend/src/modules/applications/applications.service.ts`, `backend/src/shared/email/applicationEmailTemplates.ts`, `frontend/src/features/applicant-registration/components/ApplicationStageTracker.tsx`.

**Reference:** [api.md § Interview Panel Assignments](./api.md#interview-panel-assignments--apipanel-assignments-all-admin-only), `backend/src/modules/panel-assignments/panel-assignments.service.ts`, `frontend/src/features/admin/pages/PanelAssignmentsPage.tsx`.

## 2026-08-07 — Evaluation implemented as a single score+decision on `Application`, not a full board evaluation-forms system

**Context:** The domain spec's Evaluation phase involves 13 board members each filling per-battery-test forms, feeding a Comparative Assessment (CompAss) ranking. The immediate ask was "admin can post jobs and evaluate applicants" — a much smaller scope.

**Decision:** Added four fields directly to `Application` (`evaluationScore`, `evaluationRemarks`, `evaluatedAt`, `evaluatedByUserId`) rather than a separate `Evaluation`/`EvaluationForm` model. Any one `ADMIN` user can record one score (0-100) + decision (`QUALIFIED`/`NOT_QUALIFIED`) + remarks per application via `PATCH /api/applications/:id/evaluate`, which overwrites the previous evaluation if run again.

**Pros:** Matches the requested scope exactly with minimal schema/API surface; the mandatory-field and score-threshold validation the spec calls out for "Eval Forms" is satisfied by the DTO (`score` and `decision` required, `score` bounded 0-100).

**Cons:** Doesn't model multiple evaluators, per-battery-test scores, or CompAss ranking at all — "evaluate" here means one person's overall score, and a second admin evaluating the same application silently overwrites the first. Not acceptable once the real multi-board-member Evaluation phase is built.

**Future impact:** When the full Evaluation phase from the RSP spec is implemented, this will need to become a proper `Evaluation` model (one row per evaluator per battery test, `Application` 1:N `Evaluation`), with the current `evaluationScore`/`evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` fields on `Application` likely repurposed as a computed/aggregate summary rather than raw input. Flagged in project-memory.md's technical debt.

**Superseded/extended:** the multi-evaluator system this entry anticipated was built on 2026-08-08 (see the entry below) — `evaluationScore`/`evaluationRemarks`/etc. on `Application` were kept as-is (the admin's own final decision) rather than repurposed, with the panel's per-evaluator scores living in new `PanelEvaluation`/`PanelScore` tables instead. Then, in a second 2026-08-08 entry ("Sifting/PQE/Interview pipeline"), this single free-standing "evaluate" action was itself repurposed into the Sifting phase's pass/fail call (`evaluationScore` dropped, `evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` renamed `siftingRemarks`/`siftedAt`/`siftedByUserId`) once it became clear it was standing in for Sifting all along, not a genuine final decision.

**Reference:** [database.md § applications](./database.md#applications), [api.md § Applications](./api.md#applications--apiapplications-all-require-auth), `backend/src/modules/applications/`.

## 2026-08-07 — Admin and applicant are separate route trees, not the same pages with conditional UI

**Context:** Asked for the admin panel to be visibly different from the applicant experience, with admins restricted to posting jobs and evaluating applicants only.

**Decision:** `frontend/src/features/admin/` is a distinct feature with its own pages under `/admin/*` routes, guarded by `<ProtectedRoute role="ADMIN">`. Applicant routes (`/jobs`, `/register`, `/applications`) are guarded by `<ProtectedRoute role="APPLICANT">` and redirect an admin back to `/admin/jobs` if they try to hit them directly (and vice versa). `Layout`'s nav shows an entirely different link set per role rather than the same links with some hidden. (Superseded/extended by the sidebar-shell decision below — the admin pages were originally `CreateJobPostingPage`/`EvaluateApplicantsPage` under the same top nav as applicants; now they're `JobManagementPage`/`UsersManagementPage`/`EvaluateApplicantsPage`/`AuditLogsPage` under `AdminShell`'s sidebar. `/registration` was later merged into `/register` — see the 2026-08-08 unified-registration decision below.)

**Pros:** Clean separation matches "admin can only post jobs and evaluate applicants" literally — there's no code path where an admin session can reach the applicant registration wizard or an applicant session can reach evaluation screens.

**Cons:** Some duplication of route-guard boilerplate between the two route groups in `App.tsx`; acceptable at this route count.

**Future impact:** If a third role appears (e.g. a board member distinct from a full admin), `ProtectedRoute`'s `role` prop would need to accept an array, and `Layout`'s nav switch would need a third branch.

## 2026-08-08 — Eligibility gate at application submission: structured per-posting requirement, join table over JSON/scalar-list

**Context:** Applicants without the eligibility a posting requires were able to apply — `ApplicationsService.submit()` only checked that a self-declared-eligible applicant had uploaded *some* `ELIGIBILITY_PROOF` document, never that their `eligibilityType` actually satisfied the posting. The posting side had no structured field to compare against: `JobPosting.qualificationEligibility` is free text (e.g. "RA 1080 or CSC Professional required") written by an admin for applicants to read, not something the backend can parse reliably. Fixing this required deciding how a posting expresses which eligibility type(s) it needs.

**Decision:** Added `JobPostingRequiredEligibility`, a join table (`jobPostingId`, `eligibilityType`, unique together) rather than a Prisma scalar-list field or a `Json` column on `JobPosting`. `JobPostingsRepository` flattens the join rows into a `requiredEligibilityTypes: EligibilityType[]` array on every read and replaces the full set (`deleteMany` + `create`) on update, so every other layer (service, controller, frontend) just sees a plain array — the join table is an implementation detail. An empty array means no eligibility is required. `ApplicationsService.submit()` now 400s before creating the application unless `applicant.hasEligibility && posting.requiredEligibilityTypes.includes(applicant.eligibilityType)` (skipped entirely when the array is empty), and the frontend's `JobPostingsListPage` disables/relabels the "Apply" button using the same check so an ineligible applicant is told why before clicking, not after. The pre-existing "if you claim eligibility, prove it with a document" check is unchanged and still runs independently.

**Pros:** A join table matches the codebase's existing style for admin-managed one-to-many links (`PanelAssignment` is structurally identical) and lets Prisma/MySQL enforce the schema directly, rather than trusting an unvalidated `Json` blob or working around MySQL's lack of native scalar-list support. Keeping the free-text `qualificationEligibility` field alongside it (rather than deriving display text from the structured array) preserves whatever nuance an admin already wrote there for applicants to read, while the structured array is the only thing enforcement logic touches.

**Cons:** Two eligibility-related fields on `JobPosting` now (`qualificationEligibility` free text, `requiredEligibilityTypes` structured) that admins must keep in sync by hand — nothing stops them drifting (e.g. the text says "RA 1080 preferred" while the checkboxes require CSC Professional). A join table also means every job-posting read does an extra `include`, though at this data volume it's immaterial.

**Future impact:** If eligibility requirements ever need per-posting nuance beyond "any one of these types" (e.g. "RA 1080 AND 2 years experience", or an eligibility type that's only acceptable for certain positions), the flat `EligibilityType[]` check in `ApplicationsService.submit()` is the first place to extend — it's isolated to a single `if` block, not spread across the codebase.

**Reference:** [database.md § job_posting_required_eligibilities](./database.md#job_posting_required_eligibilities), [api.md § Job Postings](./api.md#job-postings--apijob-postings) / [§ Applications](./api.md#applications--apiapplications-all-require-auth), `backend/src/modules/job-postings/job-postings.repository.ts`, `backend/src/modules/applications/applications.service.ts`, `frontend/src/features/job-postings/pages/JobPostingsListPage.tsx`.

## 2026-08-08 — Applicant-initiated application withdrawal: allowed up to FOR_INTERVIEW, not logged to the audit trail

**Context:** `Application.status` has included `WITHDRAWN` since the pipeline's first migration, but nothing ever set it - there was no applicant-facing withdraw action. `docs/rsp-domain-spec.md` has zero mentions of "withdraw"; there's no specified cutoff for when an applicant may withdraw, so which statuses should allow it was an undocumented call to make. Separately, every other `Application` transition (`sift`, `scheduleInterview`, exam-score import) is admin/panel-initiated and gets an `AuditLog` entry; `submit()` - the only prior applicant-initiated transition - does not, per the existing "applicant-side actions aren't audited yet" convention (see Audit Logging in `docs/project-memory.md`).

**Decision:** An application can be withdrawn (`PATCH /api/applications/:id/withdraw`) from `SUBMITTED`/`UNDER_SIFTING`/`QUALIFIED`/`FOR_INTERVIEW` - i.e. any non-terminal status. `NOT_QUALIFIED` and `WITHDRAWN` itself are excluded (400) since both are already terminal outcomes with nothing left to withdraw from. Ownership is enforced the same way `submit`/`listMine` do it - resolve the caller's own `Applicant` row via `userId`, then compare `application.applicantId` against it - and a mismatch 404s (not 403), so an applicant probing another applicant's application ID can't distinguish "not yours" from "doesn't exist." Like `submit()`, `withdraw()` does not write an `AuditLog` entry, staying consistent with the existing applicant-action convention rather than auditing this one applicant action while every other one stays unaudited.

**Pros:** The status whitelist matches how the rest of the pipeline already treats `NOT_QUALIFIED`/`WITHDRAWN` as terminal (nothing else transitions out of them either). Reusing `submit`/`listMine`'s exact ownership-resolution pattern, rather than inventing a new one, keeps applicant-scoped resource access consistent across the module.

**Cons:** The specific cutoff (through `FOR_INTERVIEW`, not further) is a judgment call with no spec backing it - a real DILG process might want to disallow withdrawal once an interview is scheduled, or allow it all the way through Deliberation once that phase exists. Not auditing applicant-initiated actions at all (submit, now withdraw) means there's no admin-visible trail if an applicant repeatedly submits and withdraws, though the audit log's stated purpose (`docs/decisions.md`'s audit-trail entry, `docs/patterns.md`) has always been about admin/panel write accountability, not applicant activity monitoring.

**Future impact:** If the domain spec is ever clarified with an explicit withdrawal cutoff, the whitelist is a single `WITHDRAWABLE_STATUSES` constant in `applications.service.ts` to change. If applicant-side audit logging is added later (tracked as a known gap in `docs/project-memory.md`), `withdraw()` should get the same treatment as `submit()` in that pass, not be singled out now.

**Reference:** [database.md § applications](./database.md#applications), [api.md § Applications](./api.md#applications--apiapplications-all-require-auth), `backend/src/modules/applications/applications.service.ts`, `frontend/src/features/applicant-registration/pages/MyApplicationsPage.tsx`.

## 2026-08-08 — Admin panel redesigned around a sidebar shell (`AdminShell`), not the shared top nav

**Context:** Asked for the admin panel to look like "an admin panel setup" — sidebar navigation — with full CRUD for Users, Jobs, and a new History of Logs section, distinct from the two-link top nav the admin section had before.

**Decision:** `frontend/src/features/admin/components/AdminShell.tsx` renders a left sidebar (Job Management / Users Management / Evaluate Applicants / History of Logs, active-highlighted via `useLocation()`) and every `/admin/*` page wraps its content in it. `Layout`'s top bar drops the admin nav links entirely (they'd be redundant with the sidebar) and stays minimal for admins; it also swaps `.app-main`'s centered-960px styling for a full-width `.app-main--full` when `pathname.startsWith("/admin")`, so the sidebar isn't squeezed into the applicant pages' narrow column.

**Pros:** Reads as a distinct admin product surface, not applicant pages with extra links; matches conventional admin-panel UX (persistent left nav) rather than the applicant section's simple top nav.

**Cons:** `AdminShell` is repeated as a wrapper in every admin page component rather than applied once via a nested-route `<Outlet/>` layout — chosen to keep the existing children-prop routing pattern in `App.tsx` unchanged (lower risk than restructuring routing) at the cost of one extra import/wrap per admin page.

**Future impact:** If the admin page count grows much further, revisit converting `/admin/*` to a nested-route layout (`<Route path="/admin" element={<AdminShell/>}>` with child `<Outlet/>` routes) to stop repeating the wrapper. Not needed at four pages.

**Reference:** [architecture.md § Role-based routing](./architecture.md#role-based-routing-frontend), `frontend/src/features/admin/components/AdminShell.tsx`.

## 2026-08-08 — Audit log (`AuditLog`) has no update/delete path, by design

**Context:** "History of Logs" needed a backing data model. The ask was framed as part of "complete CRUD" for the admin panel, but an audit trail that admins can edit or delete isn't actually an audit trail — it's just another editable table.

**Decision:** `AuditLogsRepository` only exposes `record()` (create) and `findMany()` (read). There is no `PATCH`/`DELETE` route, controller method, or repository method for `AuditLog` at any layer — not even admin-gated. Entries are written automatically by other services after a successful write (see [patterns.md § Audit Trail](./patterns.md#audit-trail-append-only-log-via-injected-repository)).

**Pros:** The log stays trustworthy as a record of what actually happened; no risk of an admin (accidentally or otherwise) editing history to hide an earlier action.

**Cons:** No way to redact a log entry that contains something it shouldn't (e.g. if a `details` string ever included sensitive data by mistake) short of a direct database operation outside the app. Acceptable given `details` strings are built from data already visible elsewhere in the admin panel (emails, job titles, scores) — nothing logged that isn't already exposed via the CRUD screens themselves.

**Future impact:** If regulatory/compliance requirements ever demand log redaction, that should be a narrowly-scoped, heavily-audited-itself operation (e.g. a one-off maintenance script with its own logging), not a general API endpoint.

**Reference:** [database.md § audit_logs](./database.md#audit_logs), [api.md § Audit Logs](./api.md#audit-logs--apiaudit-logs-admin-only-read-only).

## 2026-08-08 — `JobPosting.createdByUserId` and `Application.evaluatedByUserId` are nullable/`SetNull`, so admins are deletable

**Context:** Users Management needed real delete capability. `JobPosting.createdByUserId` was originally a required field with Prisma's default `Restrict` behavior on delete, which would silently block deleting any admin who had ever posted a job — surprising and undiscoverable from the Users Management UI (the delete would just fail with a generic FK error).

**Decision:** Made `createdByUserId` optional (`String?`) with an explicit `onDelete: SetNull`, matching the pattern `evaluatedByUserId` on `Application` already used. Deleting a user now always succeeds (except for self-delete, blocked at the service layer) and severs the creator/evaluator link on their past job postings/evaluations rather than blocking or cascading.

**Pros:** "Delete a user" behaves predictably regardless of what that user has done in the system; job postings and evaluation history survive the deletion of whoever made them, which matches how the History of Logs already preserves entries after actor deletion (`AuditLog.actorUserId` is also nullable/`SetNull`).

**Cons:** After deleting an admin, their past job postings/evaluations show no creator/evaluator in the UI (`createdBy`/`evaluatedBy` becomes `null`) — there's no "deleted user" placeholder value, just absence. Acceptable since the `AuditLog` history still records what they did (with `actor: null` shown as "(deleted user)" in `AuditLogsPage`), even after the `User` row itself is gone.

**Reference:** [database.md § job_postings](./database.md#job_postings), `backend/prisma/schema.prisma`.

## 2026-08-08 — Registration unified into one flow; applicant pages gated on `registrationCompletedAt`

**Context:** The original design split applicant onboarding into two steps: `POST /auth/register` (email/password only, at `/register`) immediately followed by a redirect to a separate post-login wizard (`/registration`, behind `<ProtectedRoute role="APPLICANT">`) for the demographic profile, work experience, L&D, awards, and documents. Nothing stopped an authenticated applicant from navigating straight to `/jobs` or `/applications` without ever finishing the wizard — the "rest of the flow" was reachable, and skippable, only by choice of navigation, not by enforcement. Explicit product direction: all applicant information must be captured as part of registration, not deferred to after the applicant is already logged in and using the app.

**Decision:** Merged the account-creation form and the former wizard into a single component, `RegistrationPage` (`frontend/src/features/applicant-registration/pages/RegistrationPage.tsx`), mounted at one route (`/register`). It renders the account step for unauthenticated visitors and continues in place through profile → work experience → L&D → awards → documents after `register()` succeeds, with no route change in between. Added `Applicant.registrationCompletedAt` (nullable `DateTime`) and `POST /api/applicants/me/complete-registration`, called when the applicant finishes the last step (validates an eligibility-proof document has been uploaded if `hasEligibility` is true). `AuthContext` exposes `registrationComplete` (fetched from `GET /api/applicants/me` right after login/register and on session restore); `ProtectedRoute` and `HomeRedirect` redirect any applicant with `registrationComplete === false` to `/register`, whichever page they try to reach directly. The old `RegisterPage.tsx` and `RegistrationWizardPage.tsx` were deleted.

**Pros:** Matches the "collect everything at registration" requirement literally — there is no code path to `/jobs` or `/applications` that bypasses profile/work-experience/L&D/awards/documents. `/register` also stays reachable after completion (e.g. Layout's "My Profile" link) so applicants can still edit their record without a separate profile-editing surface to maintain.

**Cons:** `AuthContext` now depends on the `applicant-registration` feature's API module (`getMyProfile`) to resolve `registrationComplete`, which is a cross-feature import `shared/auth` didn't previously have. Every protected-route render for an applicant does one extra `GET /api/applicants/me` round trip on session restore/login (cheap single-row lookup, not on every navigation) that a JWT-embedded claim could have avoided at the cost of needing to re-issue tokens whenever registration status changes.

**Future impact:** If more roles or a "partially registered admin" concept is ever introduced, `registrationComplete` and the redirect logic in `ProtectedRoute`/`HomeRedirect` should generalize to a role-keyed "onboarding complete" check rather than the current `APPLICANT`-only branch.

**Reference:** [architecture.md § Registration gating](./architecture.md#registration-gating-frontend), [database.md § applicants](./database.md#applicants), [api.md § Applicants](./api.md#applicants--apiapplicants-all-require-auth).

**Reference:** [architecture.md § Role-based routing](./architecture.md#role-based-routing-frontend), `frontend/src/shared/components/ProtectedRoute.tsx`, `frontend/src/App.tsx`.

## 2026-08-08 — Interview panel & CompAss tabulation: multi-criteria rubric, admin-assigned panelists, `Application.evaluate` left unguarded

**Context:** Building the real multi-evaluator Evaluation phase the 2026-08-07 entry above deferred. Two scope forks needed deciding: (1) does a panelist give one overall interview score, or score several separately-weighted criteria; (2) can any `PANEL` account score any interview-stage applicant, or only ones on postings an admin explicitly assigned them to. Both were resolved toward the more literal reading of the domain spec's "evaluation forms" and "13 board members" framing rather than the simpler option.

**Decision:** Added `Role.PANEL` (a full third role, not an admin sub-type — provisioned the same way as `ADMIN`, through Users Management's existing role `<select>`) and `ApplicationStatus.FOR_INTERVIEW`. Four new tables: `EvaluationCriterion` (admin-editable rubric, `maxScore` doubling as weight), `PanelAssignment` (admin-managed M:N, posting × panel user), `PanelEvaluation` + `PanelScore` (one evaluation per panelist per application, with per-criterion score rows, upserted on re-submit). `PATCH /applications/:id/schedule-interview` (new, admin-only) moves an application to `FOR_INTERVIEW`; the existing `PATCH /applications/:id/evaluate` is unchanged and still finalizes regardless of current status — no server-side check blocks an admin from qualifying/disqualifying an application before every assigned panelist has scored it. `GET /panel-evaluations/tabulation/:jobPostingId` computes the ranked CompAss matrix (sum per panelist, average across panelists, descending rank) at read time in application code, surfaced as two extra columns on `EvaluateApplicantsPage` rather than a separate matrix view.

**Pros:** The rubric being admin-editable matches the spec's "administrator can edit/update evaluation forms" literally, rather than hardcoding assumed criteria the spec doesn't actually enumerate. Assignment-gating matches how real interview boards are staffed (not every panelist should see every posting) and is enforced server-side (`PanelEvaluationsService.submit` 403s a panelist scoring an application on a posting they're not assigned to), not just hidden in the UI. Leaving `evaluate` unguarded keeps the admin's finalize action simple and avoids a second source of truth for "is this ready to decide" — the tabulation view already shows `panelistsSubmitted`/`panelistsAssigned` for the admin to judge.

**Cons:** No server-side block on premature finalization means the only guard against an admin qualifying an applicant before the board has finished scoring is a frontend warning (`EvaluationRow` reads `panelistsSubmitted < panelistsAssigned` from the tabulation response) — bypassable by calling the API directly. Criteria are global, not per-posting or per-battery-test, so every interview board scores against the same rubric regardless of position; the spec's "per battery test/activity" framing could imply otherwise, but nothing in the actual ask required per-posting rubrics, and building that would mean either duplicating criteria per posting or adding a join table with no concrete requirement driving its shape yet.

**Future impact:** If premature finalization turns out to be a real problem in practice (not just a theoretical gap), add a server-side check in `ApplicationsService.evaluate()` requiring `panelistsSubmitted === panelistsAssigned` for `FOR_INTERVIEW` applications, mirroring the pattern already used for `JobPostingsService.delete`'s guard. If per-posting or per-battery-test rubrics become a real requirement, `EvaluationCriterion` would need a nullable `jobPostingId` (global rubric when null, override when set) rather than a breaking schema change. Letter/notice generation and the spec's 1:5 auto-shortlisting ratio (both listed under the domain spec's "Tabulation" section) remain unimplemented — a separate notifications/documents feature.

**Superseded/extended:** `PATCH /applications/:id/evaluate` no longer exists as of the 2026-08-08 "Sifting/PQE/Interview pipeline" entry below — it was repurposed into the Sifting decision (`PATCH /applications/:id/sift`, gated to `UNDER_SIFTING`) and there's no longer any post-interview "finalize" action at all, so the premature-finalization gap this entry flags is moot for now (the pipeline simply stops at `FOR_INTERVIEW` until a future Deliberation phase is built).

## 2026-08-08 — Sifting/PQE/Interview pipeline: repurpose the free-standing "evaluate" action, add an Excel-based PQE score import

**Context:** The Dashboard already tallied `ApplicationStatus` (`SUBMITTED`/`UNDER_SIFTING`/`FOR_INTERVIEW`/`QUALIFIED`/`NOT_QUALIFIED`/`WITHDRAWN`), but only `SUBMITTED`, `FOR_INTERVIEW`, and `QUALIFIED`/`NOT_QUALIFIED` were ever actually set — `UNDER_SIFTING` had no code path at all, and `QUALIFIED`/`NOT_QUALIFIED` were set by a free-standing "Evaluate Applicants" action (0-100 score + decision + remarks, callable from any status) that had drifted into being a generic final-call tool rather than anything tied to a specific RSP phase, once the real per-criterion panel scoring (`PanelEvaluation`/`PanelScore`) was built separately. The user described the intended order explicitly: Submitted → Under Sifting → Qualified → Examination (external; system just records the score) → For Interview (admin schedules, applicant emailed) → Panel Tabulation (already built) — which matches the domain spec's Sifting phase (pass/fail against education/training/experience/eligibility) and PQE phase (batch exam, score recorded, notice sent regardless of pass/fail) exactly.

**Decision:** Repurposed the existing "evaluate" action into the Sifting decision: `Application.evaluationScore` dropped (sifting is pass/fail, not scored), `evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` renamed `siftingRemarks`/`siftedAt`/`siftedByUserId`, and `PATCH /applications/:id/evaluate` became `PATCH /applications/:id/sift` (`SiftApplicationDto = { decision, remarks? }`), now gated to `status === UNDER_SIFTING` (previously callable from any status). `ApplicationsRepository.create()` now sets `status: "UNDER_SIFTING"` directly instead of relying on the `@default(SUBMITTED)` schema default, so every application is "Under Sifting" the instant it's submitted — no separate manual "start sifting" step. Added `Application.examinationScore`/`examinationScoredAt` and a new `POST /applications/import-exam-scores` (multipart: `.xlsx`/`.xls` + `jobPostingId`, `ADMIN`-only) that parses an Excel file (`exceljs`, `Name`/`Score` header columns) and matches each row by normalized full name against that posting's `QUALIFIED` applicants — matches get the score + a `[DEV EMAIL]`/SMTP notification, non-matches come back in the response for the admin to review and re-upload rather than failing the whole import. `PATCH /applications/:id/schedule-interview`'s guard changed from `status in {SUBMITTED, UNDER_SIFTING}` to `status === QUALIFIED && examinationScore !== null`, enforcing sifting-then-PQE-then-interview in that order.

**Pros:** Fixes a real semantic bug rather than adding a parallel feature — the old "evaluate" action was already standing in for Sifting, just without the name, the gating, or the pipeline position to show it. The Excel import matches how PQE results actually arrive in practice (a batch exam run outside the system, results tabulated in a spreadsheet) without requiring the admin to hand-enter scores one row at a time. Name-matching with a reviewable unmatched list is more forgiving than an all-or-nothing import — a handful of formatting mismatches don't block everyone else's scores from landing.

**Cons:** Name-matching is inherently fuzzier than an ID-based join — two applicants with the same normalized name on the same posting would collide (last-write-wins in the lookup map), and a typo in the spreadsheet silently produces an "unmatched" row rather than a hard error pointing at the specific cell. No pass/fail threshold is enforced on the PQE score itself (by explicit choice - score is informational, the admin decides whether to schedule an interview), so nothing stops an admin from scheduling an interview for a very low PQE score. The applicant-facing stage tracker's "Examination" node doesn't visually distinguish "awaiting a score" from "scored, awaiting interview scheduling" - both render as the same in-progress node, with the actual score (if any) shown as a line of text underneath instead.

**Future impact:** If PQE score collisions on duplicate names become a real problem, the import would need a secondary identifier (e.g. an applicant reference number column) rather than name-only matching. If a pass/fail threshold is ever wanted, `examinationScore`'s consumer (`scheduleInterview`'s guard) is the one place to add it - no schema change needed since the score is already a plain `Int`. The pipeline still stops at `FOR_INTERVIEW`/panel tabulation - Deliberation (the RD's final decision), Compliance to Requirements, and Onboarding remain future work per project-memory.md.

**Reference:** [api.md § Applications](./api.md#applications--apiapplications-all-require-auth), [database.md § applications](./database.md#applications), `backend/src/modules/applications/`, `backend/src/modules/applications/examScoreParser.ts`, `frontend/src/features/applicant-registration/components/ApplicationStageTracker.tsx`.

**Bugfix (same day):** The first cut of name-matching (`firstName lastName` only) turned out to fail on real data immediately - the actual test applicant has a middle name (`R.`) on file, and a PQE sheet naturally lists the fuller "Gibo R. Ormeneta," which the bare two-part key never matched (reported as "0 matched, 2 unmatched" on a real import attempt). Fixed by having `normalizeName()` also strip `.`/`,` (so "R." and "R" are equivalent) and adding `buildNameVariants()`, which indexes every `QUALIFIED` applicant under several plausible spellings — `firstName lastName`, `firstName middleName lastName`, `firstName middleInitial. lastName`, and each of those again with `suffix` appended when present — rather than a single fixed key.

## 2026-08-09 — Self-service password change: one role-agnostic endpoint/page, not three role-specific ones

**Context:** Neither `ADMIN` nor `PANEL` had any self-account page at all (only Users Management, which manages *other* users' accounts), and the applicant's "My Profile" link only ever reached demographic-profile fields - the `RegistrationPage` wizard's "Account" step is literally the anonymous sign-up form and is filtered out (`visibleSteps`) the moment the user is authenticated, so there was no reachable UI for a logged-in applicant to change their password either. `PATCH /api/users/:id` (admin-only, for managing other users) has never touched `passwordHash`. No password-change/reset code existed anywhere in `auth/` or `users/` before this.

**Decision:** One new endpoint, `PATCH /api/auth/me/password` (`authenticate` only, no `requireRole` - any logged-in user can call it for themselves), verifying `currentPassword` against the caller's own `passwordHash` via the existing `verifyPassword`/`hashPassword` helpers (`@/shared/utils/password`, bcryptjs, same salt rounds as registration) rather than adding a parallel hashing path. One new frontend page, `ChangePasswordPage` at `/account/password`, wrapped in `<ProtectedRoute>` with **no** `role` prop (so `APPLICANT`/`ADMIN`/`PANEL` all pass), and one "Change Password" link added to `Layout`'s header inside the existing `isAuthenticated` branch (visible regardless of role) rather than duplicating the link into `AdminShell`'s sidebar, the `PANEL` nav branch, and the `APPLICANT` nav branch separately. A wrong `currentPassword` 400s with a Zod-flatten-shaped `fieldErrors.currentPassword` (matching the `validate` middleware's existing error shape) so the frontend's existing `getFieldErrors` util renders it inline exactly like any other form validation error, rather than a 401 that risked being misread by future 401-handling code as "session expired."

**Pros:** A single implementation serving three roles avoids the exact duplication `CLAUDE.md` warns against - one endpoint, one form, one route, one nav link, instead of three near-identical copies (which is what a naive "add it separately to Users Management for admin, RegistrationPage for applicants" approach would have produced). Reusing `verifyPassword`/`hashPassword` guarantees the new password is hashed identically to how login already checks it - no risk of a second hashing convention drifting out of sync.

**Cons:** No token/session invalidation on password change - since the JWT scheme here is fully stateless (no token version, no server-side blocklist), any other already-issued, unexpired token for that user keeps working until it naturally expires (`JWT_EXPIRES_IN`, 8h in this environment). This is a real gap if "changing your password should immediately kick out anyone else logged in as you" is ever a hard requirement - it isn't enforced today for any account action (there's no equivalent revocation on role changes either), so this isn't a regression, just an existing limitation that now also applies here. There's also still no "forgot password" recovery path for a user who doesn't know their *current* password - this feature only covers the "I know my password and want to change it" case.

**Future impact:** If session invalidation-on-change becomes a requirement, the natural fix is a `tokenVersion` int on `User`, bumped in `changePassword()`, checked (and matched against the JWT payload) in the `authenticate` middleware - a schema change and a new claim, not a redesign of this feature. A true "forgot password" flow (no current password known) would need email delivery (already wired via `EmailService`) plus a time-limited reset token, which is a separate, larger feature from this one.

**Reference:** [api.md § Auth](./api.md#auth--apiauth), [project-memory.md § Auth](./project-memory.md), `backend/src/modules/auth/`, `frontend/src/features/auth/pages/ChangePasswordPage.tsx`, `frontend/src/shared/components/Layout.tsx`.

## 2026-08-12 — Forgot password (applicants): a temporary password by email, not a reset-token link; scoped to `APPLICANT` only

**Context:** Per client request ("Lets add the change password function for Applicants using their email. The email will send a temporary password and after login in it will automatically go to change password to change the temporary password"), applicants who forgot their password had no recovery path at all - the 2026-08-09 self-service change entry above explicitly flagged this gap and anticipated it would need "a time-limited reset token," i.e. a reset-link flow. The client's own spec is different and simpler: email a temporary password directly, and force a change immediately after the applicant logs in with it - no link, no separate token/expiry model to build.

**Decision:** New `POST /api/auth/forgot-password` (unauthenticated, `{ email }`), scoped to `APPLICANT` role accounts only - a silent no-op (still 204) for unknown emails *and* for `ADMIN`/`PANEL` accounts, so the endpoint can't be used to enumerate registered emails or to force-reset an admin/panel account through what's meant to be an applicant self-service path. On a match: `generateTemporaryPassword()` (new util, `crypto.randomInt` over a 12-character charset with visually ambiguous characters removed - it's read off an email and retyped), hashed via the existing `hashPassword`, saved, and `User.mustChangePassword` set `true` (new column, default `false`). Logging in with it works through the unchanged `login()` path (a temporary password is still just `passwordHash`), but the response's `user.mustChangePassword` is now `true`, and `ProtectedRoute`/`HomeRedirect` force a redirect to `/account/password` before anything else in the app is reachable - reusing the existing role-agnostic `ChangePasswordPage` from the entry above (its `currentPassword` field just happens to be the temporary one) rather than building a separate "set your new password" screen. `AuthRepository.updatePassword()` (called by both the forced and any future voluntary change) always clears `mustChangePassword`, so the gate can't outlive a completed change even if a frontend code path forgot to clear it locally.

**Pros:** No new token/expiry model, no reset-link email-click-through flow, no separate "reset password" page to build - the temporary password *is* the credential, and the existing login + change-password endpoints handle the rest unmodified. Scoping to `APPLICANT` matches the client's explicit ask ("for Applicants") and avoids widening this into a general account-recovery tool for admin/panel accounts without a decision to do so. The generic 204-regardless-of-outcome response and the role check being silent (not a 403) both close the account-enumeration angle a naive "404 if not found" implementation would have opened.

**Cons:** A temporary password sits valid and unused in the mailbox indefinitely (no expiry) until someone logs in with it - unlike a reset-token link, which is easy to time-box. Anyone with mailbox access at any point in the future could still use it, though this is no weaker than "someone read your password reset email" would be for a link-based flow either. `mustChangePassword` being a plain response field (not a JWT claim) means it's only as fresh as the last login/register response or the frontend's own local clear on successful change - there's still no `GET /me` endpoint to re-resolve it from elsewhere, consistent with the existing `registrationComplete` pattern's same tradeoff (see [project-memory.md](./project-memory.md) Technical Debt). No rate-limiting on the endpoint - an attacker who knows an applicant's email could spam temporary passwords to that inbox repeatedly; acceptable for now given this environment has no rate-limiting anywhere else either, but worth revisiting before production.

**Future impact:** If admin-initiated password reset (the other still-outstanding item in project-memory.md's Known Limitations) is ever built, it can reuse `setTemporaryPassword`/`mustChangePassword` directly rather than inventing a second mechanism - the only new piece would be an ADMIN-authenticated endpoint that looks up by user id instead of self-service by email. If mailbox-indefinite-validity ever becomes a real concern, add a `temporaryPasswordIssuedAt` timestamp and reject stale ones in `login()` - a small, additive change, not a redesign.

**Reference:** [api.md § Auth](./api.md#auth--apiauth), [database.md § users](./database.md#users), [architecture.md § Forgot password (applicants)](./architecture.md#forgot-password-applicants), `backend/src/modules/auth/`, `backend/src/shared/utils/password.ts`, `backend/src/shared/email/authEmailTemplates.ts`, `frontend/src/features/auth/pages/ForgotPasswordPage.tsx`, `frontend/src/features/auth/pages/ChangePasswordPage.tsx`, `frontend/src/shared/components/ProtectedRoute.tsx`.

## 2026-08-12 — Password complexity: composition rules + a common-password blocklist, not a NIST-purist length-only policy

**Context:** Per client request ("Lets solve no password complexity rules beyond length of 8 characters. Implement best password practice"), every password field in the app (`register`, `me/password`'s `newPassword`, and admin-provisioned `POST /api/users`) only enforced an 8-character minimum - long enough to satisfy NIST 800-63B's own minimum, but NIST's modern guidance (length over complexity, screen against breached-password lists, no forced composition rules) is itself deliberately at odds with what "password complexity rules" conventionally means and what the client explicitly asked to add. A purely NIST-purist length-only policy would have been *no change at all* from what already existed.

**Decision:** New `passwordPolicySchema` (`backend/src/shared/utils/password.ts`), applied everywhere a *new* password is set (never to `currentPassword`/login, which only checks against the stored hash): 8-72 characters (the upper bound isn't arbitrary - bcrypt silently truncates/ignores input past 72 bytes, so accepting longer input than that would create a false sense of extra strength for characters that never actually reach the hash), one lowercase letter, one uppercase letter, one number, one special character, and rejection of a small curated list of common weak passwords (`password1`, `qwerty123`, etc. - not a full breached-password-database check like Have I Been Pwned's k-anonymity API, which is future work) so a password like `Password1!` can't trivially satisfy every composition rule while still being predictable. `generateTemporaryPassword()` (the forgot-password util from the entry above) was upgraded alongside this to *guarantee* at least one character from each required class via a Fisher-Yates-shuffled construction, rather than a flat random charset that might occasionally miss a class - so a temporary password always self-satisfies the same policy an applicant would otherwise need to meet by hand, in case they keep it as their real password. Mirrored on the frontend (`frontend/src/shared/utils/passwordPolicy.ts`, `validatePassword()`) for inline pre-submit feedback in `RegistrationPage`, `ChangePasswordPage`, and the admin `UsersManagementPage` create-user form - the backend schema remains the sole source of truth, this is purely UX.

**Pros:** One shared schema reused across all three password-creation DTOs (`registerSchema`, `changePasswordSchema`, `createUserSchema`) means the rule can't drift between them the way three independently-hand-typed `.min(8)` calls already almost did. Zod's `.refine()` chain reports every broken rule at once (not just the first), so a user immediately sees everything wrong with a rejected password in one round trip instead of fixing one issue at a time. Capping at 72 characters closes a real, if minor, correctness gap (bcrypt's silent truncation) that existed even before this change and nobody had addressed.

**Cons:** Composition rules (require this character class, that character class) are exactly what NIST 800-63B recommends *against*, on the research finding that they push users toward predictable patterns (`Password1!`) rather than genuinely stronger passwords - this decision knowingly trades that research-backed guidance for the more conventional "complexity" the client explicitly asked for. The common-password blocklist is a short curated list, not a real breached-password check, so it stops the most obvious predictable passwords but nothing close to comprehensive. No client-side/backend rate-limiting on failed attempts against any of these endpoints (a pre-existing gap, not introduced here) means an attacker can still brute-force-guess at unlimited speed regardless of how strong an individual password's rules are.

**Future impact:** If a real breached-password check is ever added (e.g. Have I Been Pwned's k-anonymity range API - only a SHA-1 prefix leaves the server, never the plaintext password), it slots into `passwordPolicySchema` as one more async check without disturbing the existing synchronous rules (though `z.string().refine()` would need to become `.refine(async ...)` or the check moved into the service layer, since Zod's synchronous `safeParse` can't await). If NIST-purist guidance is ever explicitly preferred instead, the composition `.refine()` calls are the only things to remove - length + blocklist alone already satisfies that model.

**Reference:** [api.md § Auth](./api.md#auth--apiauth), `backend/src/shared/utils/password.ts`, `backend/src/modules/auth/auth.dto.ts`, `backend/src/modules/users/users.dto.ts`, `frontend/src/shared/utils/passwordPolicy.ts`, `frontend/src/features/applicant-registration/pages/RegistrationPage.tsx`, `frontend/src/features/auth/pages/ChangePasswordPage.tsx`, `frontend/src/features/admin/pages/UsersManagementPage.tsx`.

## 2026-08-09 — Full official documents checklist; Designation/IPCR moved from a per-application gate to optional registration documents

**Context:** Client-supplied requirement: the Documents step needed to list the actual official application-documents checklist (Application Letter with a specific addressee/thru block, PDS, Performance Rating, eligibility certificate, L&D certificates, Transcript of Records, Diploma, PQE passing notice, Designation proof, Award proof), and Designation to a Higher Position was explicitly called out as optional - it should never block applying to a higher (promotional) position. **Pros:** Applicants now see exactly what the official process expects, in the same order and wording as the paper checklist, rather than reverse-engineering it from a generic type dropdown. Removing the promotional gate matches the explicit "designation should not be a requirement" instruction without leaving a half-relaxed, inconsistent rule (IPCR still blocking while designation doesn't). Reusing existing enum values for Performance Rating/Designation avoided a migration that would've had to rewrite existing `IPCR`/`DESIGNATION_ORDER` rows to a new type.

**Cons:** `completeRegistration()` gained two new hard requirements (Application Letter, PDS) that didn't exist before - any already-registered applicant is unaffected (the check only runs once, at completion, not retroactively), but this does mean registration is now measurably harder to finish for anyone who hasn't gathered those two documents yet. The checklist's optional/required split is enforced client-side as informational badges plus the two backend-checked exceptions above; nothing stops an applicant from finishing registration having uploaded zero of the eight purely-optional items, which is intentional (matches "if applicable"/"if any") but means the checklist is partly aspirational, not a hard gate on data completeness.

**Future impact:** If a future requirement wants per-item validation (e.g. block finishing registration without a Transcript of Records when a post-graduate degree is claimed), that's a new conditional check in `completeRegistration()` alongside the existing three, not a redesign. If the checklist wording or addressee/thru block ever changes (e.g. a new Regional Director), it's a single static text block in `DocumentsSection.tsx` to edit - not stored data, so no migration.

## 2026-08-09 — L&D and Award proof required per entry, extending the same rule Eligibility already used; Awards rebuilt to match L&D's per-entry upload pattern

**Context:** Client-supplied requirement: "if applicant put something in [Learning & Development or Awards] they are also required to upload proofs of their claims, same with Eligibility if applicant has one." L&D already had a per-entry proof mechanism (`Document.ldInterventionId`, built in an earlier pass) but it was optional - `completeRegistration()` never checked it. Awards had no proof mechanism at all: `AWARD_PROOF` existed only as a generic applicant-level type in the Documents dropdown (from the same-day documents-checklist entry above), with no way to tie a specific proof file to a specific award - so there was no way to enforce "prove *this* award" even if we wanted to, only "prove *some* award exists somewhere."

**Decision:** Added `Document.awardId` (nullable FK to `Award`, `onDelete: Cascade`, mirroring `ldInterventionId` exactly - migration `20260809093325_add_document_award_id`) and rebuilt `AwardsSection` to match `LdInterventionSection`'s per-row upload/list/remove UI verbatim (shared `.proof-item` CSS, renamed from `.ld-proof-item` since it's no longer L&D-specific). `ApplicantsService.completeRegistration()` now requires a matching proof for **every** `LdIntervention`/`Award` row the applicant added - `documents.some(doc => doc.type === "LD_PROOF" && doc.ldInterventionId === entry.id)` per entry, not just "at least one `LD_PROOF` document exists somewhere" - and 400s naming the specific entry's title if one's missing, so the applicant knows exactly which claim needs proof rather than a generic "upload something." `AWARD_PROOF` was removed from the generic Documents-step dropdown (mirroring how `LD_PROOF` was already excluded), since a generic untied upload wouldn't satisfy the new per-entry check anyway - it would only confuse the applicant into thinking they'd satisfied a requirement they hadn't. `RegistrationPage`'s "Finish registration" gate and warning list were extended the same way, listing every entry still missing proof by name.

**Pros:** Directly implements the stated rule with no special-casing - Eligibility, L&D, and Award proof are now the same pattern ("claimed something → prove that specific thing") at three different granularities (one flag, N interventions, N awards), rather than three different enforcement styles. Reusing `LdInterventionSection`'s exact UI shape for `AwardsSection` means no new interaction pattern to learn and the shared `.proof-item` CSS instead of a second near-identical rule.

**Cons:** `completeRegistration()`'s validation cost now scales with the number of L&D/award entries (one `.some()` scan per entry against the full document list) - fine at registration-form scale, would need indexing/restructuring if an applicant could plausibly have hundreds of entries, which isn't a real scenario here. An applicant who wants to remove an unprovable claim rather than find its proof has to delete the whole entry (title, dates, agency) via `LdInterventionSection`/`AwardsSection`'s existing "Remove" button - there's no "mark as no longer claiming this" short of deletion, same limitation the pre-existing Eligibility checkbox already has (unchecking it, not the entry, is the only way).

**Future impact:** If per-entry proof ever needs to become "at least one proof across all entries is enough" (looser) or "specific proof types per entry" (stricter), the single per-entry `.some()` check in `completeRegistration()` is the one place to change for both L&D and Award. ## 2026-08-09 — Re-uploading a single-instance document type replaces it, rather than rejecting the upload or leaving duplicates

**Context:** User-reported: "I can upload multiple PDS and Application Letter. Is this ok?" Nothing broke functionally - `completeRegistration()`'s check is satisfied by *any* document of the required type existing - but the Documents table would accumulate indistinguishable duplicates with no way to tell which one is authoritative, which is a real problem for a document an admin will eventually review. The generic upload flow (`DocumentsSection`'s type dropdown + file input) had no concept of "this type already has a file."

**Decision:** For the eight document types that represent one current document per applicant (`APPLICATION_LETTER`, `PDS`, `IPCR`, `ELIGIBILITY_PROOF`, `TRANSCRIPT_OF_RECORDS`, `DIPLOMA`, `PQE_NOTICE`, `DESIGNATION_ORDER`), `DocumentsService.upload()` now deletes any existing document of that same type for the applicant (DB row + file on disk) before inserting the new one - re-uploading replaces rather than duplicating or erroring. `LD_PROOF`/`AWARD_PROOF` were initially excluded from this rule (multiple proofs per entry was the intentional design when those features were built), but see the same-day follow-up below - that stance was reversed a few hours later, same day, once the client saw the multi-file behavior in practice and asked for one-per-entry instead. `OTHER` remains a genuine multi-file miscellaneous catch-all, exempt throughout. The frontend mirrors the same type set (necessarily duplicated, `SINGLE_INSTANCE_TYPES` in both `documents.service.ts` and `DocumentsSection.tsx`) so it can drop the now-stale local entry and label the toast "replaced" instead of "uploaded."

**Follow-up (same day):** Client asked for the "Document type" dropdown to stop offering a type once it's already on file, rather than letting the user re-select it and silently trigger a replace. `DocumentsSection` now filters its dropdown to `computeAvailableTypes(items)` - single-instance types disappear from the list the moment a document of that type exists, reappearing only if the applicant removes it via the table's existing "Remove" button first. This makes the backend's replace-on-reupload path effectively unreachable through normal UI use (you can no longer select an already-satisfied type to trigger it) while leaving it in place server-side as a defensive fallback - harmless, and still correct if ever reached some other way. The same "controlled `<select>` value must always match a rendered `<option>`" bug fixed earlier this session for the eligibility dropdown applies here too: `type` state is now initialized lazily from `computeAvailableTypes(items)` on mount, and explicitly advanced to the next available type right after a successful upload removes the just-uploaded type from the list - both needed so the dropdown's value can never point at an option that no longer renders.

**Pros:** Matches how most people expect a single-slot file upload to behave (re-upload = replace, like a profile photo) while the dropdown filter now makes the *intent* explicit up front - a type visibly disappearing communicates "you're done with this one" better than only finding out via a "replaced" toast after the fact. Guarantees each single-instance type has at most one row - no ambiguity for whoever reviews the Documents list later. Enforced server-side, not just hidden in the UI, so it holds even if a client somehow re-submits the same type twice.

**Cons:** A user who wants to fix a wrong upload now has one extra required step (Remove, then re-add) instead of just re-selecting and re-uploading over it - a deliberate tradeoff for making "this type is already covered" visible rather than silent. No confirmation dialog before the underlying replace, unlike every other destructive action in this app (`ConfirmDialog` is used everywhere else data is deleted) - moot in the common path now that the dropdown won't let you reach it, but still true for the defensive backend fallback.

**Future impact:** If a type ever needs to allow more than one file *and* replace-on-type (neither "accumulate" like `LD_PROOF` nor "single slot" like `PDS`), both `SINGLE_INSTANCE_TYPES` sets and `computeAvailableTypes()` are the two places to introduce a third category.

## 2026-08-09 — PDS split into a required PDF copy and a required Excel copy, with per-document-type file-type enforcement

**Context:** Client-supplied requirement: "Applicants are required to upload Pdf and excel file of PDS. Make sure system will check the file type correctly." The real-world CS Form 212 (PDS) is filled out as an Excel workbook (needed as data, e.g. for future PDS-driven features) but is also conventionally submitted as a signed/scanned PDF. Before this change `PDS` was one single-instance slot, PDF/JPEG/PNG only (the same blanket rule every document type shared) - there was no way to require the actual spreadsheet at all, and no per-type file-type enforcement anywhere: the only gate was multer's global `fileFilter` allowing PDF/JPEG/PNG for every type indiscriminately, so nothing stopped (say) a JPEG being uploaded as "PDS" today, and nothing would have stopped an Excel file being uploaded as an Application Letter once Excel support was added for PDS.

**Decision:** Added a new `DocumentType.PDS_EXCEL` (migration `20260809105041_add_pds_excel_document_type`), a second single-instance slot alongside the existing `PDS` (now labeled "— PDF copy" in the UI, `PDS_EXCEL` labeled "— Excel (CS Form 212) copy"). `ApplicantsService.completeRegistration()` now requires both. File-type checking became genuinely per-`DocumentType` rather than one global rule: multer's `fileFilter` (`documents.upload.ts`) was widened to the *union* of every type's allowed MIME types (PDF/JPEG/PNG plus the two Excel MIME types already used by the PQE score import) - it's just the outer gate, since `fileFilter` runs mid-multipart-stream and can't reliably depend on `type` if it's a form field ordered after `file`. The authoritative check is new: `DocumentsService.upload()` calls `assertMimeTypeAllowed(fields.type, file.mimetype)` against `ALLOWED_MIME_TYPES_BY_DOCUMENT_TYPE`, run after multer has fully parsed the request (so `fields.type` is always populated regardless of field order) - every type defaults to PDF/JPEG/PNG except `PDS_EXCEL`, which requires XLSX/XLS, and mismatches 400 with a message naming the expected format. The frontend (`DocumentsSection.tsx`) mirrors this: the file input's `accept` attribute and a client-side `validateFileType()` check both switch based on the selected type, and switching the "Document type" dropdown clears any already-chosen file rather than silently carrying over a selection that may no longer be valid for the new type.

**Pros:** Directly implements the stated requirement (both formats required, each validated as the format it claims to be) without special-casing PDS's validation path outside the existing single-instance-type machinery - `PDS_EXCEL` is just another entry in `SINGLE_INSTANCE_TYPES`/`DOCUMENT_CHECKLIST`/`DOCUMENT_TYPE_LABELS`. The per-type MIME map is a real fix, not just scoped to PDS: an Excel file can no longer be uploaded as e.g. `APPLICATION_LETTER` even though multer's outer gate now allows the MIME type through generally - verified via direct API testing (5 cases: PDS_EXCEL-as-JPEG rejected, PDS_EXCEL-as-XLSX accepted, PDS-as-XLSX rejected, PDS-as-PDF accepted, APPLICATION_LETTER-as-XLSX rejected). Two-layer enforcement (broad multer gate + precise per-type service check) avoids relying on multipart field ordering, which is a documented but fragile way to make `fileFilter` type-aware.

**Cons:** Widening multer's `fileFilter` to accept Excel MIME types globally means a mismatched file (e.g. an Excel file selected for `APPLICATION_LETTER`) is now written to a temp path on disk by multer before `DocumentsService.upload()` rejects it and the request 400s - the file is never linked from a DB row (so it doesn't show up anywhere in the app) but is left orphaned in `backend/uploads/` with nothing to clean it up. This isn't a new problem this change introduced (every existing validation failure in `upload()` - e.g. an unowned `applicationId`/`ldInterventionId`/`awardId` - already has the same orphan-on-reject gap, since multer always finishes writing before the service runs) but the surface area is larger now that more MIME types clear the outer gate only to be rejected by the inner one. `PDS`'s own allowed types didn't change (still PDF/JPEG/PNG, not narrowed to PDF-only) since the client's requirement was "PDF and Excel," not "PDF only" - a scanned PDS photographed as JPEG still passes, consistent with every other document type's tolerance for a photo of a paper copy.

**Future impact:** `ALLOWED_MIME_TYPES_BY_DOCUMENT_TYPE` in `documents.service.ts` is now the one place to add a stricter or different file-type rule for any other document type, without touching multer's `fileFilter` again. The orphaned-file-on-rejected-upload gap (pre-existing, called out above) would be worth fixing generally - e.g. `upload()` unlinking `file.path` in a catch block before rethrowing - if orphaned upload files ever become an operational nuisance; not done here since it's out of scope for this specific request and pre-dates it.

**Reference:** [database.md § documents](./database.md#documents), [api.md § Applicants](./api.md#applicants--apiapplicants-all-require-auth), `backend/src/modules/applicants/documents/documents.service.ts`, `backend/src/modules/applicants/documents/documents.upload.ts`, `backend/src/modules/applicants/applicants.service.ts`, `frontend/src/features/applicant-registration/components/DocumentsSection.tsx`, `frontend/src/features/applicant-registration/pages/RegistrationPage.tsx`.

## 2026-08-09 — Application Letter moved from a registration-time requirement to an apply-time requirement, tied to the specific application

**Context:** Client-supplied requirement: "Let's not make the Application[ Letter] not required but they will need to upload the application letter when they apply. So let's remove the Application letter uploading in registration, instead lets put it when applying on a job." Application Letter had been an applicant-level `SINGLE_INSTANCE_TYPES` document since the documents-checklist rebuild (an earlier same-day entry above) - uploaded once during registration, required by `ApplicantsService.completeRegistration()`, identical in kind to PDS/Transcript/Diploma/etc. That's a mismatch with what an application letter actually is: the real DILG addressee/thru block is fixed, but a genuine cover letter is written per vacancy, not a one-time document that's equally valid for every future application. One registration-time letter also meant an applicant with several open applications could only ever have one letter on file, silently reused (or silently replaced) across postings it was never written for.

**Decision:** `Document.applicationId` already existed (added earlier for a different, unused purpose - see [database.md § documents](./database.md#documents)) and turned out to be exactly the right shape for this: `APPLICATION_LETTER` is now created only as part of `POST /api/applications`, tied via `applicationId` to the specific `Application` it was submitted with, and removed entirely from the registration-time paths - `completeRegistration()` no longer checks for it, `uploadDocumentFieldsSchema`'s `type` enum no longer accepts it (so it can't be created "loose," untied to any application, through the generic `/applicants/me/documents` endpoint), and it's out of `SINGLE_INSTANCE_TYPES` on both backend and frontend (it's one-per-application now, not one-per-applicant). `POST /api/applications` changed from a plain JSON `{ jobPostingId }` body to `multipart/form-data` (`jobPostingId` + `file`), following the same manual-`safeParse`-in-controller pattern already used by `POST /import-exam-scores` (the `validate()` middleware can't run before multer has parsed the body). `ApplicationsService.submit()` 400s if no file is provided; on success, `ApplicationsRepository.createWithApplicationLetter()` creates the `Application` row and the `Document(type=APPLICATION_LETTER, applicationId=...)` row together inside one `db.$transaction()`, so the two can never exist independently of each other. A small shared `createDiskStorage()` helper (`backend/src/shared/upload/diskStorage.ts`) was factored out of `documents.upload.ts` so the new `applicationLetter.upload.ts` multer config (PDF/JPEG/PNG only, same as the pre-existing default rule) doesn't duplicate the mkdir/destination/filename logic a third time. On the frontend, `JobPostingsListPage`'s "Apply" button now opens a modal (file input + the DILG addressee/thru block, moved verbatim from `DocumentsSection`'s old special-cased checklist row) instead of submitting on click - applying was a single fire-and-forget click before; it's now a small form, unavoidably, since a click handler can't carry a file.

**Pros:** Matches the real-world object being modeled - a letter genuinely is per-vacancy, so "per-application" is the correct scope, not an approximation. Removing it from `completeRegistration()`'s gate also lets an applicant finish registration and start browsing/applying sooner (one fewer document blocking that milestone), while still being unable to actually submit any application without a letter for that specific one. The atomic transaction rules out the partial-state failure mode (an application that exists with no letter, or a letter uploaded with no application to show for it) that a naive "create application, then upload document" two-step client flow would have risked.

**Cons:** `POST /api/applications` is now a breaking API change (JSON → multipart) for any other API consumer, though there's only ever been the one frontend caller. The Apply flow is measurably more friction than a single click (choose a file, then confirm) - an unavoidable consequence of the letter no longer being pre-uploaded, not a regression to fix. An applicant applying to five postings now uploads five separate PDF letters even if the content barely differs, versus the old one-and-done registration upload - a real cost of correctness (each letter *should* be able to differ, addressed/dated per vacancy) but still more repeated effort than before.

**Future impact:** If a "reuse my last letter" convenience is ever wanted, `GET /api/applicants/me/documents` already returns every prior `APPLICATION_LETTER` (with its `applicationId`), so the frontend could offer "copy from a previous application" as a pre-fill without any backend change - it would still need to be re-uploaded as a new `Document` for the new `applicationId`, since one document can't belong to two applications. If per-application documents are ever needed beyond the letter (e.g. a posting-specific supplementary form), `createWithApplicationLetter()`'s transaction pattern - create the parent row and its required child document together - is the template to extend or replicate.

**Follow-up (same day), per client request:** "Apply" now shows as a disabled "Already Applied" button on any posting the applicant has already submitted to, instead of staying clickable and relying on the backend's 409 to reject the click. `JobPostingsListPage` fetches `listMyApplications()` alongside postings/profile on mount and derives an `appliedJobPostingIds: Set<string>` from the results; a successful submit adds the just-applied posting's id to that set immediately (no refetch needed) so the button flips to "Already Applied" the instant the modal closes. `canApply` gained `&& !alreadyApplied` alongside its existing accepting-applications/eligibility checks. Verified in-browser with a test applicant who'd already applied to one posting: that posting showed "Already Applied" (disabled) while every other posting kept its normal state.

## 2026-08-09 — Fixed `.app-header`'s sticky positioning, broken since the day it was added

**Context:** Client request: "Lets make our top nav sticky in Applicant page." `.app-header` already had `position: sticky; top: 0;` (present since this app's earliest CSS, likely intended to work from the start) - so the request pointed at a real, pre-existing bug rather than a missing feature. Confirmed via a live scroll test on `/register` (a long form, easy to scroll): `.app-header`'s `getBoundingClientRect().top` moved in exact lockstep with `window.scrollY` instead of staying at `0`, i.e. it behaved as `position: static` despite computing to `sticky`. Walking the DOM ancestor chain from `.app-header` up to `html` and inspecting each one's computed `overflow` found the cause: `body`'s computed `overflow` was `hidden auto`, not the authored `overflow-x: hidden` alone. Per the CSS Overflow Module spec, if `overflow-x` is set to a non-`visible` value while `overflow-y` is left `visible`, the *computed* value of `overflow-y` is forced to `auto` too (a scrolling axis can't be paired with a non-scrolling one) - so `html { overflow-x: hidden; }` / `body { overflow-x: hidden; }` (added earlier the same day, for the `.auth-page` full-bleed breakout's few px of horizontal overflow - see that entry above) silently turned both `html` and `body` into independent scroll containers. `.app-header`'s nearest such container was no longer "the real viewport scroll" in the way `position: sticky` needs.

**Decision:** Changed `overflow-x: hidden` to `overflow-x: clip` on both `html` and `body`. `overflow: clip` (CSS Overflow Level 3+) clips overflowing content the same way `hidden` does, but - unlike `hidden` - does not establish a scrollable overflow region, so it isn't subject to the overflow-x/y pairing rule and doesn't turn its element into a scroll container. This was a one-line-times-two fix once the root cause was found; no component/page code changed, since the header's `position: sticky` was already correct and every page shares the one `Layout` component. Verified with a live scroll test using the exact same method that found the bug (`getBoundingClientRect().top` before/after `window.scrollTo`) - the header now stays at `top: 0` through a scroll - and separately re-confirmed the original horizontal-overflow clipping this rule exists for still works (`document.documentElement.scrollWidth === window.innerWidth` on the login page, no regression).

**Pros:** Fixes sticky positioning for the header across every role (Applicant/Admin/Panel all share `Layout`), not just the applicant pages named in the request - the bug was never applicant-specific, it just happened to be reported from there. Root-cause fix rather than a workaround (e.g. removing `position: sticky` and hand-rolling a scroll listener, or re-adding a scroll container purpose-built for the header) - `clip` does exactly what the original `hidden` was reached for ("just clip this overflow") without the side effect that was never intended.

**Cons:** `overflow: clip` is a newer value (Chrome 90+/Firefox 113+/Safari 16+) than `hidden` - a small compatibility regression on very old browsers, where it would fall back to the initial `visible` (re-exposing the few px of horizontal overflow the rule exists to hide) rather than silently degrading to the old clipped-but-sticky-broken behavior. Judged acceptable: this app already depends on `backdrop-filter` and other modern-only CSS with no stated legacy-browser requirement.

**Future impact:** If any other ancestor ever needs `overflow-x`/`overflow-y` set independently again, reach for `clip` over `hidden` by default when scrolling that axis is genuinely never wanted - `hidden`'s scroll-container side effect is easy to reintroduce by habit and won't be obvious until something inside it that depends on viewport-relative positioning (sticky headers, but also e.g. `position: fixed` in some edge cases) quietly stops working.

**Reference:** `frontend/src/shared/styles/index.css`, [architecture.md § full-bleed auth pages](./architecture.md#registration-gating-frontend).

## 2026-08-09 — Admin document viewing: "View Documents" modal on Evaluate Applicants, and the app's first file-serving endpoint

**Context:** Client request: "In Admin Evaluate Applicant page add a view details modal that the admin can check the applicants uploaded documents for confirmation of documents uploaded." Documents were write-only from the API's perspective before this - upload your own, list your own, delete your own (all self-service, resolved from the caller's own `userId`) - with no admin-facing way to see what a specific applicant had submitted, and no endpoint anywhere in the app that served raw file bytes at all (confirmed via a full-backend grep for `sendFile`/`res.download`/`express.static`/`createReadStream` before starting - zero matches). A list-only view (type/filename/date, no way to open the actual file) would have been a much smaller change, but "confirmation of documents uploaded" for a real hiring decision reasonably means the admin can actually open and inspect the file content, not just see that a row exists.

**Decision:** Two new ADMIN-only routes on the existing `applicants.routes.ts` router (documents routes already lived there, not a separate file): `GET /applicants/:id/documents` (list a specific applicant's documents, reusing `DocumentsRepository.findByApplicant` which already took an `applicantId` directly) and `GET /applicants/documents/:id/file` (streams one document's bytes via `res.sendFile`, `Content-Type` from the stored `mimeType`, `Content-Disposition: inline`). The file route explicitly checks `fs.access(document.filePath)` before calling `res.sendFile` and throws a clean 404 `NotFoundError("Document file")` if it's missing, rather than letting a raw filesystem error surface - this is not a hypothetical: earlier the same day, an unrelated cleanup mistake in this session permanently deleted 11 real files out of storage while their `Document` rows stayed intact in the DB, so a graceful "file not found" path for exactly that scenario was already known to matter, not just defensive-programming boilerplate. On the frontend, a new `ApplicantDocumentsModal` (opened via a "View Documents" button added to `EvaluationRow`'s existing action cell) fetches the list, then on a per-document "View"/"Download" click fetches the file as a `Blob` via a new `apiRequestBlob()` helper in `apiClient.ts` (mirrors `apiRequest`'s auth header + error-unwrapping, but resolves to a `Blob` instead of parsing JSON) and turns it into an object URL - `window.open()` in a new tab for inline-renderable types (PDF/JPEG/PNG), or a synthetic `<a download>` click for XLS/XLSX, which browsers can't render inline regardless of how the URL is opened. A blob-fetch was necessary rather than a plain `<a href>`/`window.open(apiUrl)`: this route requires a Bearer token, which a simple browser navigation can't attach, and putting the token in a query string instead (so a plain link would work) was rejected as a real credential-leak risk (browser history, referrer headers, server access logs) for a token with a multi-hour lifetime - fetching with the header and converting to a blob URL keeps the token out of any URL entirely. `Modal` gained an optional `wide` prop (`.modal--wide`, 720px vs. the default 440px) since the document list's five columns didn't fit the form-sized default - kept as a boolean opt-in on the existing shared component rather than a one-off custom modal, so any other future data-table-shaped modal can reuse it.

**Pros:** Reuses existing repository/service methods and the established `requireRole("ADMIN")` route-gating pattern throughout - no new architectural pattern introduced, just the first use of a "serve a file" endpoint shape in this codebase. The missing-file 404 path was verified against a real case (viewing Juls Acidre's now-missing files correctly showed "Document file not found" instead of a broken tab or a crash), not just a theoretical one. Keeping the token out of the URL is a real, not just theoretical, security improvement over the simpler `<a href>` alternative.

**Cons:** `window.open()` inline preview can be blocked by browser popup blockers if not triggered directly inside a user click handler - it is here (the `onClick` handler calls `fetchDocumentFileUrl` and `window.open` in the same async function without an intervening `await` that a blocker would treat as "no longer a direct user gesture" in most browsers, but this is a known fragility class of `window.open`-after-`fetch` patterns generally). Object URLs from `window.open()`'s blob are revoked after a fixed 10-second delay (long enough for the new tab to finish loading the blob independently) rather than tracking the opened tab's lifetime precisely - a pragmatic timeout instead of a more complex handle-tracking scheme, since object URLs are cheap and scoped to the current page's lifetime anyway (they're not shared across tabs by reference, only by the already-loaded content).

**Future impact:** `apiRequestBlob()` is now the template for any future binary-response endpoint (e.g. if an applicant-facing "view my own uploaded document" feature is ever added, mirroring this admin one). `Modal`'s `wide` prop is available to any future modal that needs more than form-width. The `fs.access`-before-`sendFile` pattern in `getFileForAdmin()` is the template if any other endpoint ever needs to serve a file that might legitimately be missing.

## 2026-08-10 — Admin-account blue/white button hover: `<body>` class instead of an `.admin-shell` descendant selector

**Context:** Client request: "Add hover effect in all buttons across the admin account that when hovered it will become blue and text will become white. This is for consistency of all buttons in Admin Account." Buttons in the app currently hover differently per variant - `.secondary` lightens to a pale blue tint (text stays navy), `.danger` darkens to a darker red, `.accent` darkens to a darker gold, and only the plain primary button already hovers to a (darker) blue with white text. The client wants one consistent blue/white hover across every admin action button regardless of variant.

**Decision:** Scoped the new hover rule off a class on `<body>` (`admin-account`), toggled by `AdminShell` (`document.body.classList.add/remove` in a `useEffect`, added/removed on mount/unmount) - not off `.admin-shell` as a plain CSS-descendant selector, even though every admin page is wrapped in `.admin-shell`. Reason: `Modal` (and `ConfirmDialog`, which is built on it) renders via `createPortal(..., document.body)`, so a Job Management "Add Job" form, a Users Management delete confirmation, or the Evaluate Applicants "View Documents" modal all render as DOM siblings of `.admin-shell`, not descendants of it - a `.admin-shell button:hover` rule would silently miss every button inside any admin modal, which is a large fraction of the admin account's actual buttons. `AdminShell` already mounts fresh per page (each admin page component wraps itself in `<AdminShell>`, there's no single persistent layout route), so add/remove-on-mount/unmount naturally tracks "currently viewing an admin page" with no extra routing logic.

The rule itself: `body.admin-account button:not(:disabled):not(.modal-close):not(.user-menu-trigger):not(.password-toggle):hover { background: var(--color-primary); color: #fff; border-color: var(--color-primary); }`. Three exclusions were deliberate, not oversights: `.modal-close` (the dialog's "×"), `.user-menu-trigger` (header email dropdown), and `.password-toggle` (Change Password's eye icon) are icon/utility controls that already have their own established, more subtle hover treatment from earlier work this session - turning them into solid blue-white boxes would look heavy-handed and wasn't what "action buttons" means in context. `:not(:disabled)` preserves every existing `button:disabled:hover`/`button.secondary:disabled:hover` override already in the stylesheet, so a disabled button still reads as inert on hover instead of flashing blue.

**Pros:** One rule instead of four (would otherwise need `button:hover`, `button.secondary:hover`, `button.danger:hover`, `button.accent:hover` each overridden separately within the admin scope). Reaches portaled modal buttons for free, which a plain ancestor selector cannot. `:not(:disabled)` keeps disabled-button behavior exactly as it already was elsewhere in the app.

**Cons:** A `<body>`-level class is slightly more "global" than a scoped component class, and in principle a bug in the toggle logic (e.g. an early return skipping the `useEffect` cleanup) could leak the class past navigation - mitigated by using a plain mount/unmount `useEffect` with no conditional early-return, and verified live (`document.body.className` is empty again after navigating to `/login`).

**Future impact:** Any new modal/dialog opened from an admin page automatically gets the same hover treatment with no extra wiring, since it's scoped by `<body>`, not by the triggering component's subtree. If a future non-admin page ever needs the same "portal reaches document.body" scoping problem solved, this is the established pattern to reuse.

## 2026-08-11 — Panel document access: viewer-scoped `DocumentsService`, PDS-only, assignment-gated — not a separate panel-facing endpoint

**Context:** Panelists needed a way to check an applicant's PDS while interviewing them, without reopening the broader "admin can see everything" access `docs/decisions.md`'s 2026-08-09 "Admin document viewing" entry established. Two shapes were possible: a new `PANEL`-only route (e.g. `GET /panel-evaluations/:applicationId/documents`) duplicating the list/stream logic already built for admin, or widening the existing `GET /applicants/:id/documents` / `GET /applicants/documents/:id/file` routes to accept `PANEL` too with role-conditional scoping inside the same service. Least-privilege requirements for `PANEL` are stricter than `ADMIN`'s: only the PDS (`PDS`/`PDS_EXCEL`, not the full checklist an admin can see), and only for an applicant the panelist is actually assigned to interview right now — not any applicant, and not after the interview stage has moved on.

**Decision:** Widened the existing two routes to `requireRole("ADMIN", "PANEL")` instead of adding a parallel panel-specific endpoint. `DocumentsService.listForApplicant`/`getFileForViewer` (the latter renamed from `getFileForAdmin` now that it's not admin-exclusive) each take a new `viewer: { id: string; role: Role }` parameter. A private `assertPanelistMayViewApplicant()` helper runs only when `viewer.role === "PANEL"`: it calls a new `PanelAssignmentsRepository.isPanelUserAssignedToApplicant(panelUserId, applicantId)` (counts `Application` rows where `applicantId` matches, `status: "FOR_INTERVIEW"`, and the posting has a `PanelAssignment` for this panel user) and throws `ForbiddenError` if it's false; the document list is separately filtered to `PANEL_VISIBLE_DOCUMENT_TYPES = new Set(["PDS", "PDS_EXCEL"])` for `PANEL` callers. `ADMIN` callers skip both checks entirely — behavior there is byte-for-byte unchanged from before this change. `DocumentsService` gained `PanelAssignmentsRepository` as a constructor dependency (wired in `container.ts`). On the frontend, `InterviewRow` opens the existing `ApplicantDocumentsModal` (unchanged) rather than a new panel-specific component, since the backend scoping alone is sufficient to make it behave correctly for a `PANEL` caller.

**Pros:** One code path (list/filter/stream) instead of two means the PDS-visibility and assignment rules can't drift between an admin route and a hypothetical panel route implementing the same idea slightly differently. Reuses `ApplicantDocumentsModal`/`apiRequestBlob()` from the 2026-08-09 admin document-viewing work as-is — no new frontend document-rendering code at all. The assignment check reuses the exact same "is this panelist currently on this posting's board for a `FOR_INTERVIEW` application" concept `panel-evaluations` already enforces for scoring (`PATCH /panel-evaluations/:applicationId` 403s the same way), so "can view" and "can score" track the same underlying fact rather than two separately-maintained authorization rules.

**Cons:** `DocumentsService`'s two methods are now slightly more complex (an extra parameter, a role branch) than a route split would have kept them; a future third viewer role with yet another visibility rule would add a third branch rather than a third clean file. Access is tied to `status === "FOR_INTERVIEW"` specifically — once an application moves past interview (e.g. a future Deliberation status), a panelist who interviewed them loses PDS access with no grace period, which is untested against the not-yet-built Deliberation phase and may need revisiting once that exists.

**Future impact:** If a fourth role or a fourth visibility policy is ever needed, `assertPanelistMayViewApplicant()` and `PANEL_VISIBLE_DOCUMENT_TYPES` are the two places to extend, not the routes or controller. See [patterns.md § Role-Based Access Control](./patterns.md#role-based-access-control-route-guard) for the general shape of this "shared route, role-conditional service-level scoping" variant, now used alongside the simpler all-or-nothing route guard.

## 2026-08-11 — Applicant Scores overview: cross-posting, admin-only, ranked client-side instead of server-side

**Context:** Client request: "In Evaluation Criteria add a button Applicant Scores button that will open a modal of the list of applicant that has score in the Evaluation phase by ranking per Criteria." The existing `PanelEvaluationsService.tabulation()` already computes a ranked matrix, but it's scoped to one job posting (a parameter on the route) and ranks by a single fixed column (overall average). "Ranking per Criteria" implied the admin needs to re-rank by whichever criterion they're currently interested in, not just the overall total, and the request's placement on the Evaluation Criteria page (not Evaluate Applicants, which is already per-posting-filterable) implied a rubric-centric, cross-posting view rather than another per-posting screen.

**Decision:** New `PanelEvaluationsRepository.findApplicationsWithScores()` (no `jobPostingId` parameter, unlike `findApplicationsForTabulation()`) fetches every application across all postings in the same `TABULATION_STATUSES` set (`FOR_INTERVIEW`/`QUALIFIED`/`NOT_QUALIFIED`) that has at least one submitted `PanelEvaluation` (`panelEvaluations: { some: {} }`), so unscored applications never appear in this view at all — there's nothing to rank them by. `PanelEvaluationsService.applicantScoresOverview()` computes, per active criterion, the *average* score across every panelist who scored it (criteria can legitimately be scored differently by different panelists, unlike `tabulation()`'s per-panelist total columns) and each applicant's average total, but deliberately does **not** sort or assign a rank — it returns `{ criteria, rows }` in submission order. Ranking is instead computed client-side in `ApplicantScoresModal`'s `rankRows()`, driven by a "Rank by" `<select>` (overall total or any one active criterion), recomputed via `useMemo` on every selection change. `GET /panel-evaluations/applicant-scores` is `ADMIN`-only (same as `/tabulation/:jobPostingId` — panel members don't get either cross-application view).

**Pros:** A single "rank by any column, interactively" requirement is naturally a frontend re-sort of already-fetched data, not N different server endpoints (or one endpoint with a `?rankBy=` query param re-querying on every dropdown change) — the entire dataset for this view is small (every scored Evaluation-phase applicant, not every applicant in the system) so fetching it once and re-sorting in memory is cheap and instant, with no network round-trip per rank-by change. Reusing `tabulation()`'s existing `totalScore()` helper (via the new `average()` helper alongside it) keeps "how is one panelist's total computed" defined in exactly one place even though this view aggregates it differently (average across panelists, not per-panelist columns).

**Cons:** Two similar-but-not-identical CompAss-adjacent computations now exist side by side (`tabulation()`: per-posting, per-panelist columns, server-ranked; `applicantScoresOverview()`: cross-posting, per-criterion averages, client-ranked) rather than one generalized function — a deliberate choice given they answer genuinely different questions (whose column set and rank-key work orthogonally), but a future reader has to check which one they need rather than there being an obvious single entry point. Client-side ranking also means a very large future dataset (many active job postings all mid-evaluation simultaneously) would need pagination-aware server-side ranking eventually — not a concern at current data volumes (this view already paginates the *rendered* rows 10/page via `usePagination`, but the full ranked set is still computed in the browser first).

**Future impact:** If this view's dataset grows large enough that fetching-then-sorting client-side becomes noticeably slow, the fix is a `?rankBy=` query param on `GET /panel-evaluations/applicant-scores` that sorts server-side before responding — `applicantScoresOverview()`'s per-criterion averages are already computed there, only the sort step would move. If a future requirement wants this same "rank by any column" interaction on the existing per-posting `tabulation()` view too, `ApplicantScoresModal`'s `rankRows()` is directly reusable against `TabulationRow[]` with a small type adjustment, rather than needing a second implementation.

## 2026-08-11 — Compliance to Requirements & Oath-Taking: Deliberation absorbed into one admin action, checklist items snapshotted not live-joined, catalog global not per-posting

**Context:** Per the domain spec's §6-7 and a client request ("After Evaluation of Applicant theres Compliance to requirements and Oathtaking. For Compliance Requirements the Applicants will just pass all the requirements before moving to Oathtaking"), the pipeline needed to continue past `FOR_INTERVIEW`/CompAss. The spec's step 5 ("Deliberation") describes a board meeting + PDC approval before the RD's decision, but the app has no existing concept of a distinct system state for that - every prior phase transition (Sifting, schedule-interview) is already just "one admin judgment-call action" against data the app already shows (the CompAss matrix, in this case). Three design questions needed answers before writing any code: (1) does Deliberation get its own status, or is it absorbed into the next action; (2) is a checklist item's requirement list computed live against the admin's current catalog, or snapshotted at some point; (3) is the requirement catalog itself per-job-posting or global.

**Decision:** (1) No `DELIBERATION` status - `PATCH /applications/:id/move-to-compliance` (`FOR_INTERVIEW` → `FOR_COMPLIANCE`) *is* the RD's decision, the same shape every other transition already is. (2) `ApplicationsService.moveToCompliance()` bulk-creates one `PENDING` `ApplicationComplianceItem` per currently-active `ComplianceRequirement` at that moment (`ComplianceItemsRepository.createManyForApplication()`) - a snapshot, not a live join against the catalog. (3) `ComplianceRequirement` is a global catalog (`compliance_requirements` table, admin CRUD at `/api/compliance-requirements`), not scoped to a `JobPosting`.

**Pros:** (1) Reuses the exact same "guard clause on current status + repository write + audit log + email" shape every other `ApplicationsService` method already follows - no new abstraction, and the RD's decision-making itself (the actual board meeting) stays an offline process the app doesn't need to model, matching how the app has never modeled *how* an admin arrives at a Sifting pass/fail either. (2) A snapshot means an applicant's checklist is stable once they enter Compliance - reviewing it, and the "all items verified" gate for scheduling Oath-Taking, both work against a fixed set the admin can reason about, instead of a set that could silently grow mid-review if someone edits the catalog. (3) Global keeps the catalog CRUD as simple as `evaluation-criteria` (which made the same simplification, see Known Limitations in project-memory.md) and matches the domain spec's framing of the CSC-mandated requirements as generic ("as mandated by CSC"), not position-specific.

**Cons:** (1) There's no dedicated audit trail entry distinguishing "the RD decided" from "an admin clicked a button on the RD's behalf" - if that distinction ever matters operationally, it isn't captured anywhere beyond the generic `actorUserId` on the audit log row. (2) A requirement added to the catalog *after* an applicant is already `FOR_COMPLIANCE` never appears on their checklist - they'd need to be moved back to `FOR_INTERVIEW` and re-advanced (no such reversal exists) to pick it up, or the admin handles it manually outside the system. Not engineered around since it's a genuine edge case (requirement catalogs are expected to stabilize quickly, unlike job postings). (3) If a future posting genuinely needs different CSC requirements than another (unlikely per the spec's wording, but possible), the catalog would need a `jobPostingId` column and a migration - not a same-shape extension the way adding a new requirement row is.

**Future impact:** If Deliberation ever needs its own tracked state (e.g. a formal PDC sign-off date, or multiple board members' approval), it would insert between `FOR_INTERVIEW` and `FOR_COMPLIANCE` as a new status - `moveToCompliance()`'s current precondition (`status === "FOR_INTERVIEW"`) would become `status === "FOR_DELIBERATION"` or similar, a small, contained change. The snapshot approach is the same pattern to reach for if any other admin-managed catalog (e.g. a future PDC checklist) needs a per-application stable copy. Two related, smaller decisions made without their own entries here: the review UI is a new `ComplianceReviewModal`/`ComplianceChecklistSection` pair rather than extending `ApplicantDocumentsModal`/`LdInterventionSection`, following this codebase's established "separate component per concern" convention (see `ApplicantScoresModal` vs. `ApplicantDocumentsModal`); and `ApplicationComplianceItem.status` only tracks the *review* outcome (`PENDING`/`VERIFIED`/`REJECTED`), not a separate "submitted" state - whether the applicant has uploaded proof is derived from the `documents` join at read time, the same "no redundant status field" choice `LD_PROOF`/`AWARD_PROOF` already made.

## 2026-08-19 — Structured qualification minimums for Sifting: soft-check hint, not a hard gate; computed client-side, not persisted; a single years-of-experience number, not a revived WorkExperience list

**Context:** Client question during Job Management: "how can the system determine that applicant has this Education, Eligibility, Training and experience" when `qualificationEducation`/`qualificationTraining`/`qualificationExperience`/`qualificationEligibility` are free text with no applicant-side structured counterpart (only `eligibilityType` was already structured, via the existing `job_posting_required_eligibilities` hard gate at apply time). Client asked to implement all of an earlier recommendation: add a closed `educationLevel` on `Applicant` matched against a `minEducationLevel` on `JobPosting`, a numeric `minYearsExperience` "computed from summing `WorkExperience` date ranges", and a numeric `minTrainingHours` summed from `LdIntervention.numberOfHours`, all shown as a hint on the Sifting screen.

Implementing the Experience piece surfaced that the original recommendation's premise was wrong: `WorkExperience` exists in `schema.prisma` but is **never collected anywhere in the app** - `RegistrationPage.tsx` deliberately excludes it ("Work experience isn't collected here - it's already part of the required PDS upload… asking for it twice would just be duplicate data entry"), so the table is permanently empty and summing it would always produce a false "0 years" reading. Reviving a full work-experience-entries step would reverse that documented decision and reintroduce the exact duplication it was written to avoid.

**Decision:** Four things, together:
1. **Soft-check hint, not a hard gate.** All three new minimums (`minEducationLevel`, `minYearsExperience`, `minTrainingHours` on `JobPosting`) are optional (`null` = no automatic check for that criterion) and never block Sifting or submission - they render a "Meets"/"Below minimum"/"No automatic check" badge next to each free-text QS line in `EvaluationRow`'s Sift modal, but the sifting decision itself stays a human `QUALIFIED`/`NOT_QUALIFIED` judgment call, same as today. This mirrors how `requiredEligibilityTypes` already works as a hard *submission* gate while the badge here is a Sifting-time *decision aid* - a different point in the pipeline, deliberately not another hard block.
2. **A single `Applicant.yearsOfExperience: Int` field, not a revived `WorkExperience` list**, collected once on the Demographic Profile step alongside a new `Applicant.educationLevel: EducationLevel` (an ordered enum, `ELEMENTARY` … `DOCTORATE`, compared by ordinal position - see `backend/src/shared/constants/educationLevels.ts`). One self-reported number is the smallest structured addition that makes the Experience hint honest without duplicating the PDS the way a full entries list would - the `WorkExperience` table itself stays exactly as unused as it already was; this decision doesn't touch it.
3. **Computed client-side (`frontend/src/shared/utils/qualificationMatch.ts`), not persisted or returned by the API as its own field.** The alternative - computing it server-side once in `ApplicationsService.listForAdmin()` and attaching it to the response - would go stale the instant any other endpoint (`sift`, `scheduleInterview`, …) replaced that same application row in the frontend's local state with a response that never computed the field, silently dropping the badge after the first action on a row. Computing it fresh from data every `AdminApplication` response already carries (`applicant.educationLevel`/`yearsOfExperience`/`ldInterventions`, `jobPosting.minEducationLevel`/`minYearsExperience`/`minTrainingHours`/`requiredEligibilityTypes`) sidesteps that entirely - correct by construction on every render, no server round trip.
4. **Free-text `qualificationX` fields stay authoritative**, never derived from or replaced by the structured minimums - "Bachelor's degree relevant to the job" carries a relevance judgment no enum/number can capture, so the badge is explicitly framed in the UI as "an automatic hint … the free-text standard is still the authoritative wording to weigh when sifting."

**Pros:** No new hard-block risk (a posting with an unset or miscalibrated minimum still sifts exactly as before - "no automatic check" rather than a false pass/fail); the Experience field is honest given what's actually collected today, rather than silently wrong; the client-side computation can never desync from whichever endpoint last touched a row, unlike a server-computed field would; and every piece is additive/nullable, so no existing posting or applicant needs a data backfill (`minEducationLevel`/`minYearsExperience`/`minTrainingHours` default to `null` = unchanged behavior for every posting created before this).

**Cons:** `yearsOfExperience` is self-reported and un-auditable against the PDS the way a real per-entry `WorkExperience` list (with dates an admin could sanity-check) would be - an applicant could overstate it with no proof requirement, unlike `hasEligibility`/L&D/Awards which all require a matching proof document. The four-field qualification-match block is one more thing rendered inside `EvaluationRow`'s already-large Sift modal. `EducationLevel`'s 9-value ladder is a judgment call (CSC PDS-adjacent categories) that won't perfectly fit every real transcript (e.g. a two-year associate's degree sits ambiguously between `VOCATIONAL` and `COLLEGE_LEVEL`).

**Future impact:** If `WorkExperience` is ever revived as real per-entry data (e.g. a future audit trail requirement), `minYearsExperience`'s comparison could switch from `Applicant.yearsOfExperience` to a computed sum of `WorkExperience` date ranges without changing `JobPosting`'s shape at all - only `qualificationMatch.ts`'s experience calculation would move. If the hint ever needs to become a real gate (e.g. blocking Sifting outright below a minimum), that's a `ApplicationsService.sift()` precondition change, not a schema change - the data this decision adds is already sufficient.

## 2026-08-19 — Compliance to Requirements: manual per-application add, not a "re-snapshot" or "sync to catalog" action; review no longer requires a proof document

**Context:** Client report: "I already applied and the application is hanging because there's no compliance in the list" - `moveToCompliance()` (see the 2026-08-11 entry above) only ever snapshots the *currently*-active `ComplianceRequirement` catalog at the moment an application enters `FOR_COMPLIANCE`. In this environment the catalog was empty (or had nothing active) at that moment, so the applicant's checklist got zero `ApplicationComplianceItem` rows - and `EvaluationRow`'s `allComplianceVerified` (`complianceItems.length > 0 && every item VERIFIED`) can then never become true, permanently blocking "Schedule Oath-Taking" with no in-app recovery path. The client's own framing - "the admin should select a compliance to pass instead of automatic" - pointed at giving the admin manual control over one application's checklist rather than only ever trusting the automatic snapshot.

Two narrower alternatives were considered and rejected: (a) re-running the snapshot for a `FOR_COMPLIANCE` application whenever the catalog changes, which would silently add/remove items on applicants already mid-review and contradicts the existing "not a live join" design this module was explicitly built around (see the 2026-08-11 entry); (b) letting `scheduleOathTaking()` proceed when `complianceItems.length === 0` (treating "no requirements" as vacuously satisfied), which would make an admin's inaction (never adding a requirement, or a catalog that's simply empty by mistake) look identical to genuine "no compliance requirements apply here" and lose the visibility an admin gets by seeing an empty checklist and having to explicitly act on it.

**Decision:** Two additive changes, both admin-only and scoped to one application at a time:
1. **New `POST /api/applications/:id/compliance-items` (`ApplicationsService.addComplianceItem()`)** lets an admin attach one more requirement from the catalog directly to a single `FOR_COMPLIANCE` application's checklist - same `PENDING`-row shape the automatic snapshot creates, same unique `(applicationId, requirementId)` constraint preventing duplicates (409 if already present). `ComplianceReviewModal` gained an "Add a requirement to this applicant's checklist" `<select>` (sourced from the existing `GET /compliance-requirements`, filtered to what's not already listed) above the table.
2. **`reviewComplianceItem()` no longer requires a `COMPLIANCE_PROOF` document to exist before verifying/rejecting.** A manually-added item starts with no proof by construction, so gating review on proof would have only moved the "stuck" problem rather than solved it - the admin now marks Verified/Rejected on their own judgment, the same discretion `sift()`'s pass/fail call already carries elsewhere in this same pipeline. This applies uniformly to both automatically-snapshotted and manually-added items, not just the latter, since a proof-optional review is a defensible admin capability either way and a split behavior (proof required for snapshot items, optional for manual ones) would be a confusing, hard-to-explain distinction.

**Pros:** Directly unblocks the reported case with no data migration and no schema change (the unique constraint and `PENDING` default already existed for exactly this row shape); an admin still has to take an explicit, audit-logged (`APPLICATION_COMPLIANCE_ITEM_ADDED`) action per application rather than the system silently working around an empty catalog; the "not a live join" snapshot design and its documented limitation (a requirement added to the catalog afterward doesn't retroactively appear) are unchanged - this only adds a manual path alongside it, not a replacement mechanism.

**Cons:** Reviewing without a proof document is a real loosening of the original design ("reviewing requires that document to already exist," per the schema's own prior comment) - an admin could now mark any requirement Verified with zero evidence on file, for both manually-added and originally-snapshotted items alike. This trusts admin judgment the same way `sift()` already does, but it's worth flagging as a deliberate broadening, not an incidental one. A completely empty Compliance Requirements catalog (no rows at all, not just none active) still leaves the "Add a requirement" picker with nothing to select - an admin hitting that case must first add at least one requirement via the existing Compliance Requirements admin page before they can unblock any applicant.

**Future impact:** If proof-optional review turns out too permissive in practice, it could be scoped back to "optional only for manually-added items" by checking `item.createdAt` against `application.complianceRequestedAt`, without touching the `addComplianceItem()` endpoint itself. If admins routinely need to add the *same* requirement across many already-in-progress applicants at once (as opposed to one at a time here), that would justify a bulk variant - not needed yet, since the reported case was a single stuck applicant.

## 2026-08-19 — Compliance review's proof-optional loosening reinstated as proof-required-for-Softcopy, split by a new per-item submissionType (Softcopy/Hardcopy)

**Context:** Same-day follow-up to the entry directly above. That change made `reviewComplianceItem()` accept `VERIFIED` with zero evidence on file for *every* item, flagged in its own "Cons" as "a real loosening of the original design" and its own "Future impact" as something to reconsider if it proved too permissive. The client reconsidered it immediately: "The compliance should only be verified once the Applicant upload the required document needed and has been approved by the Admin. Add option for compliance hardcopy(physical) or softcopy(online)." This is two asks in one - reinstate the proof requirement, but recognize that not every requirement can have a proof requirement, because some are legitimately submitted as a physical document outside the system (e.g. an original ID shown in person) with nothing to upload.

**Decision:** A new `submissionType` column on `ApplicationComplianceItem` (`ComplianceSubmissionType`: `SOFTCOPY` default, `HARDCOPY`), set per item by an admin (`ApplicationsService.setComplianceItemSubmissionType()`, `PATCH .../compliance-items/:itemId/submission-type`) rather than by the applicant - a hardcopy submission by definition never reaches the system for an applicant to declare, so there's no applicant-facing control for this. `reviewComplianceItem()`'s `VERIFIED` gate is reinstated, but scoped to `SOFTCOPY` items only: 400 unless a `COMPLIANCE_PROOF` document already exists. A `HARDCOPY` item skips that check entirely - there's no online counterpart to require, so the admin's own `VERIFIED` action is the record that they physically received and approved it. `REJECTED` stays unconditional either way (an admin can reject a requirement that was never submitted at all, e.g. past deadline). `addComplianceItem()` gained an optional `submissionType` so an admin who already knows a requirement will be hardcopy can set it at add time instead of a separate follow-up call. Existing rows (including ones already `VERIFIED` under the brief proof-optional window) default to `SOFTCOPY` via the schema default and are unaffected retroactively - the gate only applies at the moment of a new `VERIFIED` transition, not to already-settled rows.

**Pros:** Closes the exact loosening flagged as a risk in the previous entry, restoring "an admin's approval alone is not enough - the applicant's submission must exist first" for the normal online path, while still solving the original stuck-applicant problem for the case that motivated it: a hardcopy-declared item never needed an online submission to begin with, so it isn't blocked by a proof check that could never be satisfied. The choice being an explicit per-item admin action (not a free-text field, not client-set) keeps it auditable (`APPLICATION_COMPLIANCE_ITEM_SUBMISSION_TYPE_SET`) and prevents an applicant from self-declaring "hardcopy" to route around the online-proof gate.

**Cons:** An admin can still mark a `HARDCOPY` item `VERIFIED` with nothing else in the system testifying it happened - same trust-the-admin trade-off `sift()` already carries, just now scoped instead of blanket. Flipping an item's `submissionType` is unrestricted by status/timing (an admin could flip a `SOFTCOPY` item with an existing proof to `HARDCOPY` and back with no audit distinction beyond the log line) - not treated as a risk here since the same admin already has unilateral Verify/Reject authority regardless.

**Future impact:** If hardcopy submissions ever need their own evidence trail (e.g. a "received by / date" note distinct from `remarks`), that's an additive field on `ApplicationComplianceItem`, not a redesign - `submissionType` already carries the branch point. If an applicant-facing "how will you submit this" declaration is ever wanted (as a hint, not authority), it would need to stay explicitly advisory - the admin's `submissionType` setting must remain what `reviewComplianceItem()` actually checks.

## 2026-08-19 — Evaluation Criteria renamed to Categories/Criteria, with scoring moved from the category to the individual criterion/question

**Context:** Client request: "For Evaluation Criteria lets rename it to categories and the questions to criteria/question, each criteria/question should have point on its own and will be average from the scores of panels lets use average of panels. Ex. If the Category is 25% of the overall evaluation thats our max point = average of all the point of panel so even there's one missing panel score we can still have the score." Under the old model, `EvaluationCriterion` (e.g. "Communication Skills") was the *only* scored unit - a panelist gave it one number up to its `maxScore`, and its `EvaluationCriterionQuestion[]` were purely descriptive guiding text shown alongside that single score box, carrying no point value of their own. The client wants the reverse: the parent becomes a non-scored grouping ("Category"), and each of its child items ("Criteria/Questions") is individually scored with its own point value, with the category's total being the sum of those.

The "average even with a missing panel score" half of the request was already true at the *overall total* level - `PanelEvaluationsService.tabulation()`'s `average = submitted > 0 ? sum / submitted : null` already divides by however many panelists actually submitted, not a fixed assigned-count denominator - so nothing needed to change there. What was missing was the granularity: there was no per-criterion averaging concept to preserve in the first place, since only the category was ever scored.

**Decision:** Two-level schema: `Category` (renamed from `EvaluationCriterion`; `name`, `sortOrder`, `isActive` - **no stored `maxScore`**) has many `Criterion` (renamed from `EvaluationCriterionQuestion`; gains `maxScore` and `isActive`, `text` renamed `name`). A category's point value is the *sum of its own active criteria's `maxScore`*, computed at read time (`CategoriesRepository`), never stored - so it can't drift out of sync with its own children the way a manually-kept-in-sync duplicate number could. `PanelScore.criterionId` is repointed from the old category-level id to the new leaf `Criterion` id - a panelist now scores every individual criterion/question, never the category as one number; the category's reported value is always the sum of its criteria's scores, per panelist, then averaged across panelists (exactly the "average of all the point of panel" the client described, now meaningful at the sub-category level too, not just the grand total).

Because `Criterion` rows can now carry real historical `PanelScore`s (the old `EvaluationCriterionQuestion` never could - only the category above it was ever referenced by a score), the old "always fully replace on save" convention that DTO used (delete every question, recreate from the submitted array) was no longer safe: doing that on an already-scored category would silently cascade-delete a panelist's marks. `CategoriesRepository.update()` instead diffs the incoming `criteria` array against what's on file - an entry with an `id` updates in place, one without creates fresh, and anything on file but missing from the array is removed *unless* it already has a recorded score, in which case the whole update 409s (mirroring the "deactivate instead" delete-guard shape already used for `Category`/`ComplianceRequirement`).

**Data migration:** One real scored record existed in this environment ("Extemporanious Speaking", `maxScore: 25`, 3 placeholder guiding-text questions, one submitted `PanelScore` of 25). Since the old model never captured a per-question point breakdown, there was no honest way to decompose that lump score after the fact - fabricating a split would be worse than not attempting one. The migration instead: for any category with existing `PanelScore`s, collapses it to one fallback `Criterion` (name = the category's own name, `maxScore` = the category's old `maxScore`) and repoints the existing score(s) to it, discarding the old placeholder question text for that category only; for a category with guiding questions but no scores yet, splits the old `maxScore` evenly across them as a real starting point value (remainder to the last, so the sum matches exactly) - a genuine default the admin can then rebalance via the normal edit flow, not a placeholder. Applied as a hand-written SQL migration (`RENAME TABLE`/`CHANGE COLUMN`, not Prisma's default destructive `DROP TABLE` + `CREATE TABLE` diff) preceded by a one-off data-fixup script establishing every `criteria` row's `maxScore` before the `NOT NULL` constraint and the new `panel_scores.criterionId → criteria.id` FK were added, so nothing was lost or orphaned. Verified after: `Extemporanious Speaking` category shows `maxScore: 25`, its one criterion (same name) shows `maxScore: 25`, and the original `PanelScore` row (score 25) is intact, now pointing at the criterion instead of the category.

**Module/route rename:** `backend/src/modules/evaluation-criteria` → `categories`; `/api/evaluation-criteria` → `/api/categories`; `EvaluationCriteriaService`/`Repository`/`Controller` → `Categories*`; audit actions `CRITERION_CREATED/UPDATED/DELETED` → `CATEGORY_CREATED/UPDATED/DELETED`; frontend `EvaluationCriteriaPage` (`/admin/criteria`) → `CategoriesPage` (`/admin/categories`), sidebar label "Evaluation Criteria" → "Categories". `panel-evaluations` (module, route, and `PanelEvaluation`/`PanelScore` models) keeps its name - it's the scoring action itself, not the rubric being scored against, so the rename didn't touch it; `PanelEvaluationsService` now depends on `CategoriesRepository` instead of the old `EvaluationCriteriaRepository`.

**Pros:** Matches the client's requested vocabulary exactly (Category/Criteria-Questions) instead of a partial rename that would leave "criteria" meaning two different things in the same codebase (it already did, subtly - `PanelScore.criterionId` pointed at the category, not a "criterion" in the everyday sense; this rename actually *fixes* that latent naming collision as a side effect, since `criterionId` now correctly refers to a `Criterion`). Per-criterion scoring is strictly more granular than the old per-category model without losing anything - the category subtotal `applicantScoresOverview()` reports is still there, just now derived from real per-line-item scores instead of being the only number that ever existed. The diff-based criteria update closes a real data-safety gap the old model didn't have to worry about (nothing was ever scored at the question level before).

**Cons:** A genuine breaking schema change requiring a hand-migration rather than a routine `prisma migrate dev`, with unavoidable data loss for the one previously-existing record's *descriptive text* (not its score, which was preserved exactly) - acceptable here only because it was placeholder test content ("Test"/"TEst"), not real hiring data; this tradeoff would need to be revisited (e.g. requiring manual admin sign-off per category) if this migration pattern were ever needed against a production dataset with real per-question guidance text worth keeping. The rubric configuration UI is now two levels of nested form state (`CategoriesPage`'s criteria-rows-within-a-category-modal) instead of a flat list, a real increase in UI complexity for the admin configuring it.

**Future impact:** If a category is ever deleted or deactivated with criteria that still reference scores, the existing `countScores()`/delete-guard pattern (already scoped to sum across a category's criteria, not just the category row itself) continues to be the right place to extend from. If per-criterion weighting beyond a flat point value is ever requested (e.g. a criterion counting double), that's an additive multiplier field on `Criterion`, not a further restructuring - the two-level shape already supports it.

## 2026-08-19 — Category.weightPercent: a category's contribution to the overall evaluation is fixed by an admin-set percentage, normalized against its raw criteria total - not the raw total itself

**Context:** Same-day follow-up to the Category/Criterion rework directly above. That entry gave every category a *derived* `maxScore` - literally the sum of its own criteria's point values, with no independent number of its own. The client's very next request exposed why that's not enough on its own: "If I clicked Category I should have an input how much percent is this category for the overall evaluation. Example I put 25% in Battery test even I have many criteria max point should still be 25% of the overall evaluation." Under the derived-only model, a category's actual weight in the overall score was accidentally coupled to how it happened to be broken down internally - a category split into 10 criteria worth 10 points each (100 raw) would silently outweigh one with a single 10-point criterion, even if the admin intended both to count equally. That's specifically the bug the client is describing.

**Decision:** `Category` gains a real, admin-set, required column: `weightPercent` (`Int`, 1-100) - its authoritative share of the overall evaluation, entered directly on the Add/Edit Category form ("Weight (% of overall evaluation)"). It is **not derived and not validated against the criteria list** - an admin can set a category to 25% whether it ends up with 1 criterion or 20, worth 10 raw points or 1000. The existing derived `maxScore` (sum of active criteria's own `maxScore`) stays exactly as it was in the prior entry, but its role changes: it's now purely the **raw grading scale** a panelist's score inputs are bounded by, not a stand-in for the category's real weight. A panelist's raw subtotal for a category (sum of their scores across just that category's criteria) is normalized against this raw max and scaled to `weightPercent` before it counts toward anything reported - `weightedCategoryScore(rawSubtotal, rawMax, weightPercent) = rawMax > 0 ? (rawSubtotal / rawMax) * weightPercent : 0`. An application's overall score, for CompAss tabulation and the cross-posting Applicant Scores view alike, becomes the sum of every category's weighted contribution - not a flat sum of raw `PanelScore` rows the way it briefly was in the prior entry.

The app does not enforce that active categories' weights sum to 100 - `CategoriesPage` shows a live, non-blocking hint ("Total weight across active categories: N% — usually expected to add up to 100%") both in the list and inside the add/edit form (a "projected total" calculated from every *other* active category plus whatever's currently typed), the same soft-check philosophy already used for the structured-qualification-minimums feature (a hint, never a hard gate) - see the entry above it in this file.

**Migration:** Additive column, `20260819130950_add_category_weight_percent` (add-nullable → backfill → enforce-NOT-NULL, the same three-step sequence used by earlier additive migrations like `description`/`monthlySalary`). The two categories that existed in this environment at the time ("Extemporanious Speaking" and a client-created "Battery Test", 4 criteria summing to 40 raw points) were both backfilled to `100` - the only defensible default with zero other information, since there was no prior weight concept to infer from. Verified live immediately after: both categories showed `weightPercent: 100` (and the new "Total weight: 200%" hint correctly flagged the mismatch); edited them to `75`/`25` respectively through the actual admin UI, confirmed the hint cleared to a clean "100%", and confirmed via `GET /panel-evaluations/applicant-scores` and the panel-facing rubric reference panel that both now report `weightPercent` (not the old raw `maxScore`) as each category's ceiling.

**Pros:** Directly closes the exact bug the client described, with a real, unit-tested (`weightedCategoryScore`/`weightedTotalScore`, `panel-evaluations.service.test.ts`) normalization instead of an implicit assumption that raw totals happen to reflect intended weight. Keeps the "raw grading scale" (how finely a panelist can differentiate within a category) and "real weight" (how much the category matters overall) as two genuinely separate admin decisions, which is what CSC-style weighted rubrics actually need - an admin can go from 1 broad criterion to 10 granular ones without ever touching the category's weight. The soft-check "should add to 100%" hint catches the obvious misconfiguration (as it did immediately in this environment) without blocking an admin mid-edit the way a hard validation would.

**Cons:** Two numbers now describe every category (`weightPercent` the real weight, `maxScore` the raw scale) instead of one, which is inherently more for an admin to hold in their head - the UI leans hard on the field-hint copy and the live "Raw total: … / actual weight: …%" line to keep them from being confused for each other. `weightedCategoryScore`'s division makes every reported number a float in the general case (e.g. `12.5`), not the clean integers the old raw-sum model produced - already handled (`.toFixed(1)` display, no rounding in the stored/computed values), but worth flagging as a step away from whole-number scores. Nothing stops weights from never summing to 100 beyond the soft hint - an admin who ignores it gets an "overall" score that isn't really out of 100, silently.

**Future impact:** If weights ever need to be *enforced* to sum to 100 (a hard gate instead of a hint), that's a single additional check in `CategoriesService.create()`/`update()` summing all active categories' `weightPercent` - the data model already supports it without another migration. If a category's weight is ever allowed to vary per job posting (categories are still global/shared across postings - see the existing "not per-posting" Known Limitation), `weightPercent` would need to move onto a per-posting join rather than staying a flat column on `Category` - a larger change than this one, not needed yet.

**Reference:** [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation)'s "Weighted scoring", [database.md § categories / criteria](./database.md#categories--criteria), [api.md § Categories](./api.md#categories--apicategories-was-apievaluation-criteria-renamed-2026-08-19---see-docsdecisionsmd) and its "Weighted scoring" subsection, `backend/prisma/schema.prisma`, `backend/prisma/migrations/20260819130950_add_category_weight_percent/`, `backend/src/modules/categories/`, `backend/src/modules/panel-evaluations/panel-evaluations.service.ts` (+ `.test.ts`), `frontend/src/features/admin/pages/CategoriesPage.tsx`, `frontend/src/shared/utils/weightedScore.ts`.

## 2026-08-19 — Dashboard "Applications by status" switched to a pie chart, surfacing (and fixing) a hand-maintained status list that had silently fallen out of sync with the schema

**Context:** Client request: "In Dashboard the Application Status can we make it a pie chart instead." Implementing it meant reading real application data through the chart for the first time in this session (the bar-chart version had been showing all-zero/near-zero counts, so its rendering hadn't been scrutinized) - and the new chart immediately showed something wrong: a real `HIRED` application in this environment (confirmed directly in the database) reported as `applications.total: 0` from `GET /api/dashboard/summary`, and didn't appear as a slice at all.

Root cause: `dashboard.dto.ts`'s `APPLICATION_STATUSES` constant - the hand-written list `DashboardService.tally()` uses to fill every status with `0` before overlaying `groupBy`'s real counts - had never been updated when the Compliance to Requirements/Oath-Taking phases (2026-08-11) added `FOR_COMPLIANCE`/`NOT_SELECTED`/`DISQUALIFIED`/`FOR_OATH_TAKING`/`HIRED` to the `ApplicationStatus` enum. `tally()`'s `if (key in result) result[key] = ...` silently no-ops for any status not in that hand-written list, so every application that had reached one of those 5 statuses was invisibly excluded from both `applications.total` and `byStatus` - not just miscounted, *absent*, with no error or warning anywhere. `docs/api.md`'s own response-shape example had already listed `FOR_COMPLIANCE`/`FOR_OATH_TAKING`/`HIRED` (though not `NOT_SELECTED`/`DISQUALIFIED`) - the documentation described the intended/assumed behavior; the code had simply never been updated to match when those statuses were added.

**Decision:** Two changes. (1) `APPLICATION_STATUSES` now lists all 11 `ApplicationStatus` values, in schema-enum order. (2) A new `dashboard.dto.test.ts` compares `APPLICATION_STATUSES`/`JOB_POSTING_STATUSES`/`USER_ROLES` against `Object.values()` of the corresponding Prisma-generated runtime enum objects (`ApplicationStatus`/`JobPostingStatus`/`Role`, imported as values not just types) - the same class of drift now fails a test immediately instead of silently under-reporting, since these three lists have no way to be derived automatically from the schema at compile time (Prisma doesn't export a "list every enum value" helper, only the enum object itself) and are otherwise exactly this kind of hand-copy that erodes over time. For the chart itself: `PieChart` (`DashboardPage.tsx`) only renders a slice per status with at least one application - the dataviz skill's "more than ~7 classes -> table, not more colors" guidance argues against a full always-11-slice pie, and since most statuses are empty at any given moment in practice, filtering to non-zero slices is a data-driven way to stay well under that ceiling rather than an arbitrary cap. Slice percentages are direct-labeled only past an 8%-share threshold (avoids label collisions when several thin slices coexist); a legend (swatch, label, exact count) is always shown below the chart, serving both as the required ≥2-series identity source and as an exact-numbers fallback. Colors are the same status hues already used for `.badge`s and the existing bar chart - reapplication of an established token set, not a new palette decision, so the palette validator wasn't re-run.

**Pros:** The dashboard's headline "Applications" stat tile and every status breakdown are now actually correct - this was a real, previously-invisible data integrity gap on the primary admin landing page. The sync test converts "someone adds a new `ApplicationStatus` value and forgets this list" from a silent, hard-to-notice production bug into an immediate, obvious test failure. The pie chart's non-zero-only filtering means it degrades gracefully as the pipeline fills out over a hiring cycle, rather than needing revisiting as more statuses accumulate real data.

**Cons:** `JOB_POSTING_STATUSES`/`USER_ROLES` weren't actually broken (both enums are small and haven't changed since dashboard was built) - the sync test for those two is preventative rather than fixing a live bug, slightly broader scope than the minimum fix. A pie chart is generally harder to compare precisely than a bar chart for more than a couple of slices (the dataviz skill's own default job-to-form mapping recommends a stacked bar for part-to-whole, not a pie) - accepted here because it's what the client explicitly asked for, and the legend's exact counts cover the "precise comparison" need a pie alone can't.

**Future impact:** If a 12th `ApplicationStatus` (or a new `JobPostingStatus`/`Role`) is ever added, `dashboard.dto.test.ts` will fail immediately until `dashboard.dto.ts`'s corresponding list is updated - this is the intended trip-wire, not a bug to fix later. If the "Applications by status" chart ever needs to show every status regardless of count (e.g. an admin explicitly wants to confirm which statuses are empty), that's a prop toggle on `PieChart`, not a redesign.

Building bidirectional membership editing now would be speculative scope beyond what was asked; `PATCH /api/applicant-groups/:id` only accepts `name`/`description`. If an admin needs to fix a group's roster today, the workaround is delete-and-recreate (no usage guard blocks deleting a group, unlike Categories/Compliance Requirements, specifically so this workaround stays cheap).
3. **A group requires ≥2 applicants** (`applicationIds` min 2, both in the Zod schema and via the "Group" button staying disabled below 2 selections) - a "group" of one applicant isn't a group for this activity's purpose, so the degenerate case is rejected at the boundary rather than silently allowed.

Everything else intentionally mirrors `PanelAssignmentsPage`/`PanelAssignmentsService` as closely as possible per the client's explicit "same setup" instruction: the same search/job-posting/publication filters, the same header "select all" + per-row checkbox + bulk action bar mechanics, a "Group(s)" column playing the same role "Assigned Panel" does, and the same audit-log-on-every-write convention (`APPLICANT_GROUP_CREATED/UPDATED/DELETED`).

**Migration note:** The new tables (`applicant_groups`, `applicant_group_members`) are purely additive, but `prisma migrate dev` couldn't generate the migration automatically - its shadow-database diff replays every prior migration from scratch, and the hand-written `20260819123048_rename_criteria_to_categories` migration (from earlier the same day) isn't idempotent on a fresh empty database, so the replay fails with a duplicate-key error even though the real database applied it fine originally. Worked around the same way the project already handles this class of problem: wrote `20260819230413_add_applicant_groups/migration.sql` by hand (matching exactly what `migrate dev` would have generated for this diff), applied it directly via `prisma db execute`, then `prisma migrate resolve --applied` to reconcile Prisma's migration history. Verified end-to-end afterward: created a temporary second applicant/application via a throwaway script, exercised create/list/update/delete through both the raw API and the live `GroupsPage` UI (including the audit trail), then deleted all of the temporary data and scratch scripts.

**Pros:** Ships exactly the workflow described without inventing scope (no speculative membership-editing UI, no invented same-posting constraint). Reusing `PanelAssignmentsPage`'s proven selection mechanics wholesale means the new page inherits its accessibility/pagination/filter behavior for free rather than re-deriving it. The ≥2-member and delete-no-guard choices keep the "create it, redo it if wrong" flow cheap, appropriate for what's likely an infrequent, one-time-per-batch admin action rather than an ongoing roster.

**Cons:** No way to fix a single wrong member without recreating the whole group (name, description, and all) - acceptable for now given the client's literal description of the flow, but a real limitation if groups turn out to need frequent small corrections in practice. No `jobPostingId` means there's no automatic "only see applicants for this posting" scoping the way Interview Panel gets implicitly from being posting-keyed - an admin grouping applicants for one posting's exercise has to filter manually via the job-posting dropdown instead of it being structural.

**Future impact:** If membership editing is requested later, `ApplicantGroupsRepository`/`Service` already has the shape to support it cleanly (`UpdateGroupInput` would just gain an `applicationIds` diff step mirroring `CategoriesRepository.replaceCriteria()`'s add/remove-by-diff pattern) - not a redesign, just filling in a deliberately-deferred piece.

## 2026-08-20 — Fixed `20260819123048_rename_criteria_to_categories`'s root cause instead of continuing to work around it

**Context:** This migration was known to fail when replayed against a fresh empty database (see the 2026-08-19 "New 'Group' admin page" and same-day member-editing entries above, and `docs/project-memory.md`'s prior note) - "Duplicate foreign key constraint name 'panel_scores_criterionId_fkey'" on its final `ADD CONSTRAINT`. Previously worked around per-affected-migration (hand-write the new one, apply via `prisma db execute` + `prisma migrate resolve --applied`) rather than fixed, because the actual local dev database had already had this migration applied via an undocumented manual pre-migration script that dropped the old FK first; that drop was never itself a migration step, so it only ever happened on that one database. First real deployment attempt (the AWS EC2 free-tier test in the entry above) replayed the full migration history against a genuinely empty database and hit this directly via `prisma migrate deploy` - not a shadow-database quirk, a real blocker for anyone standing up a fresh environment from this repo.

**Decision:** Fixed the migration file itself: added `ALTER TABLE panel_scores DROP FOREIGN KEY panel_scores_criterionId_fkey;` immediately before the `ADD CONSTRAINT` that was colliding with it - unconditional, no `IF EXISTS` guard, since the FK will always exist at this point in a fresh replay (created by an earlier migration in the sequence).

**Pros:** Fixes the actual bug for every future fresh deployment (and `prisma migrate dev`'s shadow-database replay, unblocking that going forward too) instead of leaving another workaround for the next person to rediscover. Caught a second, more interesting bug along the way: the first attempt at this fix (`DROP FOREIGN KEY IF EXISTS`) was itself wrong - MySQL 8 on the real EC2 target rejected it as a syntax error, even though it had silently worked against local dev's MariaDB. Switched to the plain unconditional form (no engine-version-dependent syntax at all), re-verified by dropping a throwaway local database and replaying all 32 migrations against it from scratch. A lesson in its own right: a migration only ever tested against local dev's MariaDB had already fooled this exact fix once - the real target (MySQL 8 on the EC2 instance) is the only thing that can fully confirm it.

**Cons:** Edits a migration file that's already `_prisma_migrations`-recorded as applied on the existing local dev database - in principle this risks a checksum mismatch there. Verified in practice this doesn't happen: `prisma migrate deploy`/`migrate status` against the existing local database both still report clean/up-to-date after the edit (empirically confirmed, not just assumed) - already-applied migrations aren't re-executed, so the corrected SQL only ever actually runs on a fresh target going forward.

**Future impact:** Any future migration file with a similar "this assumes a manual step that happened out-of-band" comment (grep for "pre-migration script" in `backend/prisma/migrations/`) should get the same treatment - fix it to be correct from empty, rather than adding another one-off resolve workaround.

**Reference:** `backend/prisma/migrations/20260819123048_rename_criteria_to_categories/migration.sql`, `deploy/aws-ec2/README.md`.

The appended-at-the-end placement means Group Dynamics Evaluation reads after History of Logs rather than near Interview Panel where it belongs pipeline-wise - a deliberate readability/safety tradeoff, not an oversight. No automated test covers this file (can't meaningfully unit-test a Word document); verification was manual: zip integrity check, balanced-tag sanity check on the XML, and confirming the frontend serves the exact rebuilt bytes.

**Future impact:** The next manual update should follow the same pattern (extract → verified string replacement → re-zip with `System.IO.Compression`, never `Compress-Archive`) unless a proper docx-authoring toolchain (e.g. `pandoc`, or the `docx` npm package) gets added to the project - worth doing if manual updates become frequent enough that hand-editing XML stops being the faster path.

## 2026-08-21 — Multi-posting panel score inheritance: a self-referential pointer, not copied score rows

**Context:** Client requirement: "Applicants can Apply Multiple Job posting as long as Applicant is not hired and the Panel points will automatically counted in all the Applicants applied jobs so that the applicant will not be evaluated in each job." An applicant scored once needed that score to count toward every posting they'd applied to, without a second interview. Two designs were considered: (a) physically copy the scored `PanelEvaluation`/`PanelScore` rows onto the applicant's other applications, one set per sibling posting; (b) add a nullable self-referential pointer (`Application.scoreSourceApplicationId`) on the sibling applications, and resolve through it at read time wherever panel evaluations are consumed.

**Decision:** (b) - the pointer. `PanelAssignment` is scoped per-posting (`@@unique([jobPostingId, panelUserId])`), so a sibling posting's actual assigned panel never scored this applicant; copying rows under a borrowed `panelUserId` would misattribute authorship in audit logs, the panelist's own `ScoreSummaryPanel` history, and anywhere else "who scored this" is shown or relied on. `Category`/`Criterion` (the rubric) are global, not per-posting (see `docs/project-memory.md`'s Known Limitations), so a score computed once against the one shared rubric is numerically valid everywhere - there's no rubric-specific reason it couldn't be reused, only an attribution reason it shouldn't be duplicated. `scoreSourceApplicationId` always points directly at a canonical (never-inheriting) application, never chained through another inheriting one, enforced at both write sites (`ApplicationsRepository.resolveScoreSourceForApplicant()` at apply-time, `PanelEvaluationsRepository.linkSiblingScoreSources()` at scoring-time).

**Pros:** One source of truth per applicant's actual interview performance - no risk of two "copies" of the same score drifting apart if a panelist later re-scores (an inheriting application always reflects the canonical one's current data, since it holds no data of its own). No misattribution: `panel_evaluations.panelUserId`/`applicationId` always reflect who actually scored whom, for whichever posting they were actually assigned to. Resolution is a single batched query (`PanelEvaluationsRepository.resolveInherited()`) regardless of how many applications in a result set are inheriting - no N+1, and the two pure functions doing the actual list-merge (`collectScoreSourceIds`/`mergeInheritedEvaluations`) are unit-tested without a database.

**Cons:** Every reader of "this application's panel evaluations" has to know to resolve the pointer - three call sites today (`findApplicationsForTabulation`, `findApplicationsWithScores`, the `submit()` scoring guard), a fourth (`findQueueForPanelUser`) has to know to exclude inheriting applications outright. A future new consumer of panel evaluation data that forgets this resolution step would silently show an inheriting application as unscored rather than erroring - no compile-time enforcement ties a new query to this rule, it's a convention to remember, same risk class as any other cross-cutting read-time transform in this codebase (e.g. weighted-scoring normalization).

**Future impact:** Any new place that reads `Application.panelEvaluations` (directly, not through the existing repository methods) needs the same resolution or exclusion logic applied. Phase 2 (hierarchy-based hire recommendation, auto-close-on-hire - see `docs/project-memory.md`'s Future Work) builds on top of this without touching the inheritance mechanism itself, since it only reads each application's already-resolved `status`/`jobPosting.salaryGrade`.

**Reference:** `backend/prisma/migrations/20260821000001_add_application_score_inheritance/`, `backend/src/modules/applications/applications.repository.ts`, `backend/src/modules/panel-evaluations/panel-evaluations.repository.ts`, [architecture.md § Multi-posting applications & panel score inheritance](./architecture.md#multi-posting-applications--panel-score-inheritance-phase-1).

## 2026-08-21 — Hierarchy-based hiring stays a recommendation, never an automatic status change

**Context:** Client requirement (Phase 2 of the multi-posting feature above): "if applicant passed in all the Job Posting he applied he will be hired in the Higher position or Higher SG level." Two ways to implement "will be hired": (a) the system automatically sets the highest-SG application to `HIRED` the instant an applicant reaches `FOR_OATH_TAKING` on 2+ postings, no human action; (b) the system computes and surfaces the recommendation, but an admin still has to click Mark Hired themselves, same as every other terminal action in this pipeline.

**Decision:** (b) - confirmed explicitly with the user before implementation (via `AskUserQuestion`, recommended option accepted). Every other status transition in this system - Sifting's pass/fail, moving to Compliance, scheduling Oath-Taking, and Mark Hired itself - is already a deliberate, one-shot admin action with no automatic equivalent anywhere in the codebase. `HIRED` in particular is about as consequential and hard-to-reverse a status as this system has (it triggers a "you're hired" email and, as of this same feature, auto-closes every other of the applicant's open applications) - a silent, unattended status flip the moment a numeric comparison resolves felt like the wrong place to introduce the app's first fully-automatic terminal transition, especially given the comparison is a *recommendation* in the domain sense ("higher position," not a hard rule with no exceptions an admin might reasonably override).

**Pros:** Consistent with the rest of the pipeline's human-in-the-loop design - no new mental model for admins to learn ("this one status is special and can happen without anyone clicking anything"). The admin retains the ability to hire a *non*-recommended posting if there's a real-world reason to (the recommendation banner and the Mark Hired confirmation both surface the caution, but neither blocks the action) - a fully-automatic version would have had to either hard-block that override or silently do the "wrong" thing with no chance to intervene.

**Cons:** Requires an admin to actually notice and act on the recommendation - nothing pages anyone or forces a decision, so an applicant could in principle sit at `FOR_OATH_TAKING` on multiple postings indefinitely if no admin visits `EvaluateApplicantsPage` for them. No reminder/notification mechanism exists in this codebase to page an admin proactively for anything (same gap applies to every other pending admin action, e.g. an unverified compliance item) - not a new gap introduced by this decision.

**Future impact:** If this ever needs to become fully automatic (e.g. a compliance requirement forcing same-day resolution), the recommendation logic (`computeHireRecommendations()`) already computes the correct target - the only change would be calling `markHired()` from a scheduled job or from the recommendation computation itself, rather than from an admin's click. The auto-close-on-hire side effect (`markHired()`'s sibling-closing logic) is unaffected either way - it fires from *any* hire, recommended or not.

**Reference:** `frontend/src/features/admin/utils/hireRecommendation.ts`, `frontend/src/features/admin/components/EvaluationRow.tsx`, `backend/src/modules/applications/applications.service.ts`'s `markHired()`.

## 2026-08-21 — Second undocumented one-off script from the Categories rename surfaces on a fresh AWS deploy: fixed with `ADD COLUMN IF NOT EXISTS`, not another manual patch (superseded same day - see the entry below, `ADD COLUMN IF NOT EXISTS` turned out not to work on this AWS instance's MySQL version)

Tracing it back, the `20260819123048_rename_criteria_to_categories` migration's own comment admits the cause: "Data for `evaluation_criterion_questions` (now `criteria`) was already reshaped by a one-off pre-migration script before this file was written: every row now has a real `maxScore`/`isActive`" - that backfill script added the two columns directly against the one database this migration was originally authored on, but was never itself captured as a committed migration file. IF NOT EXISTS isActive ...`. Verified locally first: local dev already has both columns (from whichever machine the original one-off script targeted), and applying this migration there is a confirmed no-op (`DESCRIBE criteria` before/after identical, including `maxScore`'s `Default: null` and `isActive`'s `Default: '1'` staying untouched) - proving the fix is safe to ship to every environment uniformly rather than needing "run this only on the broken one" instructions.

**Pros:** One migration, checked into git, fixes every current and future fresh deploy permanently - no more relying on a person remembering to run an undocumented script. `IF NOT EXISTS` means it's provably safe on environments that already have the columns (verified, not assumed) and a real fix on ones that don't, so there's no environment-specific branching to get wrong. No data was at risk on the affected database: `categories`/`criteria` were both empty there (every `POST /api/categories` had failed inside the same Prisma-wrapped transaction, so nothing partial ever committed).

**Cons:** `ADD COLUMN IF NOT EXISTS` requires MySQL 8.0.29+/MariaDB 10.0.2+ - only verified against local MariaDB before writing this entry, *not* actually verified against the AWS instance yet at the time. That gap turned out to matter: see the follow-up entry immediately below. Doesn't retroactively fix `_prisma_migrations`' historical inaccuracy for the original rename migration (it still claims to be self-sufficient when it wasn't) - only patches the practical consequence going forward.

**Future impact:** Grep `docs/decisions.md` and migration file comments for "one-off" / "pre-migration script" before authoring any future migration that touches `categories`/`criteria` - there could plausibly be a third undiscovered gap from the same original informal backfill. ## 2026-08-21 — `ADD COLUMN IF NOT EXISTS` isn't portable enough either: switched to `INFORMATION_SCHEMA` + `PREPARE`/`EXECUTE`

**Context:** The fix above shipped with `ALTER TABLE criteria ADD COLUMN IF NOT EXISTS ...`, checked in and deployed to the AWS EC2 instance the same day - and failed there with a MySQL syntax error (1064) near `IF NOT EXISTS`, since that clause requires MySQL 8.0.29+ and this instance runs an older MySQL 8.x. The previous entry's "Cons" section had already flagged this exact version requirement as a risk, but asserted it was "confirmed working... against the AWS instance's real MySQL 8" without having actually deployed and tested it there yet - the claim was written before the verification it described, and turned out to be wrong. The failed `ALTER` also left the migration marked `failed` in AWS's `_prisma_migrations` (Prisma error P3018), which blocks `prisma migrate deploy` from doing anything further until explicitly resolved.

**Decision:** Rewrote the same migration file (`20260821020000_add_criteria_max_score_is_active_columns/migration.sql`, same name/timestamp - it had never successfully applied anywhere except as a no-op on local dev, so editing it in place rather than adding a third migration was safe) to use `INFORMATION_SCHEMA.COLUMNS` existence checks feeding a `PREPARE`/`EXECUTE`/`DEALLOCATE PREPARE` conditional - a MySQL/MariaDB idiom with no meaningful version floor, instead of a specific-version SQL clause. Verified properly this time, against a real standalone MySQL server (XAMPP's `mysql.exe` CLI) rather than only through Prisma's client: `$executeRawUnsafe` turned out to have its own unrelated limitation ("This command is not supported in the prepared statement protocol yet," MySQL error 1295 - `PREPARE`/`EXECUTE` can't run inside another prepared statement, which is what Prisma Client's raw-query path uses under the hood) that made it look broken when it wasn't - a good reminder that "verified via Prisma Client" and "verified via how `prisma migrate deploy`'s own engine actually executes a migration file" aren't the same test. The real CLI test covered both branches: the no-op path against local dev's actual `criteria` table (columns present, `DESCRIBE` identical before/after), and the add path against a disposable throwaway database's `criteria` table built without the two columns (both correctly added with matching types/defaults), the throwaway database dropped immediately after.

**Pros:** No MySQL/MariaDB version assumption baked into the fix this time - matters here specifically since AWS turned out to be older than assumed. Verifying through the actual CLI protocol path instead of Prisma Client's raw-query wrapper caught a second, unrelated tooling gotcha before it could cause a third false "verified" claim.

**Cons:** More verbose than the single-clause version it replaces; the `PREPARE`/`EXECUTE`/`DEALLOCATE PREPARE` pattern is less immediately readable than a plain `ADD COLUMN IF NOT EXISTS` to anyone unfamiliar with the idiom, though the comment block explains why it's there.

**Future impact:** For this project going forward: don't assert a migration is "confirmed working against \<environment\>" unless it was actually run against that exact environment - a claim written before the verification it describes is exactly how the previous entry's incorrect "Cons" line happened. When a version-gated SQL feature (`IF NOT EXISTS` on `ADD COLUMN`/`ADD INDEX`, window functions, CTEs, etc.) seems tempting in a migration, prefer the `INFORMATION_SCHEMA`-conditional pattern from the start unless the target MySQL/MariaDB version is already pinned and known precisely - cheaper than finding out post-deploy. And when verifying raw SQL locally, prefer a real DB client over Prisma's `$executeRawUnsafe` for anything beyond a single simple statement, since Prisma Client's raw-query path has its own protocol-level quirks (like the nested-`PREPARE` limitation found here) that don't reflect how `prisma migrate deploy` itself executes a `migration.sql` file.

## 2026-08-21 — "Duplicate interviews": a repair pass in the queue, not a third event hook

**Context:** Score inheritance (see `docs/architecture.md § Multi-posting applications & panel score inheritance`) links two of an applicant's applications at two moments only: when a *new* application is created after a sibling is already scored, and the instant a sibling *gets* scored. Manual testing surfaced a gap neither moment covers: an applicant who applies to two postings *before either is scored* has two unlinked applications that can each independently reach `FOR_INTERVIEW` and sit in two different panels' queues - nothing stops both panels from scoring the same person. The question was where to close it: a third event hook (e.g. on `scheduleInterview()`, re-checking siblings at the moment an application enters `FOR_INTERVIEW`), or a repair pass at read/write time.

**Decision:** A repair pass, at the two points that actually matter - reading the queue (`findQueueForPanelUser()`) and writing a score (`submit()`) - rather than a third event hook.

**Pros:** An event hook only ever covers the moments someone thought to add it at; a repair pass at the queue-read and the actual write is self-healing against *any* ordering of "applied," "scheduled," and "scored" across two postings, including orderings that don't exist yet (e.g. a future path that moves an application to `FOR_INTERVIEW` some way other than `scheduleInterview()`). It also means the fix lives entirely in `panel-evaluations.repository.ts`/`.service.ts`, the two files that already own this invariant, rather than reaching into `applications.service.ts`'s `scheduleInterview()` to add awareness of a concern that belongs to panel evaluations. The read-side repair is a single batched query (`applicantId IN (...)`), not one query per candidate, so it doesn't turn `findQueueForPanelUser()` into an N+1 liability as the queue grows.

**Cons:** Two checks instead of one (queue-read repair *and* write-time reconciliation) - a caller who only patches one call site could reintroduce half the gap. The read-side repair also does a write (linking a discovered sibling) as a side effect of what looks like a read-only query, which is worth calling out at the call site (and is, in the doc comment on `repairAndExcludeAlreadyScoredElsewhere()`).

**Future impact:** If a third "sibling-awareness" event ever turns out to be needed for a different multi-posting concern (not just score inheritance), reconsider whether an event-hook or repair-pass approach fits better for that concern specifically - this decision applies to this one gap, not a blanket rule that repair-passes always beat event hooks.

**Reference:** `backend/src/modules/panel-evaluations/panel-evaluations.repository.ts` (`repairAndExcludeAlreadyScoredElsewhere()`, `reconcileScoreSource()`, `partitionQueueCandidatesToRepair()`), `backend/src/modules/panel-evaluations/panel-evaluations.service.ts` (`submit()`), `docs/architecture.md § Multi-posting applications & panel score inheritance (Phase 1)`.

## 2026-08-21 — MyApplicationsPage: a reverse-relation hint, not status propagation, for a stale-looking sibling card

**Context:** Also found in manual testing: an applicant who reached `FOR_COMPLIANCE` on one posting but was still `FOR_INTERVIEW` on a sibling posting (same inherited interview score) reported "I'm in Compliance but I only see Evaluation of Applicants details" - reading as a bug even though each card was rendering its own `status` correctly. The real question was whether Compliance/Oath-Taking should propagate across an applicant's siblings the way the interview score does, or whether each posting should keep deciding independently and the UI should just explain that.

**Decision:** Independent per-posting status stays as-is; add a UI hint (`Application.scoreInheritingApplications`, the self-relation's already-declared inverse side) so the applicant can see a sibling exists and how far along it is, instead of auto-advancing siblings' statuses.

**Pros:** Compliance and Oath-Taking are legitimately posting-specific admin decisions (a compliance requirement or an oath-taking slot can differ per position), unlike the interview score which is provably the same rubric applied to the same person regardless of posting - auto-propagating status would be presuming an equivalence that doesn't actually hold. The fix needed no migration (the inverse relation field was already declared alongside the forward one in the schema, just never included in a query) and no new endpoint - just widening `applicationWithPostingInclude` and one more block in `MyApplicationsPage.tsx`.

**Cons:** The applicant still has to look at two cards and mentally reconcile them; the hint reduces confusion but doesn't collapse the two applications into a single unified view, which is what a user description like "I am in Compliance" (singular) implicitly expects. If this keeps causing support confusion, a more direct fix (e.g. a combined "your applications" summary line, or grouping sibling cards visually) may be worth revisiting.

**Future impact:** If a future requirement ever does call for one pipeline status shared across an applicant's siblings (not just the interview score), that's a materially bigger change than this fix - it would need to define what "the" status even means when postings' Compliance/Oath-Taking outcomes could legitimately differ, not just add propagation to the existing per-application `status` field.

## 2026-08-21 — Same-day follow-up: consolidate multi-posting applicants into one row/card, drop the automatic hire recommendation for a manual pick

**Context:** The client used the multi-posting feature shipped earlier today and asked for more: "I should only see one Application status in My Application page and for Admin I should only see one Applicant data, one to evaluate and one to score in Panel... in selecting the position the admin wants for the Applicant other job posting that the applicant applied will be free for others to apply... this is manual from Admin no need to assign the highest SG automatically." This directly supersedes this same file's entry immediately above (`MyApplicationsPage`: a reverse-relation hint, not status propagation) - that entry's cross-reference-hint approach was a reasonable first step but the client wants actual consolidation, not just a pointer between separate cards. It's a natural continuation of "Duplicate interviews" and Phase 2's hire recommendation, both earlier in this file, so read those first for the score-inheritance/auto-close-on-hire mechanics this builds on.

Two structural questions needed resolving: (1) keep the data model as one `Application` row per applicant-posting pair (Option 1) and consolidate only at the view layer, or restructure around a single per-applicant "candidacy" record (Option 2)? (2) once consolidated, should the admin's final position choice still be an automatic recommendation, or fully manual?

**Decision:** Option 1 (view-layer only, no schema change) for the data model; **fully manual** position assignment, with the automatic highest-Salary-Grade recommendation removed rather than kept as a hint alongside the new manual picker.

**Pros:** Option 1 avoided a genuinely large migration - Sifting, PQE, interview scheduling, compliance items, audit logs, and emails are all keyed to one `Application` id today, and a "candidacy" restructure would have touched nearly every module in the RSP pipeline for a request that's really about how existing data is *displayed*, not what's stored. Grouping happens entirely client-side over data every affected page already fetches (`groupByApplicant()`, `combineApplicantRows()`), so most of this shipped as new pure, unit-tested utility functions plus rendering changes - low risk, easy to unit test, and `markHired()` (already a "pick one, close the rest" primitive from this morning's Phase 2 work) needed zero backend changes to serve the new "Assign Position" action. Dropping the recommendation outright (rather than keeping it as a suggestion) matches the client's explicit "no need to assign the highest SG automatically" and avoids a confusing UI where a system suggestion sits next to a manual picker that can freely ignore it - simpler to reason about, and there's now exactly one way to make this decision instead of two.

**Cons:** Per-posting actions (Sifting, PQE, Schedule Interview, Compliance review) could *not* be consolidated the same way - a collapsed applicant row still expands into the old one-row-per-posting view for those, so "one row" is true for overview/scoring/reporting screens but not for every admin action on this applicant. An admin who wants to compare postings by Salary Grade at decision time now has to read the numbers themselves out of the `AssignPositionModal`'s list instead of being handed a suggestion - a small amount of information the old recommendation provided for free is gone, on purpose. If Option 2 (a real candidacy model) is ever pursued in the future, this view-layer grouping work becomes throwaway - the grouping utilities aren't a step toward that migration, they're a substitute for it.

**Future impact:** If DILG later asks for genuinely per-posting-action-collapsing (e.g. "let me Sift someone for all their postings in one click" instead of just viewing them together), that's a materially different, harder problem - qualification standards differ per posting, so a single Sift decision can't mean the same thing across all of them without redefining what "Sift" even means for a multi-posting applicant. Revisit as a new decision if that's ever actually requested, rather than assuming this consolidation work generalizes to it.

## 2026-08-21 — Same-day reversal: My Interviews gets grouped too, and `otherApplications` gets tightened

**Context:** The entry immediately above deliberately left the panel's My Interviews queue ungrouped - the reasoning was that each row represented a genuinely distinct not-yet-decided interview, and a duplicate row was a narrow, self-resolving edge case worth a hint, not worth collapsing. The client disagreed after actually using it: "In scoring of applicant with multiple application I can still see multiple scoring. How about 1 only even if the applicant has multiple application just indicate in Job posting what are the other application will this score will go." This is a direct, explicit correction of that specific call - it doesn't touch any other part of the consolidation work.

**Decision:** Dedupe My Interviews the same way as the admin table (`groupByApplicant()`, one row per applicant, earliest-submitted entry chosen), and tighten `otherApplications` from "every other application, any status" to "every other application this score will actually propagate to" (open, unscored, unlinked - exactly `linkSiblingScoreSources()`'s own criteria).

**Pros:** Directly does what was asked, with no new backend endpoint - the existing score-inheritance propagation (`linkSiblingScoreSources()`) already covers every sibling correctly once the panelist scores whichever one row is shown; deduping was purely about not offering a redundant second "Score" action for work that only needs doing once. Tightening `otherApplications` at the same time was necessary, not optional, once it became the *only* visible indication of what a score covers (previously one hint among several visible rows, now the single row's only explanation) - the loose "any status" version could have named an already-terminal sibling that can't actually receive the score, which would have been actively misleading in this new context even though it was harmless as a side-note before.

**Cons:** This is the second reversal in the same session on "how much should the panel/admin experience be grouped" (the admin table went from ungrouped → grouped-by-default earlier the same day; this is the panel queue following the same arc one step later). Worth noticing as a pattern: default to *not* speculatively deciding a screen should stay ungrouped when the same client has already asked for grouping on a related screen in the same conversation - it likely wants the same treatment there too, and it would have been cheaper to ask or apply the same design consistently the first time than to ship, get corrected, and redo it.

**Future impact:** If a future multi-posting UI decision comes up, default toward consistency with the admin table's already-established "one row per applicant" pattern rather than re-litigating whether a given screen's duplicates are "real, distinct work items" case by case.

## 2026-08-21/22 — Evaluate Applicants' actions become group-wide too: bulk-apply Sift despite per-posting QS, Mark Hired stays the exception, compliance-item mirroring deferred

**Context:** Same-day continuation of the "one row per applicant" arc above. Client asked to go further than a shared *view*: "1 data row only, one button for View documents, Sift, PQE score, etc. All application will move at the same time." This surfaced a real tension the earlier consolidation entry (`docs/decisions.md`'s "Design call: default-collapsed grouped rows, not a redesigned per-posting action model") had explicitly used to justify keeping per-posting actions un-flattened: Sifting genuinely depends on that specific posting's own qualification standards (`computeQualificationMatch()` compares against each posting's own `minEducationLevel`/`minYearsExperience`/`minTrainingHours`/`requiredEligibilityTypes`), so a single decision applied to every posting at once could mark an applicant Qualified for a posting whose standards they don't actually meet.

**Decision:** Implement exactly what was asked - one row, one form, applies to the whole group - for Sift, PQE score entry, Schedule Interview, Move to Compliance, Not Selected, Disqualify, and Schedule Oath-Taking. Keep every posting's own QS-match panel visible in the one Sift form so the single decision is still informed, but let the decision itself apply uniformly, on purpose. Mark Hired stays the deliberate exception (routes to the existing "Assign Position" picker for a group at Oath-Taking instead of a bulk action). Compliance-item-level verify/reject inside "Manage Compliance" and the Excel bulk PQE import are *not* extended in this pass - explicitly deferred, not silently forgotten.

**Pros:** Directly delivers what the client asked for, and does so as a client-only refactor (`EvaluationRow.tsx` generalized to take an `applications` array, wrapping every existing single-application endpoint call in a new `applyToGroup()` helper) - no backend changes, no new endpoints, reusing exactly the same DTOs/routes that already existed. `Promise.allSettled` (not `Promise.all`) means one posting's server-side failure is reported honestly rather than silently discarding successes on the other postings. The QS-match panel staying visible per posting means the client - who explicitly asked for uniform application despite knowing (or being told) postings can differ - is making an informed choice, not walking into a surprise.

**Cons:** This is a real behavior change with real risk: an admin can now mark an applicant Qualified for a posting whose QS they don't actually meet, in one click, without a second confirmation specific to that mismatch. The plan mitigates this with visibility (every posting's QS panel shown) but doesn't block or warn on an actual QS failure before allowing the uniform decision - a deliberate choice to trust the admin's judgment given the client's explicit, repeated ask, not an oversight. Compliance-item verification staying per-first-application-only for now means "Manage Compliance" doesn't yet fully honor "all applications move together" at that one stage - an admin still has to open it once per posting if they want every snapshot verified, even though the requirement catalog is identical.

**Future impact:** If compliance-item mirroring is requested next, it's a bounded follow-up (`ComplianceRequirement` is a single global catalog, so every group member's `ApplicationComplianceItem.requirementId` values already match 1:1 - `ComplianceReviewModal` would need `applicationIds: string[]` and to loop its verify/reject/submission-type calls by matching `requirementId`, not a new data model). If the QS-divergence risk above ever causes a real mis-sift, revisit whether the Sift form should warn (not necessarily block) when the decision disagrees with a posting's own automatic MEETS/BELOW hint.
