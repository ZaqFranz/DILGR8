# Architecture Decisions

## 2026-08-07 — Manual DI via composition root instead of a DI framework

**Context:** `CLAUDE.md` mandates Dependency Injection as an architecture principle. Options were a framework (`tsyringe`, `inversify`) or manual constructor injection wired in one file.

**Decision:** Manual constructor injection, wired in `backend/src/container.ts`.

**Pros:** No extra dependency or decorator/reflection setup; fully readable without tooling; trivial to fake collaborators in tests by calling `new Service(fakeRepo)` directly.

**Cons:** Doesn't auto-scale — as the module count grows, `container.ts` will grow linearly and someone has to remember to wire new modules in by hand.

**Future impact:** If the module count roughly doubles (i.e. once Sifting, PQE, Evaluation, etc. are built out), revisit whether a lightweight DI container is worth the tradeoff. Not needed yet.

**Reference:** [patterns.md § Dependency Injection](./patterns.md#dependency-injection-manual-via-composition-root).

## 2026-08-07 — Prisma as the ORM, MySQL as the database

**Context:** The brief specified MySQL and "database migration, models, CRUD automation" without naming an ORM. Candidates: Prisma, TypeORM, Sequelize.

**Decision:** Prisma.

**Pros:** Strong generated TypeScript types (matches the "strict typing" coding standard), a first-class migration CLI (`prisma migrate dev`), a readable single-file schema that doubles as documentation.

**Cons:** Prisma's query API is less flexible than raw TypeORM query builders for very complex joins; generated client needs a build step (`prisma generate`) that must run after `npm install` and after every schema change.

**Future impact:** Complex reporting queries needed later (e.g. CompAss ranking matrices) may need raw SQL via `prisma.$queryRaw` rather than the query builder. Acceptable tradeoff for now.

**Reference:** [database.md](./database.md).

## 2026-08-07 — Documents stored on local disk, not object storage

**Context:** Applicants upload eligibility proof, IPCR, and Designation Order files. Needed a storage backend for the first pass.

**Decision:** Local disk (`backend/uploads/`, via Multer's `diskStorage`), with only file metadata in the `documents` table.

**Pros:** Zero external dependency/cost for local development and demoing.

**Cons:** Doesn't survive container restarts or scale past a single server instance; not production-ready as-is.

**Future impact:** Before any real deployment, swap `documents.upload.ts`'s storage engine for S3-compatible object storage (e.g. via `multer-s3` or a manual upload-then-record flow). The `Document` model's `filePath` field is storage-engine-agnostic (just a string), so this swap shouldn't require a schema change — only the multer storage config and the (not-yet-built) file-serving/download endpoint.

**Reference:** [database.md § documents](./database.md#documents).

## 2026-08-07 — IPCR/Designation/Eligibility-proof documents are applicant-level, not application-level

**Context:** The domain spec ties IPCR and "Designation to a Higher Position" documents to promotional *applications*, and eligibility proof to the applicant's eligibility checklist. A document can't be linked to an `Application` until the `Application` row exists, but the application-submission validation needs to check the documents exist *before* creating that row — a chicken-and-egg problem if documents were required to reference an application at upload time.

**Decision:** `Document.applicationId` is optional. IPCR, Designation Order, and Eligibility Proof documents are uploaded against the applicant (no `applicationId`) during registration, and `ApplicationsService.submit()` checks for their *existence and type* on the applicant, not for a specific link to the application being created.

**Pros:** Avoids the ordering problem entirely; also lets an applicant reuse the same IPCR/Designation Order across multiple promotional applications submitted within the same 10-day window, which matches "may apply for different positions at once."

**Cons:** If an applicant later needs *different* IPCR documents for two different promotional applications, this model can't distinguish which document backs which application — it only checks "does at least one exist." Not a requirement in the current spec, so left unhandled.

**Future impact:** If per-application document requirements become necessary, `Application.submit()` would need to accept explicit document IDs instead of inferring from type, and the frontend would need to prompt for that during the apply flow.

**Reference:** [database.md § documents](./database.md#documents), `backend/src/modules/applications/applications.service.ts`.

## 2026-08-07 — Evaluation implemented as a single score+decision on `Application`, not a full board evaluation-forms system

**Context:** The domain spec's Evaluation phase involves 13 board members each filling per-battery-test forms, feeding a Comparative Assessment (CompAss) ranking. The immediate ask was "admin can post jobs and evaluate applicants" — a much smaller scope.

**Decision:** Added four fields directly to `Application` (`evaluationScore`, `evaluationRemarks`, `evaluatedAt`, `evaluatedByUserId`) rather than a separate `Evaluation`/`EvaluationForm` model. Any one `ADMIN` user can record one score (0-100) + decision (`QUALIFIED`/`NOT_QUALIFIED`) + remarks per application via `PATCH /api/applications/:id/evaluate`, which overwrites the previous evaluation if run again.

**Pros:** Matches the requested scope exactly with minimal schema/API surface; the mandatory-field and score-threshold validation the spec calls out for "Eval Forms" is satisfied by the DTO (`score` and `decision` required, `score` bounded 0-100).

**Cons:** Doesn't model multiple evaluators, per-battery-test scores, or CompAss ranking at all — "evaluate" here means one person's overall score, and a second admin evaluating the same application silently overwrites the first. Not acceptable once the real multi-board-member Evaluation phase is built.

**Future impact:** When the full Evaluation phase from the RSP spec is implemented, this will need to become a proper `Evaluation` model (one row per evaluator per battery test, `Application` 1:N `Evaluation`), with the current `evaluationScore`/`evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` fields on `Application` likely repurposed as a computed/aggregate summary rather than raw input. Flagged in project-memory.md's technical debt.

**Superseded/extended:** the multi-evaluator system this entry anticipated was built on 2026-08-08 (see the entry below) — `evaluationScore`/`evaluationRemarks`/etc. on `Application` were kept as-is (the admin's own final decision) rather than repurposed, with the panel's per-evaluator scores living in new `PanelEvaluation`/`PanelScore` tables instead. Then, in a second 2026-08-08 entry ("Sifting/PQE/Interview pipeline"), this single free-standing "evaluate" action was itself repurposed into the Sifting phase's pass/fail call (`evaluationScore` dropped, `evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` renamed `siftingRemarks`/`siftedAt`/`siftedByUserId`) once it became clear it was standing in for Sifting all along, not a genuine final decision.

**Reference:** [database.md § applications](./database.md#applications), [api.md § Applications](./api.md#applications--apiapplications-all-require-auth), `backend/src/modules/applications/`.

## 2026-08-07 — Admin and applicant are separate route trees, not the same pages with conditional UI

**Context:** Asked for the admin panel to be visibly different from the applicant experience, with admins restricted to posting jobs and evaluating applicants only.

**Decision:** `frontend/src/features/admin/` is a distinct feature with its own pages under `/admin/*` routes, guarded by `<ProtectedRoute role="ADMIN">`. Applicant routes (`/jobs`, `/register`, `/applications`) are guarded by `<ProtectedRoute role="APPLICANT">` and redirect an admin back to `/admin/jobs` if they try to hit them directly (and vice versa). `Layout`'s nav shows an entirely different link set per role rather than the same links with some hidden. (Superseded/extended by the sidebar-shell decision below — the admin pages were originally `CreateJobPostingPage`/`EvaluateApplicantsPage` under the same top nav as applicants; now they're `JobManagementPage`/`UsersManagementPage`/`EvaluateApplicantsPage`/`AuditLogsPage` under `AdminShell`'s sidebar. `/registration` was later merged into `/register` — see the 2026-08-08 unified-registration decision below.)

**Pros:** Clean separation matches "admin can only post jobs and evaluate applicants" literally — there's no code path where an admin session can reach the applicant registration wizard or an applicant session can reach evaluation screens.

**Cons:** Some duplication of route-guard boilerplate between the two route groups in `App.tsx`; acceptable at this route count.

**Future impact:** If a third role appears (e.g. a board member distinct from a full admin), `ProtectedRoute`'s `role` prop would need to accept an array, and `Layout`'s nav switch would need a third branch.

## 2026-08-08 — Eligibility gate at application submission: structured per-posting requirement, join table over JSON/scalar-list

**Context:** Applicants without the eligibility a posting requires were able to apply — `ApplicationsService.submit()` only checked that a self-declared-eligible applicant had uploaded *some* `ELIGIBILITY_PROOF` document, never that their `eligibilityType` actually satisfied the posting. The posting side had no structured field to compare against: `JobPosting.qualificationEligibility` is free text (e.g. "RA 1080 or CSC Professional required") written by an admin for applicants to read, not something the backend can parse reliably. Fixing this required deciding how a posting expresses which eligibility type(s) it needs.

**Decision:** Added `JobPostingRequiredEligibility`, a join table (`jobPostingId`, `eligibilityType`, unique together) rather than a Prisma scalar-list field or a `Json` column on `JobPosting`. `JobPostingsRepository` flattens the join rows into a `requiredEligibilityTypes: EligibilityType[]` array on every read and replaces the full set (`deleteMany` + `create`) on update, so every other layer (service, controller, frontend) just sees a plain array — the join table is an implementation detail. An empty array means no eligibility is required. `ApplicationsService.submit()` now 400s before creating the application unless `applicant.hasEligibility && posting.requiredEligibilityTypes.includes(applicant.eligibilityType)` (skipped entirely when the array is empty), and the frontend's `JobPostingsListPage` disables/relabels the "Apply" button using the same check so an ineligible applicant is told why before clicking, not after. The pre-existing "if you claim eligibility, prove it with a document" check is unchanged and still runs independently.

**Pros:** A join table matches the codebase's existing style for admin-managed one-to-many links (`PanelAssignment` is structurally identical) and lets Prisma/MySQL enforce the schema directly, rather than trusting an unvalidated `Json` blob or working around MySQL's lack of native scalar-list support. Keeping the free-text `qualificationEligibility` field alongside it (rather than deriving display text from the structured array) preserves whatever nuance an admin already wrote there for applicants to read, while the structured array is the only thing enforcement logic touches.

**Cons:** Two eligibility-related fields on `JobPosting` now (`qualificationEligibility` free text, `requiredEligibilityTypes` structured) that admins must keep in sync by hand — nothing stops them drifting (e.g. the text says "RA 1080 preferred" while the checkboxes require CSC Professional). A join table also means every job-posting read does an extra `include`, though at this data volume it's immaterial.

**Future impact:** If eligibility requirements ever need per-posting nuance beyond "any one of these types" (e.g. "RA 1080 AND 2 years experience", or an eligibility type that's only acceptable for certain positions), the flat `EligibilityType[]` check in `ApplicationsService.submit()` is the first place to extend — it's isolated to a single `if` block, not spread across the codebase.

**Reference:** [database.md § job_posting_required_eligibilities](./database.md#job_posting_required_eligibilities), [api.md § Job Postings](./api.md#job-postings--apijob-postings) / [§ Applications](./api.md#applications--apiapplications-all-require-auth), `backend/src/modules/job-postings/job-postings.repository.ts`, `backend/src/modules/applications/applications.service.ts`, `frontend/src/features/job-postings/pages/JobPostingsListPage.tsx`.

## 2026-08-08 — Applicant-initiated application withdrawal: allowed up to FOR_INTERVIEW, not logged to the audit trail

**Context:** `Application.status` has included `WITHDRAWN` since the pipeline's first migration, but nothing ever set it - there was no applicant-facing withdraw action. `docs/rsp-domain-spec.md` has zero mentions of "withdraw"; there's no specified cutoff for when an applicant may withdraw, so which statuses should allow it was an undocumented call to make. Separately, every other `Application` transition (`sift`, `scheduleInterview`, exam-score import) is admin/panel-initiated and gets an `AuditLog` entry; `submit()` - the only prior applicant-initiated transition - does not, per the existing "applicant-side actions aren't audited yet" convention (see Audit Logging in `docs/project-memory.md`).

**Decision:** An application can be withdrawn (`PATCH /api/applications/:id/withdraw`) from `SUBMITTED`/`UNDER_SIFTING`/`QUALIFIED`/`FOR_INTERVIEW` - i.e. any non-terminal status. `NOT_QUALIFIED` and `WITHDRAWN` itself are excluded (400) since both are already terminal outcomes with nothing left to withdraw from. Ownership is enforced the same way `submit`/`listMine` do it - resolve the caller's own `Applicant` row via `userId`, then compare `application.applicantId` against it - and a mismatch 404s (not 403), so an applicant probing another applicant's application ID can't distinguish "not yours" from "doesn't exist." Like `submit()`, `withdraw()` does not write an `AuditLog` entry, staying consistent with the existing applicant-action convention rather than auditing this one applicant action while every other one stays unaudited.

**Pros:** The status whitelist matches how the rest of the pipeline already treats `NOT_QUALIFIED`/`WITHDRAWN` as terminal (nothing else transitions out of them either). Reusing `submit`/`listMine`'s exact ownership-resolution pattern, rather than inventing a new one, keeps applicant-scoped resource access consistent across the module.

**Cons:** The specific cutoff (through `FOR_INTERVIEW`, not further) is a judgment call with no spec backing it - a real DILG process might want to disallow withdrawal once an interview is scheduled, or allow it all the way through Deliberation once that phase exists. Not auditing applicant-initiated actions at all (submit, now withdraw) means there's no admin-visible trail if an applicant repeatedly submits and withdraws, though the audit log's stated purpose (`docs/decisions.md`'s audit-trail entry, `docs/patterns.md`) has always been about admin/panel write accountability, not applicant activity monitoring.

**Future impact:** If the domain spec is ever clarified with an explicit withdrawal cutoff, the whitelist is a single `WITHDRAWABLE_STATUSES` constant in `applications.service.ts` to change. If applicant-side audit logging is added later (tracked as a known gap in `docs/project-memory.md`), `withdraw()` should get the same treatment as `submit()` in that pass, not be singled out now.

**Reference:** [database.md § applications](./database.md#applications), [api.md § Applications](./api.md#applications--apiapplications-all-require-auth), `backend/src/modules/applications/applications.service.ts`, `frontend/src/features/applicant-registration/pages/MyApplicationsPage.tsx`.

## 2026-08-08 — Admin panel redesigned around a sidebar shell (`AdminShell`), not the shared top nav

**Context:** Asked for the admin panel to look like "an admin panel setup" — sidebar navigation — with full CRUD for Users, Jobs, and a new History of Logs section, distinct from the two-link top nav the admin section had before.

**Decision:** `frontend/src/features/admin/components/AdminShell.tsx` renders a left sidebar (Job Management / Users Management / Evaluate Applicants / History of Logs, active-highlighted via `useLocation()`) and every `/admin/*` page wraps its content in it. `Layout`'s top bar drops the admin nav links entirely (they'd be redundant with the sidebar) and stays minimal for admins; it also swaps `.app-main`'s centered-960px styling for a full-width `.app-main--full` when `pathname.startsWith("/admin")`, so the sidebar isn't squeezed into the applicant pages' narrow column.

**Pros:** Reads as a distinct admin product surface, not applicant pages with extra links; matches conventional admin-panel UX (persistent left nav) rather than the applicant section's simple top nav.

**Cons:** `AdminShell` is repeated as a wrapper in every admin page component rather than applied once via a nested-route `<Outlet/>` layout — chosen to keep the existing children-prop routing pattern in `App.tsx` unchanged (lower risk than restructuring routing) at the cost of one extra import/wrap per admin page.

**Future impact:** If the admin page count grows much further, revisit converting `/admin/*` to a nested-route layout (`<Route path="/admin" element={<AdminShell/>}>` with child `<Outlet/>` routes) to stop repeating the wrapper. Not needed at four pages.

**Reference:** [architecture.md § Role-based routing](./architecture.md#role-based-routing-frontend), `frontend/src/features/admin/components/AdminShell.tsx`.

## 2026-08-08 — Audit log (`AuditLog`) has no update/delete path, by design

**Context:** "History of Logs" needed a backing data model. The ask was framed as part of "complete CRUD" for the admin panel, but an audit trail that admins can edit or delete isn't actually an audit trail — it's just another editable table.

**Decision:** `AuditLogsRepository` only exposes `record()` (create) and `findMany()` (read). There is no `PATCH`/`DELETE` route, controller method, or repository method for `AuditLog` at any layer — not even admin-gated. Entries are written automatically by other services after a successful write (see [patterns.md § Audit Trail](./patterns.md#audit-trail-append-only-log-via-injected-repository)).

**Pros:** The log stays trustworthy as a record of what actually happened; no risk of an admin (accidentally or otherwise) editing history to hide an earlier action.

**Cons:** No way to redact a log entry that contains something it shouldn't (e.g. if a `details` string ever included sensitive data by mistake) short of a direct database operation outside the app. Acceptable given `details` strings are built from data already visible elsewhere in the admin panel (emails, job titles, scores) — nothing logged that isn't already exposed via the CRUD screens themselves.

**Future impact:** If regulatory/compliance requirements ever demand log redaction, that should be a narrowly-scoped, heavily-audited-itself operation (e.g. a one-off maintenance script with its own logging), not a general API endpoint.

**Reference:** [database.md § audit_logs](./database.md#audit_logs), [api.md § Audit Logs](./api.md#audit-logs--apiaudit-logs-admin-only-read-only).

## 2026-08-08 — `JobPosting.createdByUserId` and `Application.evaluatedByUserId` are nullable/`SetNull`, so admins are deletable

**Context:** Users Management needed real delete capability. `JobPosting.createdByUserId` was originally a required field with Prisma's default `Restrict` behavior on delete, which would silently block deleting any admin who had ever posted a job — surprising and undiscoverable from the Users Management UI (the delete would just fail with a generic FK error).

**Decision:** Made `createdByUserId` optional (`String?`) with an explicit `onDelete: SetNull`, matching the pattern `evaluatedByUserId` on `Application` already used. Deleting a user now always succeeds (except for self-delete, blocked at the service layer) and severs the creator/evaluator link on their past job postings/evaluations rather than blocking or cascading.

**Pros:** "Delete a user" behaves predictably regardless of what that user has done in the system; job postings and evaluation history survive the deletion of whoever made them, which matches how the History of Logs already preserves entries after actor deletion (`AuditLog.actorUserId` is also nullable/`SetNull`).

**Cons:** After deleting an admin, their past job postings/evaluations show no creator/evaluator in the UI (`createdBy`/`evaluatedBy` becomes `null`) — there's no "deleted user" placeholder value, just absence. Acceptable since the `AuditLog` history still records what they did (with `actor: null` shown as "(deleted user)" in `AuditLogsPage`), even after the `User` row itself is gone.

**Reference:** [database.md § job_postings](./database.md#job_postings), `backend/prisma/schema.prisma`.

## 2026-08-08 — Registration unified into one flow; applicant pages gated on `registrationCompletedAt`

**Context:** The original design split applicant onboarding into two steps: `POST /auth/register` (email/password only, at `/register`) immediately followed by a redirect to a separate post-login wizard (`/registration`, behind `<ProtectedRoute role="APPLICANT">`) for the demographic profile, work experience, L&D, awards, and documents. Nothing stopped an authenticated applicant from navigating straight to `/jobs` or `/applications` without ever finishing the wizard — the "rest of the flow" was reachable, and skippable, only by choice of navigation, not by enforcement. Explicit product direction: all applicant information must be captured as part of registration, not deferred to after the applicant is already logged in and using the app.

**Decision:** Merged the account-creation form and the former wizard into a single component, `RegistrationPage` (`frontend/src/features/applicant-registration/pages/RegistrationPage.tsx`), mounted at one route (`/register`). It renders the account step for unauthenticated visitors and continues in place through profile → work experience → L&D → awards → documents after `register()` succeeds, with no route change in between. Added `Applicant.registrationCompletedAt` (nullable `DateTime`) and `POST /api/applicants/me/complete-registration`, called when the applicant finishes the last step (validates an eligibility-proof document has been uploaded if `hasEligibility` is true). `AuthContext` exposes `registrationComplete` (fetched from `GET /api/applicants/me` right after login/register and on session restore); `ProtectedRoute` and `HomeRedirect` redirect any applicant with `registrationComplete === false` to `/register`, whichever page they try to reach directly. The old `RegisterPage.tsx` and `RegistrationWizardPage.tsx` were deleted.

**Pros:** Matches the "collect everything at registration" requirement literally — there is no code path to `/jobs` or `/applications` that bypasses profile/work-experience/L&D/awards/documents. `/register` also stays reachable after completion (e.g. Layout's "My Profile" link) so applicants can still edit their record without a separate profile-editing surface to maintain.

**Cons:** `AuthContext` now depends on the `applicant-registration` feature's API module (`getMyProfile`) to resolve `registrationComplete`, which is a cross-feature import `shared/auth` didn't previously have. Every protected-route render for an applicant does one extra `GET /api/applicants/me` round trip on session restore/login (cheap single-row lookup, not on every navigation) that a JWT-embedded claim could have avoided at the cost of needing to re-issue tokens whenever registration status changes.

**Future impact:** If more roles or a "partially registered admin" concept is ever introduced, `registrationComplete` and the redirect logic in `ProtectedRoute`/`HomeRedirect` should generalize to a role-keyed "onboarding complete" check rather than the current `APPLICANT`-only branch.

**Reference:** [architecture.md § Registration gating](./architecture.md#registration-gating-frontend), [database.md § applicants](./database.md#applicants), [api.md § Applicants](./api.md#applicants--apiapplicants-all-require-auth).

**Reference:** [architecture.md § Role-based routing](./architecture.md#role-based-routing-frontend), `frontend/src/shared/components/ProtectedRoute.tsx`, `frontend/src/App.tsx`.

## 2026-08-08 — Interview panel & CompAss tabulation: multi-criteria rubric, admin-assigned panelists, `Application.evaluate` left unguarded

**Context:** Building the real multi-evaluator Evaluation phase the 2026-08-07 entry above deferred. Two scope forks needed deciding: (1) does a panelist give one overall interview score, or score several separately-weighted criteria; (2) can any `PANEL` account score any interview-stage applicant, or only ones on postings an admin explicitly assigned them to. Both were resolved toward the more literal reading of the domain spec's "evaluation forms" and "13 board members" framing rather than the simpler option.

**Decision:** Added `Role.PANEL` (a full third role, not an admin sub-type — provisioned the same way as `ADMIN`, through Users Management's existing role `<select>`) and `ApplicationStatus.FOR_INTERVIEW`. Four new tables: `EvaluationCriterion` (admin-editable rubric, `maxScore` doubling as weight), `PanelAssignment` (admin-managed M:N, posting × panel user), `PanelEvaluation` + `PanelScore` (one evaluation per panelist per application, with per-criterion score rows, upserted on re-submit). `PATCH /applications/:id/schedule-interview` (new, admin-only) moves an application to `FOR_INTERVIEW`; the existing `PATCH /applications/:id/evaluate` is unchanged and still finalizes regardless of current status — no server-side check blocks an admin from qualifying/disqualifying an application before every assigned panelist has scored it. `GET /panel-evaluations/tabulation/:jobPostingId` computes the ranked CompAss matrix (sum per panelist, average across panelists, descending rank) at read time in application code, surfaced as two extra columns on `EvaluateApplicantsPage` rather than a separate matrix view.

**Pros:** The rubric being admin-editable matches the spec's "administrator can edit/update evaluation forms" literally, rather than hardcoding assumed criteria the spec doesn't actually enumerate. Assignment-gating matches how real interview boards are staffed (not every panelist should see every posting) and is enforced server-side (`PanelEvaluationsService.submit` 403s a panelist scoring an application on a posting they're not assigned to), not just hidden in the UI. Leaving `evaluate` unguarded keeps the admin's finalize action simple and avoids a second source of truth for "is this ready to decide" — the tabulation view already shows `panelistsSubmitted`/`panelistsAssigned` for the admin to judge.

**Cons:** No server-side block on premature finalization means the only guard against an admin qualifying an applicant before the board has finished scoring is a frontend warning (`EvaluationRow` reads `panelistsSubmitted < panelistsAssigned` from the tabulation response) — bypassable by calling the API directly. Criteria are global, not per-posting or per-battery-test, so every interview board scores against the same rubric regardless of position; the spec's "per battery test/activity" framing could imply otherwise, but nothing in the actual ask required per-posting rubrics, and building that would mean either duplicating criteria per posting or adding a join table with no concrete requirement driving its shape yet.

**Future impact:** If premature finalization turns out to be a real problem in practice (not just a theoretical gap), add a server-side check in `ApplicationsService.evaluate()` requiring `panelistsSubmitted === panelistsAssigned` for `FOR_INTERVIEW` applications, mirroring the pattern already used for `JobPostingsService.delete`'s guard. If per-posting or per-battery-test rubrics become a real requirement, `EvaluationCriterion` would need a nullable `jobPostingId` (global rubric when null, override when set) rather than a breaking schema change. Letter/notice generation and the spec's 1:5 auto-shortlisting ratio (both listed under the domain spec's "Tabulation" section) remain unimplemented — a separate notifications/documents feature.

**Reference:** [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation), [database.md § evaluation_criteria / panel_assignments / panel_evaluations](./database.md#evaluation_criteria), [api.md § Evaluation Criteria](./api.md#evaluation-criteria--apievaluation-criteria), `backend/src/modules/evaluation-criteria/`, `backend/src/modules/panel-assignments/`, `backend/src/modules/panel-evaluations/`.

**Superseded/extended:** `PATCH /applications/:id/evaluate` no longer exists as of the 2026-08-08 "Sifting/PQE/Interview pipeline" entry below — it was repurposed into the Sifting decision (`PATCH /applications/:id/sift`, gated to `UNDER_SIFTING`) and there's no longer any post-interview "finalize" action at all, so the premature-finalization gap this entry flags is moot for now (the pipeline simply stops at `FOR_INTERVIEW` until a future Deliberation phase is built).

## 2026-08-08 — Sifting/PQE/Interview pipeline: repurpose the free-standing "evaluate" action, add an Excel-based PQE score import

**Context:** The Dashboard already tallied `ApplicationStatus` (`SUBMITTED`/`UNDER_SIFTING`/`FOR_INTERVIEW`/`QUALIFIED`/`NOT_QUALIFIED`/`WITHDRAWN`), but only `SUBMITTED`, `FOR_INTERVIEW`, and `QUALIFIED`/`NOT_QUALIFIED` were ever actually set — `UNDER_SIFTING` had no code path at all, and `QUALIFIED`/`NOT_QUALIFIED` were set by a free-standing "Evaluate Applicants" action (0-100 score + decision + remarks, callable from any status) that had drifted into being a generic final-call tool rather than anything tied to a specific RSP phase, once the real per-criterion panel scoring (`PanelEvaluation`/`PanelScore`) was built separately. The user described the intended order explicitly: Submitted → Under Sifting → Qualified → Examination (external; system just records the score) → For Interview (admin schedules, applicant emailed) → Panel Tabulation (already built) — which matches the domain spec's Sifting phase (pass/fail against education/training/experience/eligibility) and PQE phase (batch exam, score recorded, notice sent regardless of pass/fail) exactly.

**Decision:** Repurposed the existing "evaluate" action into the Sifting decision: `Application.evaluationScore` dropped (sifting is pass/fail, not scored), `evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` renamed `siftingRemarks`/`siftedAt`/`siftedByUserId`, and `PATCH /applications/:id/evaluate` became `PATCH /applications/:id/sift` (`SiftApplicationDto = { decision, remarks? }`), now gated to `status === UNDER_SIFTING` (previously callable from any status). `ApplicationsRepository.create()` now sets `status: "UNDER_SIFTING"` directly instead of relying on the `@default(SUBMITTED)` schema default, so every application is "Under Sifting" the instant it's submitted — no separate manual "start sifting" step. Added `Application.examinationScore`/`examinationScoredAt` and a new `POST /applications/import-exam-scores` (multipart: `.xlsx`/`.xls` + `jobPostingId`, `ADMIN`-only) that parses an Excel file (`exceljs`, `Name`/`Score` header columns) and matches each row by normalized full name against that posting's `QUALIFIED` applicants — matches get the score + a `[DEV EMAIL]`/SMTP notification, non-matches come back in the response for the admin to review and re-upload rather than failing the whole import. `PATCH /applications/:id/schedule-interview`'s guard changed from `status in {SUBMITTED, UNDER_SIFTING}` to `status === QUALIFIED && examinationScore !== null`, enforcing sifting-then-PQE-then-interview in that order.

**Pros:** Fixes a real semantic bug rather than adding a parallel feature — the old "evaluate" action was already standing in for Sifting, just without the name, the gating, or the pipeline position to show it. The Excel import matches how PQE results actually arrive in practice (a batch exam run outside the system, results tabulated in a spreadsheet) without requiring the admin to hand-enter scores one row at a time. Name-matching with a reviewable unmatched list is more forgiving than an all-or-nothing import — a handful of formatting mismatches don't block everyone else's scores from landing.

**Cons:** Name-matching is inherently fuzzier than an ID-based join — two applicants with the same normalized name on the same posting would collide (last-write-wins in the lookup map), and a typo in the spreadsheet silently produces an "unmatched" row rather than a hard error pointing at the specific cell. No pass/fail threshold is enforced on the PQE score itself (by explicit choice - score is informational, the admin decides whether to schedule an interview), so nothing stops an admin from scheduling an interview for a very low PQE score. The applicant-facing stage tracker's "Examination" node doesn't visually distinguish "awaiting a score" from "scored, awaiting interview scheduling" - both render as the same in-progress node, with the actual score (if any) shown as a line of text underneath instead.

**Future impact:** If PQE score collisions on duplicate names become a real problem, the import would need a secondary identifier (e.g. an applicant reference number column) rather than name-only matching. If a pass/fail threshold is ever wanted, `examinationScore`'s consumer (`scheduleInterview`'s guard) is the one place to add it - no schema change needed since the score is already a plain `Int`. The pipeline still stops at `FOR_INTERVIEW`/panel tabulation - Deliberation (the RD's final decision), Compliance to Requirements, and Onboarding remain future work per project-memory.md.

## 2026-08-09 — Self-service password change: one role-agnostic endpoint/page, not three role-specific ones

**Context:** Neither `ADMIN` nor `PANEL` had any self-account page at all (only Users Management, which manages *other* users' accounts), and the applicant's "My Profile" link only ever reached demographic-profile fields - the `RegistrationPage` wizard's "Account" step is literally the anonymous sign-up form and is filtered out (`visibleSteps`) the moment the user is authenticated, so there was no reachable UI for a logged-in applicant to change their password either. `PATCH /api/users/:id` (admin-only, for managing other users) has never touched `passwordHash`. No password-change/reset code existed anywhere in `auth/` or `users/` before this.

**Decision:** One new endpoint, `PATCH /api/auth/me/password` (`authenticate` only, no `requireRole` - any logged-in user can call it for themselves), verifying `currentPassword` against the caller's own `passwordHash` via the existing `verifyPassword`/`hashPassword` helpers (`@/shared/utils/password`, bcryptjs, same salt rounds as registration) rather than adding a parallel hashing path. One new frontend page, `ChangePasswordPage` at `/account/password`, wrapped in `<ProtectedRoute>` with **no** `role` prop (so `APPLICANT`/`ADMIN`/`PANEL` all pass), and one "Change Password" link added to `Layout`'s header inside the existing `isAuthenticated` branch (visible regardless of role) rather than duplicating the link into `AdminShell`'s sidebar, the `PANEL` nav branch, and the `APPLICANT` nav branch separately. A wrong `currentPassword` 400s with a Zod-flatten-shaped `fieldErrors.currentPassword` (matching the `validate` middleware's existing error shape) so the frontend's existing `getFieldErrors` util renders it inline exactly like any other form validation error, rather than a 401 that risked being misread by future 401-handling code as "session expired."

**Pros:** A single implementation serving three roles avoids the exact duplication `CLAUDE.md` warns against - one endpoint, one form, one route, one nav link, instead of three near-identical copies (which is what a naive "add it separately to Users Management for admin, RegistrationPage for applicants" approach would have produced). Reusing `verifyPassword`/`hashPassword` guarantees the new password is hashed identically to how login already checks it - no risk of a second hashing convention drifting out of sync.

**Cons:** No token/session invalidation on password change - since the JWT scheme here is fully stateless (no token version, no server-side blocklist), any other already-issued, unexpired token for that user keeps working until it naturally expires (`JWT_EXPIRES_IN`, 8h in this environment). This is a real gap if "changing your password should immediately kick out anyone else logged in as you" is ever a hard requirement - it isn't enforced today for any account action (there's no equivalent revocation on role changes either), so this isn't a regression, just an existing limitation that now also applies here. There's also still no "forgot password" recovery path for a user who doesn't know their *current* password - this feature only covers the "I know my password and want to change it" case.

**Future impact:** If session invalidation-on-change becomes a requirement, the natural fix is a `tokenVersion` int on `User`, bumped in `changePassword()`, checked (and matched against the JWT payload) in the `authenticate` middleware - a schema change and a new claim, not a redesign of this feature. A true "forgot password" flow (no current password known) would need email delivery (already wired via `EmailService`) plus a time-limited reset token, which is a separate, larger feature from this one.

**Reference:** [api.md § Auth](./api.md#auth--apiauth), [project-memory.md § Auth](./project-memory.md), `backend/src/modules/auth/`, `frontend/src/features/auth/pages/ChangePasswordPage.tsx`, `frontend/src/shared/components/Layout.tsx`.

## 2026-08-09 — Re-uploading a single-instance document type replaces it, rather than rejecting the upload or leaving duplicates

**Context:** User-reported: "I can upload multiple PDS and Application Letter. Is this ok?" Nothing broke functionally - `completeRegistration()`'s check is satisfied by *any* document of the required type existing - but the Documents table would accumulate indistinguishable duplicates with no way to tell which one is authoritative, which is a real problem for a document an admin will eventually review. The generic upload flow (`DocumentsSection`'s type dropdown + file input) had no concept of "this type already has a file."

**Decision:** For the eight document types that represent one current document per applicant (`APPLICATION_LETTER`, `PDS`, `IPCR`, `ELIGIBILITY_PROOF`, `TRANSCRIPT_OF_RECORDS`, `DIPLOMA`, `PQE_NOTICE`, `DESIGNATION_ORDER`), `DocumentsService.upload()` now deletes any existing document of that same type for the applicant (DB row + file on disk) before inserting the new one - re-uploading replaces rather than duplicating or erroring. `LD_PROOF`/`AWARD_PROOF` were initially excluded from this rule (multiple proofs per entry was the intentional design when those features were built), but see the same-day follow-up below - that stance was reversed a few hours later, same day, once the client saw the multi-file behavior in practice and asked for one-per-entry instead. `OTHER` remains a genuine multi-file miscellaneous catch-all, exempt throughout. The frontend mirrors the same type set (necessarily duplicated, `SINGLE_INSTANCE_TYPES` in both `documents.service.ts` and `DocumentsSection.tsx`) so it can drop the now-stale local entry and label the toast "replaced" instead of "uploaded."

**Follow-up (same day):** Client asked for the "Document type" dropdown to stop offering a type once it's already on file, rather than letting the user re-select it and silently trigger a replace. `DocumentsSection` now filters its dropdown to `computeAvailableTypes(items)` - single-instance types disappear from the list the moment a document of that type exists, reappearing only if the applicant removes it via the table's existing "Remove" button first. This makes the backend's replace-on-reupload path effectively unreachable through normal UI use (you can no longer select an already-satisfied type to trigger it) while leaving it in place server-side as a defensive fallback - harmless, and still correct if ever reached some other way. The same "controlled `<select>` value must always match a rendered `<option>`" bug fixed earlier this session for the eligibility dropdown applies here too: `type` state is now initialized lazily from `computeAvailableTypes(items)` on mount, and explicitly advanced to the next available type right after a successful upload removes the just-uploaded type from the list - both needed so the dropdown's value can never point at an option that no longer renders.

**Pros:** Matches how most people expect a single-slot file upload to behave (re-upload = replace, like a profile photo) while the dropdown filter now makes the *intent* explicit up front - a type visibly disappearing communicates "you're done with this one" better than only finding out via a "replaced" toast after the fact. Guarantees each single-instance type has at most one row - no ambiguity for whoever reviews the Documents list later. Enforced server-side, not just hidden in the UI, so it holds even if a client somehow re-submits the same type twice.

**Cons:** A user who wants to fix a wrong upload now has one extra required step (Remove, then re-add) instead of just re-selecting and re-uploading over it - a deliberate tradeoff for making "this type is already covered" visible rather than silent. No confirmation dialog before the underlying replace, unlike every other destructive action in this app (`ConfirmDialog` is used everywhere else data is deleted) - moot in the common path now that the dropdown won't let you reach it, but still true for the defensive backend fallback.

**Future impact:** If a type ever needs to allow more than one file *and* replace-on-type (neither "accumulate" like `LD_PROOF` nor "single slot" like `PDS`), both `SINGLE_INSTANCE_TYPES` sets and `computeAvailableTypes()` are the two places to introduce a third category.

## 2026-08-09 — PDS split into a required PDF copy and a required Excel copy, with per-document-type file-type enforcement

**Context:** Client-supplied requirement: "Applicants are required to upload Pdf and excel file of PDS. Make sure system will check the file type correctly." The real-world CS Form 212 (PDS) is filled out as an Excel workbook (needed as data, e.g. for future PDS-driven features) but is also conventionally submitted as a signed/scanned PDF. Before this change `PDS` was one single-instance slot, PDF/JPEG/PNG only (the same blanket rule every document type shared) - there was no way to require the actual spreadsheet at all, and no per-type file-type enforcement anywhere: the only gate was multer's global `fileFilter` allowing PDF/JPEG/PNG for every type indiscriminately, so nothing stopped (say) a JPEG being uploaded as "PDS" today, and nothing would have stopped an Excel file being uploaded as an Application Letter once Excel support was added for PDS.

**Decision:** Added a new `DocumentType.PDS_EXCEL` (migration `20260809105041_add_pds_excel_document_type`), a second single-instance slot alongside the existing `PDS` (now labeled "— PDF copy" in the UI, `PDS_EXCEL` labeled "— Excel (CS Form 212) copy"). `ApplicantsService.completeRegistration()` now requires both. File-type checking became genuinely per-`DocumentType` rather than one global rule: multer's `fileFilter` (`documents.upload.ts`) was widened to the *union* of every type's allowed MIME types (PDF/JPEG/PNG plus the two Excel MIME types already used by the PQE score import) - it's just the outer gate, since `fileFilter` runs mid-multipart-stream and can't reliably depend on `type` if it's a form field ordered after `file`. The authoritative check is new: `DocumentsService.upload()` calls `assertMimeTypeAllowed(fields.type, file.mimetype)` against `ALLOWED_MIME_TYPES_BY_DOCUMENT_TYPE`, run after multer has fully parsed the request (so `fields.type` is always populated regardless of field order) - every type defaults to PDF/JPEG/PNG except `PDS_EXCEL`, which requires XLSX/XLS, and mismatches 400 with a message naming the expected format. The frontend (`DocumentsSection.tsx`) mirrors this: the file input's `accept` attribute and a client-side `validateFileType()` check both switch based on the selected type, and switching the "Document type" dropdown clears any already-chosen file rather than silently carrying over a selection that may no longer be valid for the new type.

**Pros:** Directly implements the stated requirement (both formats required, each validated as the format it claims to be) without special-casing PDS's validation path outside the existing single-instance-type machinery - `PDS_EXCEL` is just another entry in `SINGLE_INSTANCE_TYPES`/`DOCUMENT_CHECKLIST`/`DOCUMENT_TYPE_LABELS`. The per-type MIME map is a real fix, not just scoped to PDS: an Excel file can no longer be uploaded as e.g. `APPLICATION_LETTER` even though multer's outer gate now allows the MIME type through generally - verified via direct API testing (5 cases: PDS_EXCEL-as-JPEG rejected, PDS_EXCEL-as-XLSX accepted, PDS-as-XLSX rejected, PDS-as-PDF accepted, APPLICATION_LETTER-as-XLSX rejected). Two-layer enforcement (broad multer gate + precise per-type service check) avoids relying on multipart field ordering, which is a documented but fragile way to make `fileFilter` type-aware.

**Cons:** Widening multer's `fileFilter` to accept Excel MIME types globally means a mismatched file (e.g. an Excel file selected for `APPLICATION_LETTER`) is now written to a temp path on disk by multer before `DocumentsService.upload()` rejects it and the request 400s - the file is never linked from a DB row (so it doesn't show up anywhere in the app) but is left orphaned in `backend/uploads/` with nothing to clean it up. This isn't a new problem this change introduced (every existing validation failure in `upload()` - e.g. an unowned `applicationId`/`ldInterventionId`/`awardId` - already has the same orphan-on-reject gap, since multer always finishes writing before the service runs) but the surface area is larger now that more MIME types clear the outer gate only to be rejected by the inner one. `PDS`'s own allowed types didn't change (still PDF/JPEG/PNG, not narrowed to PDF-only) since the client's requirement was "PDF and Excel," not "PDF only" - a scanned PDS photographed as JPEG still passes, consistent with every other document type's tolerance for a photo of a paper copy.

**Future impact:** `ALLOWED_MIME_TYPES_BY_DOCUMENT_TYPE` in `documents.service.ts` is now the one place to add a stricter or different file-type rule for any other document type, without touching multer's `fileFilter` again. The orphaned-file-on-rejected-upload gap (pre-existing, called out above) would be worth fixing generally - e.g. `upload()` unlinking `file.path` in a catch block before rethrowing - if orphaned upload files ever become an operational nuisance; not done here since it's out of scope for this specific request and pre-dates it.

**Decision:** `Document.applicationId` already existed (added earlier for a different, unused purpose - see [database.md § documents](./database.md#documents)) and turned out to be exactly the right shape for this: `APPLICATION_LETTER` is now created only as part of `POST /api/applications`, tied via `applicationId` to the specific `Application` it was submitted with, and removed entirely from the registration-time paths - `completeRegistration()` no longer checks for it, `uploadDocumentFieldsSchema`'s `type` enum no longer accepts it (so it can't be created "loose," untied to any application, through the generic `/applicants/me/documents` endpoint), and it's out of `SINGLE_INSTANCE_TYPES` on both backend and frontend (it's one-per-application now, not one-per-applicant). `POST /api/applications` changed from a plain JSON `{ jobPostingId }` body to `multipart/form-data` (`jobPostingId` + `file`), following the same manual-`safeParse`-in-controller pattern already used by `POST /import-exam-scores` (the `validate()` middleware can't run before multer has parsed the body). `ApplicationsService.submit()` 400s if no file is provided; on success, `ApplicationsRepository.createWithApplicationLetter()` creates the `Application` row and the `Document(type=APPLICATION_LETTER, applicationId=...)` row together inside one `db.$transaction()`, so the two can never exist independently of each other. A small shared `createDiskStorage()` helper (`backend/src/shared/upload/diskStorage.ts`) was factored out of `documents.upload.ts` so the new `applicationLetter.upload.ts` multer config (PDF/JPEG/PNG only, same as the pre-existing default rule) doesn't duplicate the mkdir/destination/filename logic a third time. On the frontend, `JobPostingsListPage`'s "Apply" button now opens a modal (file input + the DILG addressee/thru block, moved verbatim from `DocumentsSection`'s old special-cased checklist row) instead of submitting on click - applying was a single fire-and-forget click before; it's now a small form, unavoidably, since a click handler can't carry a file.

**Pros:** Matches the real-world object being modeled - a letter genuinely is per-vacancy, so "per-application" is the correct scope, not an approximation. Removing it from `completeRegistration()`'s gate also lets an applicant finish registration and start browsing/applying sooner (one fewer document blocking that milestone), while still being unable to actually submit any application without a letter for that specific one. The atomic transaction rules out the partial-state failure mode (an application that exists with no letter, or a letter uploaded with no application to show for it) that a naive "create application, then upload document" two-step client flow would have risked.

**Cons:** `POST /api/applications` is now a breaking API change (JSON → multipart) for any other API consumer, though there's only ever been the one frontend caller. The Apply flow is measurably more friction than a single click (choose a file, then confirm) - an unavoidable consequence of the letter no longer being pre-uploaded, not a regression to fix. An applicant applying to five postings now uploads five separate PDF letters even if the content barely differs, versus the old one-and-done registration upload - a real cost of correctness (each letter *should* be able to differ, addressed/dated per vacancy) but still more repeated effort than before.

**Future impact:** If a "reuse my last letter" convenience is ever wanted, `GET /api/applicants/me/documents` already returns every prior `APPLICATION_LETTER` (with its `applicationId`), so the frontend could offer "copy from a previous application" as a pre-fill without any backend change - it would still need to be re-uploaded as a new `Document` for the new `applicationId`, since one document can't belong to two applications. If per-application documents are ever needed beyond the letter (e.g. a posting-specific supplementary form), `createWithApplicationLetter()`'s transaction pattern - create the parent row and its required child document together - is the template to extend or replicate.

## 2026-08-09 — Fixed `.app-header`'s sticky positioning, broken since the day it was added

**Context:** Client request: "Lets make our top nav sticky in Applicant page." `.app-header` already had `position: sticky; top: 0;` (present since this app's earliest CSS, likely intended to work from the start) - so the request pointed at a real, pre-existing bug rather than a missing feature. Confirmed via a live scroll test on `/register` (a long form, easy to scroll): `.app-header`'s `getBoundingClientRect().top` moved in exact lockstep with `window.scrollY` instead of staying at `0`, i.e. it behaved as `position: static` despite computing to `sticky`. Walking the DOM ancestor chain from `.app-header` up to `html` and inspecting each one's computed `overflow` found the cause: `body`'s computed `overflow` was `hidden auto`, not the authored `overflow-x: hidden` alone. Per the CSS Overflow Module spec, if `overflow-x` is set to a non-`visible` value while `overflow-y` is left `visible`, the *computed* value of `overflow-y` is forced to `auto` too (a scrolling axis can't be paired with a non-scrolling one) - so `html { overflow-x: hidden; }` / `body { overflow-x: hidden; }` (added earlier the same day, for the `.auth-page` full-bleed breakout's few px of horizontal overflow - see that entry above) silently turned both `html` and `body` into independent scroll containers. `.app-header`'s nearest such container was no longer "the real viewport scroll" in the way `position: sticky` needs.

**Decision:** Changed `overflow-x: hidden` to `overflow-x: clip` on both `html` and `body`. `overflow: clip` (CSS Overflow Level 3+) clips overflowing content the same way `hidden` does, but - unlike `hidden` - does not establish a scrollable overflow region, so it isn't subject to the overflow-x/y pairing rule and doesn't turn its element into a scroll container. This was a one-line-times-two fix once the root cause was found; no component/page code changed, since the header's `position: sticky` was already correct and every page shares the one `Layout` component. Verified with a live scroll test using the exact same method that found the bug (`getBoundingClientRect().top` before/after `window.scrollTo`) - the header now stays at `top: 0` through a scroll - and separately re-confirmed the original horizontal-overflow clipping this rule exists for still works (`document.documentElement.scrollWidth === window.innerWidth` on the login page, no regression).

**Pros:** Fixes sticky positioning for the header across every role (Applicant/Admin/Panel all share `Layout`), not just the applicant pages named in the request - the bug was never applicant-specific, it just happened to be reported from there. Root-cause fix rather than a workaround (e.g. removing `position: sticky` and hand-rolling a scroll listener, or re-adding a scroll container purpose-built for the header) - `clip` does exactly what the original `hidden` was reached for ("just clip this overflow") without the side effect that was never intended.

**Cons:** `overflow: clip` is a newer value (Chrome 90+/Firefox 113+/Safari 16+) than `hidden` - a small compatibility regression on very old browsers, where it would fall back to the initial `visible` (re-exposing the few px of horizontal overflow the rule exists to hide) rather than silently degrading to the old clipped-but-sticky-broken behavior. Judged acceptable: this app already depends on `backdrop-filter` and other modern-only CSS with no stated legacy-browser requirement.

**Future impact:** If any other ancestor ever needs `overflow-x`/`overflow-y` set independently again, reach for `clip` over `hidden` by default when scrolling that axis is genuinely never wanted - `hidden`'s scroll-container side effect is easy to reintroduce by habit and won't be obvious until something inside it that depends on viewport-relative positioning (sticky headers, but also e.g. `position: fixed` in some edge cases) quietly stops working.

**Reference:** `frontend/src/shared/styles/index.css`, [architecture.md § full-bleed auth pages](./architecture.md#registration-gating-frontend).

The file route explicitly checks `fs.access(document.filePath)` before calling `res.sendFile` and throws a clean 404 `NotFoundError("Document file")` if it's missing, rather than letting a raw filesystem error surface - this is not a hypothetical: earlier the same day, an unrelated cleanup mistake in this session permanently deleted 11 real files out of storage while their `Document` rows stayed intact in the DB, so a graceful "file not found" path for exactly that scenario was already known to matter, not just defensive-programming boilerplate. On the frontend, a new `ApplicantDocumentsModal` (opened via a "View Documents" button added to `EvaluationRow`'s existing action cell) fetches the list, then on a per-document "View"/"Download" click fetches the file as a `Blob` via a new `apiRequestBlob()` helper in `apiClient.ts` (mirrors `apiRequest`'s auth header + error-unwrapping, but resolves to a `Blob` instead of parsing JSON) and turns it into an object URL - `window.open()` in a new tab for inline-renderable types (PDF/JPEG/PNG), or a synthetic `<a download>` click for XLS/XLSX, which browsers can't render inline regardless of how the URL is opened. A blob-fetch was necessary rather than a plain `<a href>`/`window.open(apiUrl)`: this route requires a Bearer token, which a simple browser navigation can't attach, and putting the token in a query string instead (so a plain link would work) was rejected as a real credential-leak risk (browser history, referrer headers, server access logs) for a token with a multi-hour lifetime - fetching with the header and converting to a blob URL keeps the token out of any URL entirely. `Modal` gained an optional `wide` prop (`.modal--wide`, 720px vs. the default 440px) since the document list's five columns didn't fit the form-sized default - kept as a boolean opt-in on the existing shared component rather than a one-off custom modal, so any other future data-table-shaped modal can reuse it.

**Pros:** Reuses existing repository/service methods and the established `requireRole("ADMIN")` route-gating pattern throughout - no new architectural pattern introduced, just the first use of a "serve a file" endpoint shape in this codebase. The missing-file 404 path was verified against a real case (viewing Juls Acidre's now-missing files correctly showed "Document file not found" instead of a broken tab or a crash), not just a theoretical one. Keeping the token out of the URL is a real, not just theoretical, security improvement over the simpler `<a href>` alternative.

**Cons:** `window.open()` inline preview can be blocked by browser popup blockers if not triggered directly inside a user click handler - it is here (the `onClick` handler calls `fetchDocumentFileUrl` and `window.open` in the same async function without an intervening `await` that a blocker would treat as "no longer a direct user gesture" in most browsers, but this is a known fragility class of `window.open`-after-`fetch` patterns generally). Object URLs from `window.open()`'s blob are revoked after a fixed 10-second delay (long enough for the new tab to finish loading the blob independently) rather than tracking the opened tab's lifetime precisely - a pragmatic timeout instead of a more complex handle-tracking scheme, since object URLs are cheap and scoped to the current page's lifetime anyway (they're not shared across tabs by reference, only by the already-loaded content).

**Future impact:** `apiRequestBlob()` is now the template for any future binary-response endpoint (e.g. if an applicant-facing "view my own uploaded document" feature is ever added, mirroring this admin one). `Modal`'s `wide` prop is available to any future modal that needs more than form-width. The `fs.access`-before-`sendFile` pattern in `getFileForAdmin()` is the template if any other endpoint ever needs to serve a file that might legitimately be missing.

**Reference:** [api.md § Applicants](./api.md#applicants--apiapplicants-all-require-auth), `backend/src/modules/applicants/documents/documents.service.ts`, `backend/src/modules/applicants/documents/documents.controller.ts`, `backend/src/modules/applicants/applicants.routes.ts`, `frontend/src/features/admin/api/adminDocumentsApi.ts`, `frontend/src/features/admin/components/ApplicantDocumentsModal.tsx`, `frontend/src/features/admin/components/EvaluationRow.tsx`, `frontend/src/shared/api/apiClient.ts`, `frontend/src/shared/components/Modal.tsx`.

## 2026-08-10 — Manual, single-application PQE score entry alongside the bulk Excel import

**Context:** Client request: "add a manual adding of PQE score instead of waiting for the import of PQE Score for versatility of system." The only way to record a Pre-Qualifying Examination score was `POST /import-exam-scores` (an Excel upload matched by applicant name against a whole posting's `QUALIFIED` applicants) - correcting or entering a single applicant's score meant building a one-row spreadsheet, or waiting to batch it with others.

**Decision:** Added a single-application counterpart rather than reworking the import path: `PATCH /applications/:id/exam-score` (`{ score: number }`, integer 0–100 via `setExamScoreSchema`, ADMIN-only) → `ApplicationsService.setExaminationScore()`, which 400s unless the application is currently `QUALIFIED` (mirroring the bulk import's implicit rule - it only ever matches `QUALIFIED` applicants in the first place - made explicit here since there's no "unmatched" list to silently drop an out-of-order attempt into) → `ApplicationsRepository.setExaminationScore()` (a new single-row sibling of the existing `bulkSetExaminationScores`, returning the updated `ApplicationWithApplicant` the way `sift()`/`scheduleInterview()` already do, since a manual single-entry action can meaningfully return "the thing you just changed" where a bulk import can't). Reuses `examScoreEmail` for the same applicant notification the bulk path sends, and records a *distinct* audit action (`APPLICATION_EXAM_SCORE_SET`, not `APPLICATION_EXAM_SCORES_IMPORTED`) so the History of Logs can tell a manual entry apart from a batch import rather than conflating them under one action name. On the frontend, `EvaluationRow`'s single expand/collapse action button gained a third case (`canEnterExamScore = status === "QUALIFIED" && examinationScore === null`) - `toggleLabel()` now returns "Enter PQE Score" for this state and expanding reveals a small `field-grid` form (one number input, client-side 0–100/integer check, submit), following the exact same shape as the adjacent Sift/Schedule Interview forms rather than inventing a different interaction pattern for the third case. The static "Awaiting PQE score" hint text this replaced only described the situation with no way to act on it from the row - removed since the new button *is* the action.

**Pros:** Mirrors three already-established patterns in the same file (repository single-row methods returning the updated record, `EvaluationRow`'s single-button-reveals-a-form UX, and the "distinct audit action per real-world distinct action" convention already used for `APPLICATION_SIFTED` vs. panel actions) rather than introducing a fourth. An admin can now fix or backfill one applicant's score without touching everyone else's.

**Cons:** Two ways to set the same field (`examinationScore`) now exist with separate code paths (`setExaminationScore` vs. `importExaminationScores`/`bulkSetExaminationScores`) that both need to stay correct if the underlying rule (must be `QUALIFIED`) ever changes - a small duplication cost accepted because unifying them (e.g. routing the bulk import through repeated single-row calls) would have meant giving up the bulk path's one transaction for many single updates, and unifying the other direction (teaching the single-entry endpoint to also accept a name-matched Excel file) would have made a "manual, one at a time" feature request more complicated than asked for.

**Future impact:** If a third way to set this field is ever needed (e.g. a panel-facing entry point), `setExaminationScore()` on the service is the one place enforcing the `QUALIFIED` rule and sending the notification - route a new caller through it rather than writing directly to the repository.

Follow the new naming in Applicant My application page. So that all is aligned." **Decision:** New `frontend/src/shared/constants/applicationStatus.ts` exporting `APPLICATION_STATUS_LABELS: Record<ApplicationStatus, string>` - genuinely shared (imported by all three call sites), not the "duplicate the map per file" convention used elsewhere in this app (`DOCUMENT_TYPE_LABELS`, `SINGLE_INSTANCE_TYPES`) - those are duplicated because they mirror a *backend* enum across the workspace boundary, where cross-workspace sharing isn't set up; this is a purely-frontend, purely-display concern shared across multiple *frontend* features, the same situation `ELIGIBILITY_LABELS` (`shared/constants/eligibility.ts`) already established a precedent for, so it went in the same place rather than becoming a third duplicated copy. `EvaluationRow.tsx` and `MyApplicationsPage.tsx` (which had no label map at all before this) now index into it directly; `DashboardPage.tsx`'s existing `APPLICATION_STATUS_META` keeps its own structure (it also carries a per-status bar color the shared map has no reason to know about) but now sources each `label` field from the shared constant instead of hardcoding a fourth copy of the same six strings. **Pros:** Three inconsistent copies collapsed to one - the next status-label rename (if any) touches one file instead of needing to remember three (as this bug demonstrates happens in practice, not just in theory). `EvaluationRow`/`MyApplicationsPage` also stopped rendering a raw, underscored enum string as visible UI text, which was arguably always a rougher edge than the specific "Interview" vs. "Evaluation of Applicants" wording mismatch the client happened to notice first.

**Cons:** None significant - this is a pure consolidation with no behavior change; the only risk was a typo'd key breaking a lookup, which `Record<ApplicationStatus, string>`'s exhaustiveness check at the TypeScript level rules out (a missing or misspelled status key fails to compile rather than rendering `undefined` at runtime).

**Future impact:** Any future page that needs to show an `Application.status` as text should import `APPLICATION_STATUS_LABELS` rather than rendering the raw value or adding a fifth local copy.

## 2026-08-10 — Admin-account blue/white button hover: `<body>` class instead of an `.admin-shell` descendant selector

**Context:** Client request: "Add hover effect in all buttons across the admin account that when hovered it will become blue and text will become white. This is for consistency of all buttons in Admin Account." Buttons in the app currently hover differently per variant - `.secondary` lightens to a pale blue tint (text stays navy), `.danger` darkens to a darker red, `.accent` darkens to a darker gold, and only the plain primary button already hovers to a (darker) blue with white text. The client wants one consistent blue/white hover across every admin action button regardless of variant.

**Decision:** Scoped the new hover rule off a class on `<body>` (`admin-account`), toggled by `AdminShell` (`document.body.classList.add/remove` in a `useEffect`, added/removed on mount/unmount) - not off `.admin-shell` as a plain CSS-descendant selector, even though every admin page is wrapped in `.admin-shell`. Reason: `Modal` (and `ConfirmDialog`, which is built on it) renders via `createPortal(..., document.body)`, so a Job Management "Add Job" form, a Users Management delete confirmation, or the Evaluate Applicants "View Documents" modal all render as DOM siblings of `.admin-shell`, not descendants of it - a `.admin-shell button:hover` rule would silently miss every button inside any admin modal, which is a large fraction of the admin account's actual buttons. `AdminShell` already mounts fresh per page (each admin page component wraps itself in `<AdminShell>`, there's no single persistent layout route), so add/remove-on-mount/unmount naturally tracks "currently viewing an admin page" with no extra routing logic.

The rule itself: `body.admin-account button:not(:disabled):not(.modal-close):not(.user-menu-trigger):not(.password-toggle):hover { background: var(--color-primary); color: #fff; border-color: var(--color-primary); }`. Three exclusions were deliberate, not oversights: `.modal-close` (the dialog's "×"), `.user-menu-trigger` (header email dropdown), and `.password-toggle` (Change Password's eye icon) are icon/utility controls that already have their own established, more subtle hover treatment from earlier work this session - turning them into solid blue-white boxes would look heavy-handed and wasn't what "action buttons" means in context. `:not(:disabled)` preserves every existing `button:disabled:hover`/`button.secondary:disabled:hover` override already in the stylesheet, so a disabled button still reads as inert on hover instead of flashing blue.

**Pros:** One rule instead of four (would otherwise need `button:hover`, `button.secondary:hover`, `button.danger:hover`, `button.accent:hover` each overridden separately within the admin scope). Reaches portaled modal buttons for free, which a plain ancestor selector cannot. `:not(:disabled)` keeps disabled-button behavior exactly as it already was elsewhere in the app.

**Cons:** A `<body>`-level class is slightly more "global" than a scoped component class, and in principle a bug in the toggle logic (e.g. an early return skipping the `useEffect` cleanup) could leak the class past navigation - mitigated by using a plain mount/unmount `useEffect` with no conditional early-return, and verified live (`document.body.className` is empty again after navigating to `/login`).

**Future impact:** Any new modal/dialog opened from an admin page automatically gets the same hover treatment with no extra wiring, since it's scoped by `<body>`, not by the triggering component's subtree. If a future non-admin page ever needs the same "portal reaches document.body" scoping problem solved, this is the established pattern to reuse.

**Reference:** `frontend/src/features/admin/components/AdminShell.tsx`, `frontend/src/shared/styles/index.css`, `frontend/src/shared/components/Modal.tsx`.
