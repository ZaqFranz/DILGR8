# Project Memory

Last updated: 2026-08-08.

## Current Architecture

npm-workspaces monorepo. `backend/` = Express + TypeScript + Prisma/MySQL REST API, feature-first + Clean Architecture layering (routes → controller → service → repository), manual DI via `container.ts`. `frontend/` = React + TypeScript SPA (Vite), feature-first, JWT session in `localStorage` via `AuthContext`. Full detail: [architecture.md](./architecture.md).

## Major Components

- **Auth** (`backend/src/modules/auth`, `frontend/src/features/auth`): register/login, JWT issuance/verification, and self-service password change (`PATCH /api/auth/me/password`, `ChangePasswordPage` at `/account/password`). Registration's UI lives in the `applicant-registration` feature (see below), not `auth` — `auth` only owns the account-credentials endpoints and pages (`LoginPage`, `ChangePasswordPage`). The change-password route/nav link is role-agnostic - one `ProtectedRoute` (no `role` restriction) and one "Change Password" link in `Layout`'s header, shown for any authenticated role (`APPLICANT`/`ADMIN`/`PANEL`) rather than three separate role-specific pages, since the endpoint and form are identical regardless of role.
- **Applicants** (`backend/src/modules/applicants`, `frontend/src/features/applicant-registration`): a single continuous registration flow (`RegistrationPage`, route `/register`) covering account creation, demographic profile, work experience, L&D interventions, awards, and document uploads — no applicant data collection happens after this flow, only edits to it. `POST /api/applicants/me/complete-registration` marks it done; `ProtectedRoute`/`HomeRedirect` block every other applicant page until `Applicant.registrationCompletedAt` is set (`AuthContext.registrationComplete`). See [architecture.md § Registration gating](./architecture.md#registration-gating-frontend). Each L&D intervention and each award can have one proof file (PDF/JPEG/PNG, ≤5MB) attached directly on `LdInterventionSection`/`AwardsSection` (identical per-row upload/list/remove UI, shared `.proof-item` style) - a `Document(type=LD_PROOF, ldInterventionId=...)`/`Document(type=AWARD_PROOF, awardId=...)` tied to that specific entry, distinct from the generic applicant-level `DocumentsSection`, which isn't tied to any one claim. The file input for a given entry disappears once it has a proof, reappearing only after that proof is removed - re-uploading replaces the existing file for that entry (`DocumentsService.upload()` deletes the old row+file first) rather than accumulating multiple proofs per entry. `completeRegistration()` requires a matching proof for **every** L&D/award entry the applicant added (not just one proof somewhere) - the same rule as Eligibility Proof (required only if `hasEligibility` is declared), extended to "claiming something means proving it," 400ing with the specific entry's title if one's missing. `DocumentsSection` shows the full official application-documents checklist (Application Letter through Proof of Award(s), 11 items) with Required/Optional tags and the Application Letter's addressee block as static instructional text; only Application Letter, PDS, and PDS_EXCEL are unconditionally required to finish registration, everything else (including L&D/Award proof, conditional on having added an entry) is optional/conditional per the checklist's "if applicable"/"if any" wording. The 9 single-instance types in that generic dropdown (everything except `LD_PROOF`/`AWARD_PROOF`/`OTHER`) represent one current document per applicant, not a list - re-uploading one replaces the existing file (DB row + disk file both deleted first) instead of accumulating duplicates - see [decisions.md](./decisions.md). The PDS itself is now two separate required uploads - `PDS` (a PDF/scanned copy) and `PDS_EXCEL` (the actual CS Form 212 spreadsheet, `.xlsx`/`.xls`) - since the client needs both formats, not either/or. Every document type enforces its own allowed file types now, not just one blanket PDF/JPEG/PNG rule for everything: multer's `fileFilter` (`documents.upload.ts`) is a permissive outer gate covering the union of every type's allowed MIME types, and the authoritative per-`type` check (`assertMimeTypeAllowed()` in `documents.service.ts`, `ALLOWED_MIME_TYPES_BY_DOCUMENT_TYPE`) 400s if the file doesn't match what that specific type expects (e.g. an Excel file submitted as `PDS`, or an image submitted as `PDS_EXCEL`) - see [database.md § documents](./database.md#documents).
- **Job Postings** (`backend/src/modules/job-postings`, `frontend/src/features/job-postings`, `frontend/src/features/admin`): browse open postings (applicant); full admin CRUD (`JobManagementPage`) with computed 10-day closing date and a delete guard that blocks removing a posting with submitted applications. Each posting carries `description`, `monthlySalary`, `placeOfAssignment`, and `duties` (all free-text) alongside the four `qualification*` fields, mirroring the level of detail on typical DILG job-posting flyers; `monthlySalary` shows on the applicant-facing list card, the rest are behind the "View Details" modal (`JobPostingsListPage`) — see [database.md § job_postings](./database.md#job_postings).
- **Applications** (`backend/src/modules/applications`, folded into the `applicant-registration` frontend feature for applicants): submit an application to a posting, which moves it straight to `UNDER_SIFTING` automatically. Submission is gated on: profile exists, posting open/within window, not a duplicate, and — if the posting has any `requiredEligibilityTypes` (checkboxes on the admin Job Management form, see [database.md § job_posting_required_eligibilities](./database.md#job_posting_required_eligibilities)) — the applicant's own `hasEligibility`/`eligibilityType` actually satisfies one of them; the frontend disables "Apply" up front with the same check rather than letting the applicant find out only after clicking. Separately, any applicant who self-declared `hasEligibility` must have an `ELIGIBILITY_PROOF` document uploaded, regardless of whether the posting requires eligibility at all. Full pipeline: `SUBMITTED` → `UNDER_SIFTING` → `QUALIFIED`/`NOT_QUALIFIED` (admin Sifting decision, `PATCH .../sift`, pass/fail against the posting's qualification standards) → PQE score recorded on a Qualified application via an Excel import matched by name (`POST .../import-exam-scores`, `backend/src/modules/applications/examScoreParser.ts`) → `FOR_INTERVIEW` (`PATCH .../schedule-interview`, gated to Qualified + a recorded PQE score) → panel tabulation (below). Stops there for now - no post-interview status exists yet (Deliberation is future work, see Known Limitations). Separately, the applicant themself can withdraw their own application at any point up to `FOR_INTERVIEW` (`PATCH .../withdraw`, `MyApplicationsPage`'s "Withdraw" button + confirm dialog) - 400s if already `NOT_QUALIFIED`/`WITHDRAWN` (both terminal), 404s if the application isn't theirs. This is the only applicant-initiated status transition; every other transition above is admin/panel-initiated.
- **Admin panel** (`frontend/src/features/admin`, wrapped in `AdminShell`'s sidebar layout): role-gated section (`/admin/*`, landing page is `/admin/dashboard`) with seven sections - **Dashboard** (`backend/src/modules/dashboard`; read-only aggregate counts - applicants, job postings by status, applications by status, top job postings by application count, recent audit activity - see [api.md § Dashboard](./api.md#dashboard--apidashboard-admin-only-read-only)), **Job Management** (full CRUD), **Users Management** (`backend/src/modules/users`; full CRUD on `User` incl. admin-provisioning new admins/panelists, self-delete blocked), **Evaluate Applicants** (one table listing every application across every job posting at once, with a search-by-applicant-name/email box and a "Job title" filter dropdown - `GET /api/applications` called with no `jobPostingId` returns everything unfiltered, and tabulation is fetched per distinct posting present in the results, keyed in a `Record<jobPostingId, TabulationResult>` so Panel Avg/Rank stay correct per-posting even when rows from several postings are visible together; PQE Excel import stays gated to the Job title filter being set to one specific posting, since the import inherently targets one posting's Qualified applicants - records the Sifting pass/fail decision, imports PQE scores from an Excel file, schedules a Qualified+scored application for interview, shows the CompAss panel-score matrix once scored - see [decisions.md](./decisions.md)), **Interview Panel** (`backend/src/modules/panel-assignments`; assigns `PANEL` users to a posting's interview board), **Evaluation Criteria** (`backend/src/modules/evaluation-criteria`; admin-editable interview rubric), and **History of Logs** (`backend/src/modules/audit-logs`; read-only, deliberately no update/delete path - see decisions.md).
- **Interview Panel & Tabulation** (`backend/src/modules/panel-evaluations`, `frontend/src/features/panel`): the real multi-evaluator Evaluation phase — `PANEL`-role users see their assigned interview queue (`GET /panel-evaluations/my-queue`, `MyInterviewsPage` at `/panel/interviews`) and score each application against the active rubric; admin views the resulting ranked CompAss matrix inline on Evaluate Applicants (`GET /panel-evaluations/tabulation/:jobPostingId`). See [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation).
- **Application stage tracking & notifications** (`ApplicationStageTracker` in `frontend/src/features/applicant-registration/components/`, `backend/src/shared/email/`): `MyApplicationsPage` renders a 4-node stepper (Submitted → Sifting → Examination → Interview) per application, driven purely by `ApplicationStatus` (`QUALIFIED`/`NOT_QUALIFIED` resolve on the Sifting node itself, the same way the old terminal "Decision" node used to, since sifting is now mid-pipeline rather than final); `WITHDRAWN` bypasses the stepper for a distinct muted state, and the recorded PQE score (if any) shows as a line of text under the tracker. `ApplicationsService` emails the applicant via `EmailService` after each real status/data change it makes (submit, sift, PQE score import, schedule-interview, withdraw) - see [api.md § Applications](./api.md#applications--apiapplications-all-require-auth) for the SMTP config and dev-mode fallback. Scheduling an interview is a form, not a single click: admin supplies date/time, venue, and optionally attire/notes (`EvaluationRow`'s expanded panel on `EvaluateApplicantsPage`), all of which land in the `forInterviewEmail` the applicant receives and are shown under their own stage tracker on `MyApplicationsPage` once scheduled.

## Audit Logging

`AuditLog` records every Users/Job Postings/Evaluate/Interview-Panel write (job/user CRUD, application sift + exam-score-import + schedule-interview, criterion CRUD, panel assign/unassign, panel evaluation submit — see [patterns.md § Audit Trail](./patterns.md#audit-trail-append-only-log-via-injected-repository)). Not (yet) instrumented: applicant-side actions (profile edits, document uploads, application submission) - only admin/panel actions are logged today. If "history of logs" needs to expand to cover applicant activity too, that's a straightforward extension of the same pattern in `ApplicantsService`/`DocumentsService`, not a redesign.

## Coding Conventions

- Strict TypeScript everywhere (`strict: true`, `noUncheckedIndexedAccess` on the backend).
- Zod schemas are the single source of truth for both runtime validation and TS types (`z.infer`).
- Path alias `@/*` → `src/*` on both backend (resolved at build time via `tsc-alias`) and frontend (resolved by Vite).
- No comments explaining *what* code does; only *why*, and only when non-obvious (see repo-wide instruction in `CLAUDE.md`).

## Naming Conventions

- Backend files: `<feature>.<layer>.ts` (`applicants.service.ts`), sub-features nested in a folder (`applicants/documents/documents.service.ts`).
- Frontend: `PascalCase.tsx` for components/pages, `camelCase.ts` for api/util modules.
- Database tables: `snake_case` (via Prisma `@@map`); Prisma models: `PascalCase`.
- Git commits: Conventional Commits (`feat(...)`, `fix(...)`, etc.) — see `CLAUDE.md`.

## API Standards

REST under `/api`, JSON bodies, JWT bearer auth, uniform error shape `{ error: { code, message, details } }`. Full reference: [api.md](./api.md).

## Database Standards

MySQL, Prisma migrations (`prisma migrate dev`), UUID primary keys, cascade deletes from parent to child records, timestamps on every mutable table. Full reference: [database.md](./database.md).

## Known Limitations

- **Admin UI covers Dashboard, Job Management, Users Management, Evaluate Applicants, Interview Panel, Evaluation Criteria, and History of Logs.** There's still no screen for admins to validate Eligibility=N applicants specifically (the Sifting decision on `EvaluateApplicantsPage` covers the general pass/fail call, but doesn't surface the Eligibility=N red-flag from registration as its own checklist item). This is unrelated to (and not fixed by) the per-posting eligibility-type gate added 2026-08-08 — a posting with no `requiredEligibilityTypes` still lets an Eligibility=N applicant apply freely, exactly per the domain spec's "flagged for manual validation, not blocked" wording; only postings that explicitly require an eligibility type reject them.
- **Real SMTP is now configured in this environment** (Gmail, via an App Password in `backend/.env` - not checked into git, see `.gitignore`). Applicant stage-change emails send for real; the `[DEV EMAIL]` console-log fallback still applies automatically if `SMTP_HOST` is ever unset (e.g. in a fresh clone).
- **PQE score import matches by name only, no secondary identifier.** Two applicants with the same normalized name on the same posting would collide in the import's lookup (last-write-wins); a typo in the spreadsheet produces a silent "unmatched" row rather than a specific error. `buildNameVariants()` (`applications.service.ts`) tries several name forms per applicant (with/without middle name, middle initial, suffix) and ignores case/whitespace/periods, so a spreadsheet name doesn't have to exactly match the bare `firstName lastName` shown elsewhere in the app — but a genuinely different spelling (nickname, missing/extra name part beyond what's covered) still won't match. No pass/fail threshold is enforced on the score either (by design - it's informational, the admin decides whether to schedule an interview from it). See [decisions.md](./decisions.md#2026-08-08--siftingpqeinterview-pipeline-repurpose-the-free-standing-evaluate-action-add-an-excel-based-pqe-score-import).
- **No status past `FOR_INTERVIEW`.** The pipeline (Submitted → Sifting → Qualified → PQE score → Interview → panel tabulation) stops there - Deliberation (the RD's final decision), Compliance to Requirements, and Onboarding are all future work, not just unimplemented UI.
- **Evaluation criteria are global, not per-posting or per-battery-test.** Every interview board scores against the same rubric regardless of position, even though the domain spec frames evaluation as "per battery test/activity."
- **No admin-initiated password reset, and no "forgot password" recovery.** A logged-in user can change their own password (`PATCH /api/auth/me/password`, requires knowing the current one - see Auth above), but `PATCH /api/users/:id` still can't touch another user's password, and there's no email-based reset flow for a user who's locked out. If an applicant/admin/panelist forgets their password, an operator would have to update `passwordHash` directly in the database - there's no in-app path yet.
- **Password change doesn't invalidate other active sessions.** JWTs are stateless with no revocation mechanism (no token version/blocklist anywhere) - changing a password doesn't force other logged-in devices/tabs holding an older still-unexpired token to re-authenticate. Acceptable for now given `JWT_EXPIRES_IN` is short-lived (8h in this environment's `.env`), but worth a token-version claim if this ever needs to be airtight.
- **Audit log details aren't a diff.** `JobPostingsService.update()`/`UsersService.update()` log the entire submitted payload in `details`, not just the fields that actually changed - accurate but noisier than necessary to read (visible e.g. as a full job-posting JSON dump in History of Logs for a status-only edit).
- **No automatic job-posting close job.** `JobPosting.status` doesn't flip to `CLOSED` on a timer; `JobPostingsService.isAcceptingApplications()` checks `closingAt` at submission time as a safeguard, but a stale `OPEN` posting past its window will still *list* as open in the UI (just can't be applied to). Admins can close manually now via Job Management's edit form.
- **Local disk file storage** — not durable across redeploys, not production-ready (see [decisions.md](./decisions.md)).
- **No automated tests yet** — `vitest` is wired into both `package.json`s but no test files exist.
- **Known dependency vulnerabilities (dev-only):** `npm audit` flags Vite/Vitest/react-router at moderate–critical severity; fixes require major version bumps (Vite 5→8, Vitest 2→4, react-router-dom 6→7) that weren't attempted in this pass to avoid destabilizing a fresh scaffold. Safe to defer since these affect the dev server / build tooling, not the shipped runtime bundle, but should be revisited before any production deployment.

## Technical Debt

- `registrationComplete` (in `AuthContext`) is resolved via an extra `GET /api/applicants/me` call on session restore/login rather than being embedded in the JWT — simpler (no token-reissue-on-status-change problem) but costs one small round trip per session start. See [decisions.md](./decisions.md#2026-08-08--registration-unified-into-one-flow-applicant-pages-gated-on-registrationcompletedat).
- Frontend `types.ts` files duplicate backend DTO shapes by hand; no generated client (e.g. OpenAPI/tRPC) keeping them in sync.
- `ApplicantsRepository`/`ApplicationsRepository` etc. return Prisma's generated types directly rather than mapped domain models — acceptable at this scale, but if domain logic grows more complex than "check field, throw AppError," consider introducing real domain model classes distinct from Prisma's row types.
- `PATCH /api/applications/:id/sift` is a one-shot decision, not versioned — no evaluator-history table, just the single `siftedAt`/`siftedByUserId`/`siftingRemarks` overwrite target on `Application` (gated to `UNDER_SIFTING` so it can't be re-run after the fact, unlike the free-standing "evaluate" action it replaced — see [decisions.md](./decisions.md#2026-08-08--siftingpqeinterview-pipeline-repurpose-the-free-standing-evaluate-action-add-an-excel-based-pqe-score-import)).
- `PATCH /api/panel-evaluations/:applicationId` has the same overwrite-not-version behavior for a panelist's own scores - re-submitting replaces the prior score/remarks with no history kept.

1. **Admin console**: manual eligibility validation queue (surfacing the `eligibilityValidated`/Eligibility=N red-flag from the spec); admin-initiated password reset.
2. ~~**Sifting**~~ — done 2026-08-08: applications move to `UNDER_SIFTING` automatically on submit; admin records a Qualified/Not-Qualified pass/fail decision against the posting's QS on `EvaluateApplicantsPage`, with an email sent either way. Still missing: an *automatic* check against the QS fields (today it's an admin judgment call, not a system comparison) and bulk letter-sending (each decision emails one applicant at a time).
3. **PQE**: score recording done 2026-08-08 (Excel import matched by applicant name, feeds `Application.examinationScore`, applicant notified regardless of score). Still missing: batch scheduling (AM/PM/max 60 applicants) and a dedicated schedule-notification letter (today the only PQE-related email is the score-recorded one).
4. ~~**Evaluation (full)**~~ — done 2026-08-08: multi-evaluator `PanelEvaluation`/`PanelScore` model, `PANEL`-role board access to a rubric of admin-editable `EvaluationCriterion` rows, feeding CompAss. See [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation).
5. **Tabulation / CompAss**: ranked matrix generation ✅ (see above); still missing: shortlisting at the 1:5 ratio, regret/shortlist letters, PSL and QME.
6. **Deliberation, Compliance to Requirements, Onboarding**: per the spec's step-by-step process.
7. **Learning & Development / PDC modules**: POMS ranking, L&D plans, permit-to-study workflow.
