# Project Memory

Last updated: 2026-08-13 (full-system audit round 2: fixed HTML injection in outbound emails and a missing role check on Positions' panel members - see CHANGELOG for detail).

## Current Architecture

npm-workspaces monorepo. `backend/` = Express + TypeScript + Prisma/MySQL REST API, feature-first + Clean Architecture layering (routes → controller → service → repository), manual DI via `container.ts`. `frontend/` = React + TypeScript SPA (Vite), feature-first, JWT session in `localStorage` via `AuthContext`. Full detail: [architecture.md](./architecture.md).

## Major Components

- **Auth** (`backend/src/modules/auth`, `frontend/src/features/auth`): register/login, JWT issuance/verification, self-service password change (`PATCH /api/auth/me/password`, `ChangePasswordPage` at `/account/password`), and applicant forgot-password (`POST /api/auth/forgot-password`, `ForgotPasswordPage` at `/forgot-password`, linked from `LoginPage`). Registration's UI lives in the `applicant-registration` feature (see below), not `auth` — `auth` only owns the account-credentials endpoints and pages (`LoginPage`, `ForgotPasswordPage`, `ChangePasswordPage`). The change-password route/nav link is role-agnostic - one `ProtectedRoute` (no `role` restriction) rather than three separate role-specific pages, since the endpoint and form are identical regardless of role. "Change Password" and "Log out" live together in `Layout`'s `.user-menu` dropdown (trigger = the user's email), shown for any authenticated role (`APPLICANT`/`ADMIN`/`PANEL`) - previously two separate always-visible header items. `ChangePasswordPage` itself is centered (`.centered-page`, a small reusable class for any single-focused-card page rather than a list/table) and its three password fields use the new shared `PasswordInput` (`frontend/src/shared/components/PasswordInput.tsx`) - a plain `<input type="password">` plus a trailing eye-icon toggle to reveal/hide the value, since there was previously no way to check what you'd typed short of retyping it. `PasswordInput` isn't wired into `LoginPage`/`RegistrationPage`'s account-creation password field yet (only requested for Change Password) but is a drop-in replacement wherever a masked password field is used. **Forgot password** issues a random temporary password by email to an `APPLICANT` account (silent no-op for unknown emails or `ADMIN`/`PANEL` accounts) and sets `User.mustChangePassword`, which `ProtectedRoute`/`HomeRedirect` use to force a redirect to `ChangePasswordPage` before anything else is reachable, regardless of role, until a real password is set - see [architecture.md § Forgot password (applicants)](./architecture.md#forgot-password-applicants) and [decisions.md](./decisions.md)'s 2026-08-12 "Forgot password (applicants)" entry. **Every new-password field** (`register`'s `password`, `me/password`'s `newPassword`, admin-provisioned `POST /api/users`'s `password`) is validated against a shared `passwordPolicySchema` (`backend/src/shared/utils/password.ts`) - 8-72 characters, one lowercase/uppercase/digit/special character each, and rejection of a small common-password blocklist - mirrored on the frontend (`validatePassword()`, `frontend/src/shared/utils/passwordPolicy.ts`) for inline feedback; `generateTemporaryPassword()` guarantees it satisfies the same policy. See [decisions.md](./decisions.md)'s 2026-08-12 "Password complexity" entry.
- **Applicants** (`backend/src/modules/applicants`, `frontend/src/features/applicant-registration`): a single continuous registration flow (`RegistrationPage`, route `/register`) covering account creation, demographic profile, work experience, L&D interventions, awards, and document uploads — no applicant data collection happens after this flow, only edits to it, with one exception: the Application Letter, collected at apply time instead (see `job-postings`/`applications` below), since it's addressed to a specific vacancy rather than something to capture once up front. `POST /api/applicants/me/complete-registration` marks registration done; `ProtectedRoute`/`HomeRedirect` block every other applicant page until `Applicant.registrationCompletedAt` is set (`AuthContext.registrationComplete`). See [architecture.md § Registration gating](./architecture.md#registration-gating-frontend). Each L&D intervention and each award can have one proof file (PDF/JPEG/PNG, ≤5MB) attached directly on `LdInterventionSection`/`AwardsSection` (identical per-row upload/list/remove UI, shared `.proof-item` style) - a `Document(type=LD_PROOF, ldInterventionId=...)`/`Document(type=AWARD_PROOF, awardId=...)` tied to that specific entry, distinct from the generic applicant-level `DocumentsSection`, which isn't tied to any one claim. The file input for a given entry disappears once it has a proof, reappearing only after that proof is removed - re-uploading replaces the existing file for that entry (`DocumentsService.upload()` deletes the old row+file first) rather than accumulating multiple proofs per entry. `completeRegistration()` requires a matching proof for **every** L&D/award entry the applicant added (not just one proof somewhere) - the same rule as Eligibility Proof (required only if `hasEligibility` is declared), extended to "claiming something means proving it," 400ing with the specific entry's title if one's missing. `RegistrationPage`'s "Next" button is disabled on the Learning & Development / Awards steps themselves (not just the final "Finish registration" button) while any entry on that step lacks proof, with the same per-entry warning shown inline - frontend-only, reusing the same `ldEntriesMissingProof`/`awardsMissingProof` arrays the end-of-wizard gate already computed. `DocumentsSection` shows the rest of the official application-documents checklist (PDS through Proof of Award(s), 10 items - Application Letter isn't listed here, see below) with Required/Optional tags; only PDS and PDS_EXCEL are unconditionally required to finish registration, everything else (including L&D/Award proof, conditional on having added an entry) is optional/conditional per the checklist's "if applicable"/"if any" wording. The 8 single-instance types in that generic dropdown (everything except `LD_PROOF`/`AWARD_PROOF`/`APPLICATION_LETTER`/`OTHER`) represent one current document per applicant, not a list - re-uploading one replaces the existing file (DB row + disk file both deleted first) instead of accumulating duplicates - see [decisions.md](./decisions.md). The PDS itself is now two separate required uploads - `PDS` (a PDF/scanned copy) and `PDS_EXCEL` (the actual CS Form 212 spreadsheet, `.xlsx`/`.xls`) - since the client needs both formats, not either/or. Every document type enforces its own allowed file types now, not just one blanket PDF/JPEG/PNG rule for everything: multer's `fileFilter` (`documents.upload.ts`) is a permissive outer gate covering the union of every type's allowed MIME types, and the authoritative per-`type` check (`assertMimeTypeAllowed()` in `documents.service.ts`, `ALLOWED_MIME_TYPES_BY_DOCUMENT_TYPE`) 400s if the file doesn't match what that specific type expects (e.g. an Excel file submitted as `PDS`, or an image submitted as `PDS_EXCEL`) - see [database.md § documents](./database.md#documents).
- **Job Postings** (`backend/src/modules/job-postings`, `frontend/src/features/job-postings`, `frontend/src/features/admin`): browse open postings (applicant); full admin CRUD (`JobManagementPage`) with computed 10-day closing date and a delete guard that blocks removing a posting with submitted applications. Each posting is modeled on the official DILG job-posting document's fields rather than an app-invented shape: `description`, `numberOfVacantPositions`, `plantillaNumbers`, `salaryGrade`, `monthlySalary`, `placeOfAssignment`, `positionNextInRank`, and `duties` alongside the four `qualification*` fields; `salaryGrade`/`monthlySalary` show on the applicant-facing list card, the rest are behind the "View Details" modal (`JobPostingsListPage`). There is no "position level" (Entry/Promotional) field - it was removed per client request since nothing branched on it and it isn't part of the official document; see [decisions.md](./decisions.md) and [database.md § job_postings](./database.md#job_postings). **`salaryGrade` is the one field that isn't free text** - a closed `"1"`-`"33"` set (`SALARY_GRADE_MONTHLY_SALARY`, `backend/src/shared/constants/salaryGrades.ts` + a frontend mirror for live preview only) that drives `monthlySalary`: the admin picks a grade from a `<select>`, and `JobPostingsService` computes/overwrites the formatted `monthlySalary` string server-side from the official DBM Salary Grade schedule on every create/update - it's no longer part of either input DTO at all. See [decisions.md](./decisions.md)'s 2026-08-12 "Fixed Monthly Salary derived from Salary Grade" entry, including a real crash (and fix) caught in-session when a legacy posting's non-numeric placeholder `salaryGrade` hit the lookup.
- **Applications** (`backend/src/modules/applications`, folded into the `applicant-registration` frontend feature for applicants): submit an application to a posting, which moves it straight to `UNDER_SIFTING` automatically. `POST /api/applications` is `multipart/form-data` (`jobPostingId` + `file`) - the `file` is the Application Letter, required to apply (400 without one) since it's addressed to that specific vacancy; `JobPostingsListPage`'s "Apply" button opens a small modal (file input + the addressee/thru block as instructional text, mirroring what used to be shown in the registration Documents step) rather than submitting on click. `ApplicationsRepository.createWithApplicationLetter()` creates the `Application` and its `Document(type=APPLICATION_LETTER, applicationId=...)` in one `$transaction`, so the two can't end up out of sync. `JobPostingsListPage` also fetches `listMyApplications()` on load and disables/relabels "Apply" to "Already Applied" for any posting already in that list (updated locally the instant a new application succeeds, no refetch needed) - client-side UX only, the backend's 409 on a duplicate `(applicantId, jobPostingId)` pair remains the real guard. Submission is otherwise gated on: profile exists, posting open/within window, not a duplicate, and — if the posting has any `requiredEligibilityTypes` (checkboxes on the admin Job Management form, see [database.md § job_posting_required_eligibilities](./database.md#job_posting_required_eligibilities)) — the applicant's own `hasEligibility`/`eligibilityType` actually satisfies one of them; the frontend disables "Apply" up front with the same check rather than letting the applicant find out only after clicking. Separately, any applicant who self-declared `hasEligibility` must have an `ELIGIBILITY_PROOF` document uploaded, regardless of whether the posting requires eligibility at all. Full pipeline: `SUBMITTED` → `UNDER_SIFTING` → `QUALIFIED`/`NOT_QUALIFIED` (admin Sifting decision, `PATCH .../sift`, pass/fail against the posting's qualification standards) → PQE score recorded on a Qualified application via an Excel import matched by name (`POST .../import-exam-scores`, `backend/src/modules/applications/examScoreParser.ts`) → `FOR_INTERVIEW` (`PATCH .../schedule-interview`, gated to Qualified + a recorded PQE score) → panel tabulation (below). Stops there for now - no post-interview status exists yet (Deliberation is future work, see Known Limitations). Separately, the applicant themself can withdraw their own application at any point up to `FOR_INTERVIEW` (`PATCH .../withdraw`, `MyApplicationsPage`'s "Withdraw" button + confirm dialog) - 400s if already `NOT_QUALIFIED`/`WITHDRAWN` (both terminal), 404s if the application isn't theirs. This is the only applicant-initiated status transition; every other transition above is admin/panel-initiated.
- **Admin panel** (`frontend/src/features/admin`, wrapped in `AdminShell`'s sidebar layout): role-gated section (`/admin/*`, landing page is `/admin/dashboard`). Every button anywhere in the admin account (inline table actions, modal/dialog buttons, "Add"/"Save"/"Cancel", etc.) hovers to the same blue background + white text regardless of its variant (primary/secondary/danger/accent) - `AdminShell` toggles an `admin-account` class on `document.body` for as long as an admin page is mounted, and `index.css` scopes the hover rule off that body class rather than `.admin-shell` so it still reaches `Modal`/`ConfirmDialog` buttons (portaled to `document.body`, outside `.admin-shell` in the DOM). Excluded: disabled buttons, and the modal close "×"/header user-menu trigger/password show-hide toggle (icon controls with their own existing hover style) - see [decisions.md](./decisions.md). Eight sections - **Dashboard** (`backend/src/modules/dashboard`; read-only aggregate counts - applicants, job postings by status, applications by status, top job postings by application count, recent audit activity - see [api.md § Dashboard](./api.md#dashboard--apidashboard-admin-only-read-only); the hero row also has a "User Manual" link beside "Refresh" that opens the published User Manual artifact in a new tab - a plain `<a href>`, no backend involvement, styled to match the buttons via generalized `button`/`a.button` CSS selectors rather than a duplicated style), **Job Management** (full CRUD), **Users Management** (`backend/src/modules/users`; full CRUD on `User` incl. admin-provisioning new admins/panelists, self-delete blocked, plus a per-row "Reset Password" action - `POST /:id/reset-password` - that emails any user a fresh temporary password via the same `generateTemporaryPassword()`/`temporaryPasswordEmail()` the applicant self-service forgot-password flow uses), **Evaluate Applicants** (one table listing every application across every job posting at once, with a search-by-applicant-name/email box and a "Job title" filter dropdown - `GET /api/applications` called with no `jobPostingId` returns everything unfiltered, and tabulation is fetched per distinct posting present in the results, keyed in a `Record<jobPostingId, TabulationResult>` so Panel Avg/Rank stay correct per-posting even when rows from several postings are visible together; PQE Excel import stays gated to the Job title filter being set to one specific posting, since the import inherently targets one posting's Qualified applicants - records the Sifting pass/fail decision, records PQE scores either via Excel import or one at a time (`PATCH /:id/exam-score`, the row's "Enter PQE Score" action - both require `QUALIFIED` status and send the same `examScoreEmail`, logged under distinct audit actions), schedules a Qualified+scored application for interview, shows the CompAss panel-score matrix once scored, and a per-row "View Documents" button opens a modal listing that specific applicant's uploaded documents with a "View"/"Download" action per file (`GET /api/applicants/:id/documents` + `GET /api/applicants/documents/:id/file`, both ADMIN-only - the app's first file-serving endpoint, since documents were write-only from the API before this); each row's action buttons ("View Documents" + the stage-dependent details button) render at a uniform width via the opt-in `.data-table-actions--uniform` CSS modifier, scoped to this table only - see [decisions.md](./decisions.md). The stage-dependent button ("Sift"/"Enter PQE Score"/"Evaluate Applicant"/"Schedule Oath-Taking"/"Details") opens a `wide` `Modal` rather than expanding the row in place - status history, panel scores, and whichever action form applies all render inside it, titled `"<action> — <applicant name>"`, closed via the modal's own Escape/click-outside/×/footer "Close" instead of a "Cancel" toggle), **Interview Panel** (`backend/src/modules/panel-assignments`; assigns `PANEL` users to a posting's interview board — `PanelAssignmentsPage` supports selecting multiple applicant rows via checkboxes (page-level "select all" plus a "select all N matching filters" shortcut) and assigning a panel to all of them in one `POST .../bulk` call, add-only across however many distinct postings the selection spans - see [decisions.md](./decisions.md)'s 2026-08-11 "Bulk panel assignment" entry), **Evaluation Criteria** (`backend/src/modules/evaluation-criteria`; admin-editable interview rubric, plus an "Applicant Scores" button opening a modal ranking every scored Evaluation-phase applicant, across all job postings, by average score per criterion or overall total - `GET /panel-evaluations/applicant-scores`, ranking done client-side since which column to rank by is an interactive choice - see [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation)), **Compliance Requirements** (`backend/src/modules/compliance-requirements`; admin CRUD on the global CSC-mandated documentary checklist catalog - see the Compliance to Requirements & Oath-Taking bullet above), and **History of Logs** (`backend/src/modules/audit-logs`; read-only, deliberately no update/delete path - see decisions.md).
- **Interview Panel & Tabulation** (`backend/src/modules/panel-evaluations`, `frontend/src/features/panel`): the real multi-evaluator Evaluation phase — `PANEL`-role users see their assigned interview queue (`GET /panel-evaluations/my-queue`, `MyInterviewsPage` at `/panel/interviews`) and score each application against the active rubric; admin views the resulting ranked CompAss matrix inline on Evaluate Applicants (`GET /panel-evaluations/tabulation/:jobPostingId`). See [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation). `MyInterviewsPage` also has two collapsible reference cards (frontend-only, no new endpoints): `CriteriaReferencePanel` (every active criterion + its guiding questions, ahead of/during scoring) and `ScoreSummaryPanel` (a panelist's own scored applications, self-scores only — never another panelist's marks or the cross-panel average, which stays ADMIN-only via tabulation). Panelists can also view an assigned applicant's PDS (`InterviewRow`'s "View PDS" button, reusing the admin `ApplicantDocumentsModal` as-is): `GET /applicants/:id/documents`/`GET /applicants/documents/:id/file` are now `requireRole("ADMIN", "PANEL")`, and `DocumentsService` takes a `viewer: { id, role }` param that, for `PANEL`, filters to `PDS`/`PDS_EXCEL` and 403s unless `PanelAssignmentsRepository.isPanelUserAssignedToApplicant()` confirms the panelist is currently assigned to interview that applicant. See [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation) and [decisions.md](./decisions.md)'s 2026-08-11 entry.
- **Application stage tracking & notifications** (`ApplicationStageTracker` in `frontend/src/features/applicant-registration/components/`, `backend/src/shared/email/`): `MyApplicationsPage` renders a 7-node stepper (Submitted → Sifting → Examination → Interview → Compliance to Requirements → Oath-Taking → Hired) per application, driven purely by `ApplicationStatus` - each of Sifting/Evaluation/Compliance can resolve in place as a rejection (`NOT_QUALIFIED`/`NOT_SELECTED`/`DISQUALIFIED` respectively, via a `REJECTION_STATUS_BY_STAGE` lookup) instead of only Sifting being able to; `WITHDRAWN` bypasses the stepper for a distinct muted state, and the recorded PQE score (if any) shows as a line of text under the tracker. `ApplicationsService` emails the applicant via `EmailService` after each real status/data change it makes (submit, sift, PQE score import, schedule-interview, withdraw, move-to-compliance, not-selected, disqualify, schedule-oath-taking, hire) - see [api.md § Applications](./api.md#applications--apiapplications-all-require-auth) for the SMTP config and dev-mode fallback. Every dynamic value interpolated into an email template (`backend/src/shared/email/applicationEmailTemplates.ts`/`authEmailTemplates.ts`) is passed through `escapeHtml()` (`backend/src/shared/utils/escapeHtml.ts`) first - these are hand-built HTML strings with no auto-escaping the way React gives the frontend for free, and `applicantName` in particular is fully free-text (no character restriction in `applicants.dto.ts`), so this was a real HTML-injection gap until the 2026-08-13 audit closed it. Scheduling an interview (or oath-taking) is a form, not a single click: admin supplies date/time, venue, and optionally attire/notes (`EvaluationRow`'s details modal on `EvaluateApplicantsPage`), all of which land in the notification email the applicant receives and are shown under their own stage tracker on `MyApplicationsPage` once scheduled. Every `ApplicationStatus` badge/label across the app (Evaluate Applicants table, `MyApplicationsPage`, Dashboard's status chart) reads from one shared `APPLICATION_STATUS_LABELS` map (`frontend/src/shared/constants/applicationStatus.ts`, `Record<ApplicationStatus, string>`) rather than each screen rendering/hardcoding its own copy - `FOR_INTERVIEW` displays as "Evaluation of Applicants" everywhere, fixing a prior three-way naming drift (raw enum text in two places, a fourth hardcoded string in a third) - see [decisions.md](./decisions.md).
- **Compliance to Requirements & Oath-Taking** (`backend/src/modules/compliance-requirements/`, `EvaluationRow`'s new actions, `ComplianceReviewModal`, `ComplianceChecklistSection`): continues the pipeline past `FOR_INTERVIEW` with no separate "Deliberation" status - `PATCH /applications/:id/move-to-compliance` (admin) *is* the RD's decision, snapshotting one `PENDING` `ApplicationComplianceItem` per currently-active, admin-managed `ComplianceRequirement` (global catalog, CRUD at `/api/compliance-requirements`, new "Compliance Requirements" admin nav section). The applicant uploads a `Document(type=COMPLIANCE_PROOF)` per item (`ComplianceChecklistSection` on `MyApplicationsPage`, same per-entry-proof pattern as `LD_PROOF`/`AWARD_PROOF`); admin reviews each in `ComplianceReviewModal` (`EvaluationRow`'s "Manage Compliance" button) - verifying/rejecting requires a proof to already exist. Once every item is `VERIFIED`, "Schedule Oath-Taking" bundles the `FOR_COMPLIANCE` → `FOR_OATH_TAKING` transition with the ceremony's date/venue/notes (mirrors `scheduleInterview`'s shape); "Mark Hired" is the final `FOR_OATH_TAKING` → `HIRED` transition, terminal for this pipeline segment. See [architecture.md § Compliance to Requirements & Oath-Taking](./architecture.md#compliance-to-requirements--oath-taking) and [decisions.md](./decisions.md)'s 2026-08-11 entry.
- **Regret letters** (`ApplicationsService.rejectAfterInterview()`/`rejectAfterCompliance()`, `EvaluationRow`'s "Not Selected"/"Disqualify" buttons): fills the gap where `FOR_INTERVIEW` and `FOR_COMPLIANCE` previously had no rejection exit at all, only a forward one - `PATCH /applications/:id/not-selected` (`FOR_INTERVIEW` → `NOT_SELECTED`) and `PATCH /applications/:id/disqualify` (`FOR_COMPLIANCE` → `DISQUALIFIED`, no "all items verified" precondition) each stamp shared `rejectedAt`/`rejectionRemarks` columns and send `regretEmail()` - the same template `sift`'s `NOT_QUALIFIED` branch uses, worded per stage, wrapped in a `ConfirmDialog` with an optional remarks textarea (`EvaluationRow.tsx`). See [architecture.md § Regret letters](./architecture.md#regret-letters-rejection-past-sifting) and [decisions.md](./decisions.md)'s 2026-08-12 entry for why these are separate statuses from `NOT_QUALIFIED` rather than a reused one.
- **Marketing** (`frontend/src/features/marketing`, no backend): a public, applicant-only, interactive `LandingPage` at `/`, replacing what used to be an unconditional redirect to `/login` for unauthenticated visitors (`HomeRedirect` in `App.tsx` renders it directly instead of `<Navigate to="/login">`; an authenticated visitor's existing role/must-change-password/incomplete-registration redirect chain is untouched). `Layout`'s full-bleed/no-default-header treatment (previously just `/login` and unauthenticated `/register`) also covers unauthenticated `/`. No admin/panel content - the page speaks only to a prospective applicant. Three interactive, real-data-backed pieces, not static copy: **open positions**, fetched live via the job-postings module's public unauthenticated `GET /` (`listJobPostings("OPEN")`), each an accordion card (collapsed summary → full qualification standards + "Register to apply" on expand, a "Closes in Nd" flag computed from the real `closingAt`) - capped at 10 visible (`POSITIONS_PAGE_SIZE`) with a "More (N remaining)" button revealing the rest of the already-in-memory list, shown only when the live count exceeds it; an **interactive pipeline** - clickable tabs over `ApplicationStageTracker`'s six real `STAGE_ORDER` stages (not the domain-spec's more abstract phase list, which has a "Deliberation" phase that isn't an actual tracked status - see Known Limitations), each revealing a short applicant-facing blurb on selection; and an **FAQ accordion** answered from what's actually implemented (the security answer references the real password-complexity policy and per-application document-access scoping, not generic reassurance). New `Reveal` component (`features/marketing/components/Reveal.tsx`) fades sections in on first scroll-into-view via `IntersectionObserver`, one-way (disconnects after firing), no-op under `prefers-reduced-motion`.

## Audit Logging

`AuditLog` records every Users/Job Postings/Evaluate/Interview-Panel write (job/user CRUD, application sift + exam-score-import + schedule-interview, criterion CRUD, panel assign/unassign, panel evaluation submit — see [patterns.md § Audit Trail](./patterns.md#audit-trail-append-only-log-via-injected-repository)). Not (yet) instrumented: applicant-side actions (profile edits, document uploads, application submission) - only admin/panel actions are logged today. If "history of logs" needs to expand to cover applicant activity too, that's a straightforward extension of the same pattern in `ApplicantsService`/`DocumentsService`, not a redesign.

## Coding Conventions

- Strict TypeScript everywhere (`strict: true`, `noUncheckedIndexedAccess` on the backend).
- Zod schemas are the single source of truth for both runtime validation and TS types (`z.infer`).
- Path alias `@/*` → `src/*` on both backend (resolved at build time via `tsc-alias`) and frontend (resolved by Vite).
- No comments explaining *what* code does; only *why*, and only when non-obvious (see repo-wide instruction in `CLAUDE.md`).
- Every page-level/section "data is loading" state renders the shared `LoadingBlock` (`{loading && <LoadingBlock />}` or an early `if (loading) return <LoadingBlock .../>`) - it's a fixed full-viewport overlay with a centered spinner over a blurred backdrop (`.loading-block` in `index.css`), not an inline row, so this is consistent everywhere it's used. Small in-progress indicators tied to one specific action (a per-row file upload, a submit button's spinner) stay as a bare `<Spinner size="sm" />` inline next to that control - only page/section-level loading gets the full-screen treatment.

## Naming Conventions

- Backend files: `<feature>.<layer>.ts` (`applicants.service.ts`), sub-features nested in a folder (`applicants/documents/documents.service.ts`).
- Frontend: `PascalCase.tsx` for components/pages, `camelCase.ts` for api/util modules.
- Database tables: `snake_case` (via Prisma `@@map`); Prisma models: `PascalCase`.
- Git commits: Conventional Commits (`feat(...)`, `fix(...)`, etc.) — see `CLAUDE.md`.

## API Standards

REST under `/api`, JSON bodies, JWT bearer auth, uniform error shape `{ error: { code, message, details } }`. Full reference: [api.md](./api.md).

## Database Standards

MySQL, Prisma migrations (`prisma migrate dev`), UUID primary keys, cascade deletes from parent to child records, timestamps on every mutable table. Full reference: [database.md](./database.md).

## Known Limitations

- **Admin UI covers Dashboard, Job Management, Users Management, Evaluate Applicants, Interview Panel, Evaluation Criteria, and History of Logs.** There's still no screen for admins to validate Eligibility=N applicants specifically (the Sifting decision on `EvaluateApplicantsPage` covers the general pass/fail call, but doesn't surface the Eligibility=N red-flag from registration as its own checklist item). This is unrelated to (and not fixed by) the per-posting eligibility-type gate added 2026-08-08 — a posting with no `requiredEligibilityTypes` still lets an Eligibility=N applicant apply freely, exactly per the domain spec's "flagged for manual validation, not blocked" wording; only postings that explicitly require an eligibility type reject them.
- **Real SMTP is now configured in this environment** (Gmail, via an App Password in `backend/.env` - not checked into git, see `.gitignore`). Applicant stage-change emails send for real; the `[DEV EMAIL]` console-log fallback still applies automatically if `SMTP_HOST` is ever unset (e.g. in a fresh clone).
- **PQE score import matches by name only, no secondary identifier.** Two applicants with the same normalized name on the same posting would collide in the import's lookup (last-write-wins); a typo in the spreadsheet produces a silent "unmatched" row rather than a specific error. `buildNameVariants()` (`applications.service.ts`) tries several name forms per applicant (with/without middle name, middle initial, suffix) and ignores case/whitespace/periods, so a spreadsheet name doesn't have to exactly match the bare `firstName lastName` shown elsewhere in the app — but a genuinely different spelling (nickname, missing/extra name part beyond what's covered) still won't match. No pass/fail threshold is enforced on the score either (by design - it's informational, the admin decides whether to schedule an interview from it). See [decisions.md](./decisions.md#2026-08-08--siftingpqeinterview-pipeline-repurpose-the-free-standing-evaluate-action-add-an-excel-based-pqe-score-import).
- **Deliberation isn't a tracked status.** The pipeline now runs Submitted → Sifting → Qualified → PQE score → Interview → panel tabulation → Compliance to Requirements → Oath-Taking → Hired, but there's no distinct "Deliberation" state between Evaluation and Compliance - the RD's decision to advance an applicant is the single `move-to-compliance` admin action, same as every other transition (see [decisions.md](./decisions.md)'s 2026-08-11 entry). Onboarding (videos, pre/post evaluations) past `HIRED` is still future work, not just unimplemented UI.
- **A compliance requirement added to the catalog after an applicant is already `FOR_COMPLIANCE` won't retroactively appear on their checklist** - `moveToCompliance()` snapshots the active catalog once, at the moment of transition (see [decisions.md](./decisions.md)). Not engineered around; an admin who needs to add a requirement mid-review handles it manually outside the system for already-in-progress applicants.
- **`EvaluationRow`'s sifting-decision summary text is wrong for any application that has progressed past `QUALIFIED`.** It renders `application.status === "QUALIFIED" ? "Qualified" : "Not qualified"` to describe the *original* sifting decision, but `Application` has one `status` column that later transitions overwrite - so a `Qualified`-then-scheduled-then-interviewed-then-`FOR_COMPLIANCE` applicant's sift summary now reads "Not qualified" (wrong) instead of "Qualified" (correct). Pre-existing since `scheduleInterview` first introduced a post-sift status (not introduced by the Compliance/Oath-Taking work, just made more visible now that more downstream statuses exist) - there's no separate stored sift-decision field to read instead. Fix would be either a dedicated `siftDecision` column or deriving the display from `siftedAt !== null` plus whether the application ever reached `NOT_QUALIFIED`.
- **Evaluation criteria are global, not per-posting or per-battery-test.** Every interview board scores against the same rubric regardless of position, even though the domain spec frames evaluation as "per battery test/activity."
- **"Exercise" isn't a defined term anywhere in `docs/rsp-domain-spec.md`.** When asked for a "criteria per exercise" reference panel for panelists, this was interpreted as "the rubric for this evaluation session" — i.e. the existing flat `EvaluationCriterion` list (`CriteriaReferencePanel`, 2026-08-11) — since there's no multi-exercise structure (e.g. separate Situational/Technical rounds) in the schema or spec to key off instead. Revisit this interpretation if a genuine multi-exercise/multi-battery-test structure is ever requested; it would need `EvaluationCriterion` to gain an exercise/category grouping, not just a reference-panel change.
- ~~**No admin-initiated password reset.**~~ — done 2026-08-13: `POST /api/users/:id/reset-password` (`UsersService.resetPassword()`) lets an admin issue a fresh temporary password to any user (not just `ADMIN`/`PANEL` - no reason to exclude `APPLICANT`), reusing `generateTemporaryPassword()`/`temporaryPasswordEmail()` from the forgot-password flow. `UsersManagementPage` gained a "Reset Password" button per row (`ConfirmDialog`, non-danger styling since it's not destructive).
- **Password change doesn't invalidate other active sessions.** JWTs are stateless with no revocation mechanism (no token version/blocklist anywhere) - changing a password doesn't force other logged-in devices/tabs holding an older still-unexpired token to re-authenticate. Acceptable for now given `JWT_EXPIRES_IN` is short-lived (8h in this environment's `.env`), but worth a token-version claim if this ever needs to be airtight.
- **Audit log details aren't a diff.** `JobPostingsService.update()`/`UsersService.update()` log the entire submitted payload in `details`, not just the fields that actually changed - accurate but noisier than necessary to read (visible e.g. as a full job-posting JSON dump in History of Logs for a status-only edit).
- **No automatic job-posting close job.** `JobPosting.status` doesn't flip to `CLOSED` on a timer; `JobPostingsService.isAcceptingApplications()` checks `closingAt` at submission time as a safeguard, but a stale `OPEN` posting past its window will still *list* as open in the UI (just can't be applied to). Admins can close manually now via Job Management's edit form.
- **The Salary Grade schedule needs a manual data update each time DBM issues a new tranche.** `SALARY_GRADE_MONTHLY_SALARY` (`backend/src/shared/constants/salaryGrades.ts` + a frontend mirror) currently holds EO 64/SSL VI's Third Tranche (effective January 1, 2026); a Fourth Tranche is already scheduled for January 2027. Updating it is a one-line-per-grade data edit, not a redesign, but nothing in the app reminds an admin to do it - the schedule will silently go stale otherwise. 3 pre-existing postings from before this feature still carry a non-numeric `salaryGrade` placeholder ("Not yet specified") left over from an earlier migration backfill; they can't be saved again until an admin picks a real grade (by design, not a bug - see [decisions.md](./decisions.md)'s 2026-08-12 entry).
- **Local disk file storage** — not durable across redeploys, not production-ready (see [decisions.md](./decisions.md)).
- **Minimal automated test coverage.** `vitest` is wired into both `package.json`s; as of the 2026-08-12 full-system audit there are exactly two test files (`backend/src/modules/panel-evaluations/panel-evaluations.service.test.ts`, `frontend/src/features/admin/components/ApplicantScoresModal.test.ts`), covering only the CompAss competition-ranking logic that audit fixed. Everything else (services, repositories, components, routes) still has zero coverage - a real gap for a system this size, deliberately not closed wholesale in one pass. The audit also found and fixed a prerequisite bug: `backend/` had no `vitest.config.ts`, so the `@/*` alias every backend file imports through was unresolvable by the test runner - no backend test could have run at all before that fix (`vitest.config.ts` now mirrors `tsconfig.json`'s `paths` via `resolve.alias`).
- **No rate limiting anywhere** (`/api/auth/login`, `/api/auth/forgot-password` in particular) - noted during the 2026-08-12 full-system audit but not added, since it's a new dependency/middleware decision rather than a same-shape fix. Login is brute-forceable at whatever rate the network allows (mitigated somewhat by bcrypt's own cost factor, not by anything server-side); forgot-password can be spammed to flood an arbitrary applicant's inbox with temporary-password emails. Worth adding (`express-rate-limit` is the natural fit, no new architecture needed) before any real deployment.
- **`jwt.verify()` doesn't pin `algorithms: ["HS256"]` explicitly** - noted during the same audit, defense-in-depth only. Not currently exploitable (one symmetric `JWT_SECRET`, no RS256 keypair anywhere for an algorithm-confusion attack to target), but cheap to tighten.
- **Known dependency vulnerabilities (dev-only):** `npm audit` flags Vite/Vitest/react-router at moderate–critical severity; fixes require major version bumps (Vite 5→8, Vitest 2→4, react-router-dom 6→7) that weren't attempted in this pass to avoid destabilizing a fresh scaffold. Safe to defer since these affect the dev server / build tooling, not the shipped runtime bundle, but should be revisited before any production deployment.

## Technical Debt

- `registrationComplete` (in `AuthContext`) is resolved via an extra `GET /api/applicants/me` call on session restore/login rather than being embedded in the JWT — simpler (no token-reissue-on-status-change problem) but costs one small round trip per session start. See [decisions.md](./decisions.md#2026-08-08--registration-unified-into-one-flow-applicant-pages-gated-on-registrationcompletedat).
- Frontend `types.ts` files duplicate backend DTO shapes by hand; no generated client (e.g. OpenAPI/tRPC) keeping them in sync.
- `ApplicantsRepository`/`ApplicationsRepository` etc. return Prisma's generated types directly rather than mapped domain models — acceptable at this scale, but if domain logic grows more complex than "check field, throw AppError," consider introducing real domain model classes distinct from Prisma's row types.
- `PATCH /api/applications/:id/sift` is a one-shot decision, not versioned — no evaluator-history table, just the single `siftedAt`/`siftedByUserId`/`siftingRemarks` overwrite target on `Application` (gated to `UNDER_SIFTING` so it can't be re-run after the fact, unlike the free-standing "evaluate" action it replaced — see [decisions.md](./decisions.md#2026-08-08--siftingpqeinterview-pipeline-repurpose-the-free-standing-evaluate-action-add-an-excel-based-pqe-score-import)).
- `PATCH /api/panel-evaluations/:applicationId` has the same overwrite-not-version behavior for a panelist's own scores - re-submitting replaces the prior score/remarks with no history kept.
