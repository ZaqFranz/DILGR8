# Database

MySQL via Prisma. Schema source of truth: `backend/prisma/schema.prisma`.

## Entity overview

```
User (1) ── (1) Applicant (1) ── (N) WorkExperience
   │                      │  ── (N) LdIntervention ── (N) Document (LD_PROOF, ldInterventionId set)
   │                      │  ── (N) Award
   │                      │  ── (N) Document
   │                      │  ── (N) Application ── (1) JobPosting
   │                      │                     ├── (N) Document (IPCR/DesignationOrder, applicationId set)
   │                      │                     ├── (N) PanelEvaluation ── (N) PanelScore ── (1) EvaluationCriterion
   │                      │                     └── (N) ApplicationComplianceItem ── (1) ComplianceRequirement
   │                      │                                                     └── (N) Document (COMPLIANCE_PROOF, complianceItemId set)
   │
   ├── (N) JobPosting (createdBy, nullable)
   ├── (N) Application (siftedBy, nullable)
   ├── (N) AuditLog (actor, nullable)
   ├── (N) PanelAssignment (panelUser) ── (1) JobPosting
   ├── (N) PanelEvaluation (panelUser)
   └── (N) ApplicationComplianceItem (reviewedBy, nullable)

ApplicantGroup (1) ── (N) ApplicantGroupMember (N) ── (1) Application
```

## Tables

### `users`
Auth identity. `role` is `APPLICANT` (default), `ADMIN`, or `PANEL` (interview board members - see the `panel_assignments`/`panel_evaluations` tables below). Password stored as a bcrypt hash, never plaintext. Full CRUD via `/api/users` (ADMIN only) — see [api.md](./api.md); a user can't delete their own account, and (added 2026-08-22, audit remediation) can't hard-delete any account that has at least one `Application` row, since that would cascade away real hiring/evaluation history (see below and `docs/decisions.md`'s 2026-08-22 entry).

- `mustChangePassword` (default `false`) is set `true` when an applicant requests a temporary password via `POST /api/auth/forgot-password`, and cleared automatically the moment any password change succeeds (`PATCH /api/auth/me/password`, self-service or using the temporary password as `currentPassword`). Returned on the `user` object from both `/login` and `/register`; the frontend gates on it the same way it gates on `registrationCompletedAt` — see [architecture.md § Registration gating](./architecture.md#registration-gating-frontend), which now also covers this forced-password-change redirect.
- `tokenVersion` (default `0`, added 2026-08-22, audit remediation) — embedded in every issued access token and re-checked against this column on every authenticated request (`authenticate()`). Bumped on any password change (self-service, forgot-password, admin-issued temporary password) and on any admin-initiated `PATCH /api/users/:id` update, so a token issued before that change is rejected immediately instead of remaining valid until its natural expiry. See [architecture.md § Authentication & session revocation](./architecture.md#authentication--session-revocation) and `docs/decisions.md`'s 2026-08-22 entry.

### `applicants`
One row per registered applicant, created once via `POST /api/applicants/me`. Holds the demographic profile plus the eligibility flag (`hasEligibility`, `eligibilityType`, `eligibilityValidated`).

- `eligibilityValidated` always starts `false`. It exists for the admin-side manual validation workflow described in the domain spec (Eligibility=N is "subject to manual validation"; Eligibility=Y still needs an admin to confirm the uploaded proof) — **the admin validation UI itself is not built yet** (tracked in project-memory.md).
- `registrationCompletedAt` (nullable) is set once via `POST /api/applicants/me/complete-registration`, after the applicant has gone through profile, work experience, L&D, awards, and documents. The frontend uses it (via `AuthContext.registrationComplete`) to gate access to the rest of the app — see [architecture.md § Registration gating](./architecture.md#registration-gating-frontend) — so applicant data collection is never deferred to after the applicant is already using the app.
- `educationLevel` (`EducationLevel`, required) and `yearsOfExperience` (`Int`, default `0`) are structured counterparts to `job_postings.minEducationLevel`/`minYearsExperience` below, collected on the Demographic Profile step (`DemographicProfileForm.tsx`) - they exist specifically to enable an automatic Sifting hint, the same soft-check role `eligibilityType` already plays via `job_posting_required_eligibilities`. `EducationLevel` is an ordered enum (`ELEMENTARY` … `DOCTORATE`, ascending attainment - see `backend/src/shared/constants/educationLevels.ts`'s `EDUCATION_LEVEL_VALUES`, mirrored on the frontend) compared by ordinal position, not string equality. `yearsOfExperience` is a single self-reported number, not a list of dated entries - `work_experiences` (below) exists in the schema but is deliberately never collected from applicants, since that would duplicate what's already on the required PDS upload; this field is a lighter-weight structured number for comparison purposes only. See [decisions.md](./decisions.md)'s entry on structured qualification minimums.

### `work_experiences`, `ld_interventions`, `awards`
Simple child tables of `applicants`, one row per entry the applicant adds. Cascade-deleted with the applicant. `ld_interventions` and `awards` each additionally have an optional `Document[]` back-relation (`LD_PROOF`/`AWARD_PROOF` type respectively) - see `documents` below. Every `ld_interventions`/`awards` entry requires at least one matching proof document before registration can complete (`ApplicantsService.completeRegistration()`) - same rule as eligibility: claiming something means proof of that specific claim is required.

### `documents`
Uploaded files. `applicantId` is always set. `applicationId` is set for documents tied to a specific application - as of this change, that's exactly the `APPLICATION_LETTER` created alongside that `Application` in `ApplicationsRepository.createWithApplicationLetter()` (see `applications` below); every other type is applicant-level (`applicationId` null) rather than per-application, uploaded once during registration and checked by type. `ldInterventionId` is set only for `LD_PROOF` documents and `awardId` only for `AWARD_PROOF` documents, each tying a proof file (certificate, citation, etc.) to the specific `LdIntervention`/`Award` claim it backs up - both `onDelete: Cascade`, so removing an entry removes its proof files too. An entry has zero or one proof document, never more - `DocumentsService.upload()` deletes any existing `LD_PROOF`/`AWARD_PROOF` for that exact entry before inserting a new one, so re-uploading replaces it (same rule as the single-instance applicant-level types below, just scoped per entry instead of per applicant); the frontend hides the file input on `LdInterventionSection`/`AwardsSection`'s per-row "Proof" column once an entry has a file, showing it again only once that file is removed. Files are stored on local disk under `backend/uploads/` (path in `filePath`); only metadata lives in the DB.

`type` (`DocumentType`) covers the full official application-documents checklist: `APPLICATION_LETTER` (per-application, not applicant-level - see below), `PDS` (Personal Data Sheet, PDF/scanned copy), `PDS_EXCEL` (the same PDS but the raw CS Form 212 spreadsheet - the applicant must upload both; see below), `IPCR` (labeled "Performance Rating (Last Rating Period)" in the UI), `ELIGIBILITY_PROOF`, `LD_PROOF`, `TRANSCRIPT_OF_RECORDS`, `DIPLOMA`, `PQE_NOTICE`, `DESIGNATION_ORDER` (labeled "Proof of Designation"), `AWARD_PROOF`, `COMPLIANCE_PROOF`, `OTHER`. `COMPLIANCE_PROOF` isn't part of the original a-j checklist - it's uploaded much later, per `application_compliance_items` row (`complianceItemId` set, same one-slot-per-parent-entity pattern as `LD_PROOF`/`AWARD_PROOF`), during the post-evaluation Compliance to Requirements phase (see `applications`/`application_compliance_items` below). `PDS` and `PDS_EXCEL` are unconditionally hard-required at registration (`ApplicantsService.completeRegistration()` blocks without either); `APPLICATION_LETTER` is required too, but at apply time instead (`ApplicationsService.submit()` 400s without one - see `applications` below); `ELIGIBILITY_PROOF` is required only if `Applicant.hasEligibility` is true; `LD_PROOF`/`AWARD_PROOF` are required per entry only if the applicant added any `ld_interventions`/`awards` rows (each entry needs its own matching proof - see `work_experiences, ld_interventions, awards` above); every other type is genuinely optional/conditional, matching the checklist's "if applicable"/"if any" qualifiers - `DESIGNATION_ORDER` in particular is never required to submit an application, even to a `PROMOTIONAL` posting (see [decisions.md](./decisions.md)).

Every type except `OTHER` represents a single current document, at one of three scopes: the eight applicant-level types (`PDS`, `PDS_EXCEL`, `IPCR`, `ELIGIBILITY_PROOF`, `TRANSCRIPT_OF_RECORDS`, `DIPLOMA`, `PQE_NOTICE`, `DESIGNATION_ORDER`) are one-per-applicant; `LD_PROOF`/`AWARD_PROOF` are one-per-entry (one per `LdIntervention`/`Award` row); `APPLICATION_LETTER` is one-per-application (one per `Application` row - an applicant reapplying to a different posting uploads a new letter for that application, since the letter is addressed to a specific vacancy). The applicant-level types go through `DocumentsService.upload()`, which deletes whatever already occupies that slot (DB row + file on disk) before inserting the new one, so re-uploading always replaces rather than accumulates; `APPLICATION_LETTER` instead goes through the dedicated apply-time path (below) and was removed from `DocumentsService`'s `SINGLE_INSTANCE_TYPES` and from `uploadDocumentFieldsSchema`'s `type` enum entirely, since there's no legitimate way to create one through the generic upload endpoint anymore (nothing to tie it to an application there). `OTHER` is the sole exception among applicant-level types - a genuine multi-file miscellaneous catch-all with no slot to replace.

**File type enforcement:** every `DocumentType` accepts PDF/JPEG/PNG by default (a scanned or photographed paper copy) except `PDS_EXCEL`, which must be the actual spreadsheet (`.xlsx`/`.xls` - `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` or `application/vnd.ms-excel`, the same MIME set used by the PQE score import). Multer's `fileFilter` (`documents.upload.ts`) is only the outer gate - it accepts the union of every type's allowed MIME types, since `req.body.type` isn't reliably parsed yet when `fileFilter` runs mid-stream. The authoritative, type-aware check is `assertMimeTypeAllowed()` in `documents.service.ts`, run after multer has fully parsed the request and rejecting with a 400 (e.g. uploading an Excel file as `PDS` or an image as `PDS_EXCEL` both 400) - `ALLOWED_MIME_TYPES_BY_DOCUMENT_TYPE` is where a future type-specific rule would be added. The frontend (`DocumentsSection.tsx`) mirrors the same rule via its own `accept` attribute per type and a matching client-side check, so the wrong file type is caught before the network round trip too.

### `job_postings`
A vacancy, modeled directly on the fields of an official DILG job-posting document rather than an app-invented shape. `description` (`@db.Text`, required) is a free-text overview of the role/duties, separate from the four `qualification*` fields below it (the formal QS requirements) — only shown to applicants behind `JobPostingsListPage`'s "View Details" modal, not on the list card itself. `numberOfVacantPositions` (`VARCHAR(191)`), `plantillaNumbers` (`@db.Text` - "Number/s", so it may hold more than one), and `positionNextInRank` (`@db.Text`) are free-text rather than numeric/structured columns, so each can carry values exactly as the official document prints them (e.g. `numberOfVacantPositions: "One (1)"`, `positionNextInRank: "None required"`) instead of the schema imposing its own format. `salaryGrade` (`VARCHAR(191)`) is the one exception to "free text" among this group — constrained to `"1"`-`"33"` at the DTO layer (a zod enum, not a DB-level check), since it now drives `monthlySalary` rather than being purely cosmetic. `monthlySalary` (`VARCHAR(191)`) stays a formatted string (`"₱53,818.00"`, same "carry the value exactly as the document prints it" reasoning) but is no longer admin-typed - `JobPostingsService` computes and overwrites it from `salaryGrade` on every create/update, via the official DBM Salary Grade schedule (`backend/src/shared/constants/salaryGrades.ts`, mirrored on the frontend for a live preview only) - see [decisions.md](./decisions.md)'s 2026-08-12 "Fixed Monthly Salary derived from Salary Grade" entry. `placeOfAssignment` (`@db.Text`, required) and `duties` (`@db.Text`, required) are shown only in the details modal, alongside `description` and the qualification standards — `duties` is one duty per line, rendered by the frontend as a numbered list split on `\n`. There is no "position level" (`ENTRY`/`PROMOTIONAL`) field or enum - it existed early on as a coarse Entry/Promotional label but nothing in the app ever branched on it (confirmed before removal - see [decisions.md](./decisions.md)), and it doesn't correspond to anything on the official document these fields now mirror; the admin list/edit UI dropped the corresponding filter and form field, and the applicant-facing card/details view show `salaryGrade` where "Level" used to be. `closingAt` is computed at creation time in `JobPostingsService.computeClosingAt()` as `postedAt + 10 days, 23:59:59` per the domain spec's 10-day application window. `status` is `OPEN`/`CLOSED`; there is no scheduled job yet to flip it automatically when `closingAt` passes (`JobPostingsService.isAcceptingApplications()` checks both `status` and `closingAt` at submission time as a safeguard) — admins can also close a posting manually via `PATCH`.

`qualificationEligibility` (`@db.Text`) remains free text shown to applicants for context (e.g. "RA 1080 or CSC Professional required") but is never parsed programmatically — the machine-enforced requirement lives separately in `job_posting_required_eligibilities` (below). A posting with no rows there requires no eligibility to apply.

`minEducationLevel` (`EducationLevel?`), `minYearsExperience` (`Int?`), and `minTrainingHours` (`Int?`) are optional structured minimums alongside `qualificationEducation`/`qualificationExperience`/`qualificationTraining` above - `null` (the default; every existing posting before this migration has all three unset) means no automatic Sifting hint for that criterion, since a posting can rely on the free text alone. None of the three ever replaces its free-text sibling as the authoritative QS wording ("relevant to the job" can't be captured by an enum/number) - they only drive a computed "meets/below/no automatic check" badge on `EvaluateApplicantsPage`'s Sift modal, computed **client-side** (`frontend/src/shared/utils/qualificationMatch.ts`) from these three fields plus the matching `applicants.educationLevel`/`yearsOfExperience`/`ldInterventions` fields - not persisted or returned by the API as its own field, so it's always fresh after any status-changing action re-renders the row (see [decisions.md](./decisions.md)).

### `job_posting_required_eligibilities`
Join table: one row per `EligibilityType` a posting requires (`RA1080`/`CSC_PROFESSIONAL`/`CSC_SUBPROFESSIONAL`/`BARANGAY`), unique on `(jobPostingId, eligibilityType)`, `onDelete: Cascade` from `job_postings`. Exists because MySQL doesn't support Prisma scalar-list fields, so a `JobPosting.requiredEligibilityTypes: EligibilityType[]` array isn't directly representable as a column — `JobPostingsRepository` flattens these rows into a `requiredEligibilityTypes: EligibilityType[]` array on the way out (and replaces the whole set on update via `deleteMany` + `create` in one call) so callers never deal with the join table directly. An applicant satisfies a posting's requirement when `Applicant.hasEligibility` is true and `Applicant.eligibilityType` is one of the posting's rows; `ApplicationsService.submit()` hard-blocks (400) submission otherwise. See [decisions.md](./decisions.md).

Because `monthlySalary`, `placeOfAssignment`, and `duties` were added as required columns after `job_postings` already had seeded rows, the migration (`20260808044639_add_salary_place_duties_to_job_posting`) follows the established add-nullable → backfill → enforce-NOT-NULL pattern (MySQL `TEXT`/`VARCHAR` columns backing a required field can't carry a `DEFAULT` in a single `ADD COLUMN ... NOT NULL`, since existing rows would violate it immediately) — same pattern used for `description` earlier.

`createdByUserId` is nullable with `onDelete: SetNull` (not the required/Restrict Prisma would default to) specifically so deleting the admin who posted a job doesn't get blocked by, or cascade into deleting, the posting — see [decisions.md](./decisions.md). Deleting a posting itself is blocked (409) while it has any applications, to avoid silently wiping out submitted applications via cascade; close it instead.

### `applications`
Join between `applicants` and `job_postings`, unique on `(applicantId, jobPostingId)` — an applicant may apply to several postings but only once each. Submitting requires an `APPLICATION_LETTER` file (`POST /api/applications` is `multipart/form-data`: `jobPostingId` + `file`) - `ApplicationsService.submit()` 400s without one, and `ApplicationsRepository.createWithApplicationLetter()` creates the `Application` and its `Document(type=APPLICATION_LETTER, applicationId=...)` together in one `$transaction`, so an application can never exist without its letter (or vice versa). The full pipeline: `SUBMITTED` → `UNDER_SIFTING` (set automatically the instant an application is submitted - there's no separate "start sifting" step) → `QUALIFIED`/`NOT_QUALIFIED` (the Sifting phase's pass/fail call against the posting's qualification standards, via `PATCH /api/applications/:id/sift`, 400 unless currently `UNDER_SIFTING`) → PQE score recorded on a `QUALIFIED` application, either via bulk Excel import (`POST /api/applications/import-exam-scores`, matched by applicant name) or one at a time (`PATCH /api/applications/:id/exam-score`, `{ score }`, 400 unless the application is `QUALIFIED`) - neither changes `status` → `FOR_INTERVIEW` (`PATCH /api/applications/:id/schedule-interview`, 400 unless `status === QUALIFIED` **and** `examinationScore` is set; also stamps `interviewScheduledAt`/`interviewVenue`/`interviewAttire`/`interviewNotes` from the admin-supplied `ScheduleInterviewDto`, so the notification email can tell the applicant when/where to show up and what to wear) → interview panel scoring (`panel_evaluations`/`panel_scores` below). `WITHDRAWN` can be reached from any of `SUBMITTED`/`UNDER_SIFTING`/`QUALIFIED`/`FOR_INTERVIEW`/`FOR_COMPLIANCE`/`FOR_OATH_TAKING` via the applicant's own `PATCH /api/applications/:id/withdraw` (stamps `withdrawnAt`) - it's the one transition the applicant themself triggers rather than an admin/panelist. `NOT_QUALIFIED`, `NOT_SELECTED`, `DISQUALIFIED`, `HIRED`, and `WITHDRAWN` itself are all terminal and can't be withdrawn from. See `compliance_requirements`/`application_compliance_items` below for the phases past `FOR_INTERVIEW`; the Deliberation phase (final RD decision) is absorbed into the single `move-to-compliance` admin action rather than a distinct status - see [decisions.md](./decisions.md).

Sifting stamps `siftingRemarks`/`siftedAt`/`siftedByUserId` (→ `users.id`) — pass/fail only, no numeric score, matching the domain spec's Sifting criteria (education/training/experience/eligibility). The PQE import stamps `examinationScore`/`examinationScoredAt`. Both are separate from the interview panel's per-criterion scoring below — the panel average is display-only context (via `GET /panel-evaluations/tabulation/:jobPostingId`), never written back onto `Application`. Withdrawal stamps only `withdrawnAt` — unlike `siftedByUserId` there's no separate actor column, since `applicantId` already identifies whose action it was and there's no admin equivalent to disambiguate.

Past `FOR_INTERVIEW`, the pipeline continues: `PATCH /api/applications/:id/move-to-compliance` (400 unless `status === FOR_INTERVIEW`) sets `status: FOR_COMPLIANCE` and stamps `complianceRequestedAt`, and bulk-creates one `application_compliance_items` row per currently-active `compliance_requirements` row (a snapshot - see that table below). Once every item is `VERIFIED`, `PATCH /api/applications/:id/oath-taking` (400 unless `status === FOR_COMPLIANCE` **and** every item is `VERIFIED`) sets `status: FOR_OATH_TAKING`, stamps `complianceCompletedAt`, and stamps `oathTakingScheduledAt`/`oathTakingVenue`/`oathTakingNotes` from the admin-supplied schedule (mirrors `schedule-interview`'s combined transition+schedule shape). `PATCH /api/applications/:id/hire` (400 unless `status === FOR_OATH_TAKING`) sets `status: HIRED` and stamps `hiredAt` - terminal for this pipeline segment; Onboarding itself is future work. Since 2026-08-21, it also bulk-transitions every other of the applicant's `OPEN_APPLICATION_STATUSES` applications to `NOT_SELECTED` (same `rejectedAt`/`rejectionRemarks` columns the regret exits below already use, remarks system-generated naming the posting they lost to) - see [architecture.md](./architecture.md)'s Multi-posting applications section. `WITHDRAWN`'s reachable-from set now also includes `FOR_COMPLIANCE`/`FOR_OATH_TAKING` (an applicant can still withdraw up until actually hired) — see [decisions.md](./decisions.md).

`FOR_INTERVIEW` and `FOR_COMPLIANCE` each have a regret/rejection exit alongside their forward one: `PATCH /api/applications/:id/not-selected` (400 unless `status === FOR_INTERVIEW`) sets `status: NOT_SELECTED`, and `PATCH /api/applications/:id/disqualify` (400 unless `status === FOR_COMPLIANCE`, no "all items verified" precondition) sets `status: DISQUALIFIED` - both stamp the same shared `rejectedAt`/`rejectionRemarks` columns (one pair reused by both actions rather than two near-identical sets, since they're the same kind of one-shot terminal call just from a different stage) and send the applicant the same `regretEmail()` template `sift`'s `NOT_QUALIFIED` branch already used, worded per stage. These are distinct statuses from `NOT_QUALIFIED` specifically so `ApplicationStageTracker.tsx` can resolve the rejection on the stage node it actually happened at (Evaluation of Applicants / Compliance to Requirements) instead of showing every rejection as if it happened back at Sifting. See [decisions.md](./decisions.md).

`scoreSourceApplicationId` (added 2026-08-21, migration `20260821000001_add_application_score_inheritance`, per client request: applicants may apply to multiple postings at once "as long as Applicant is not hired," and shouldn't be interviewed separately for each one) is a nullable self-relation - when set, this application's panel interview score is carried over from another of the same applicant's applications rather than scored here. Always points directly at a canonical (never-inheriting) application, never chained through another inheriting one. Set three ways: `ApplicationsRepository.createWithApplicationLetter()` links a *new* application at creation time if the applicant already has a scored (or already-inheriting) one; `PanelEvaluationsRepository.linkSiblingScoreSources()` links every *existing* open sibling the moment a canonical application is actually scored (`PanelEvaluationsService.submit()`, called right after `upsertEvaluation()`); and, added 2026-08-21 to close a race those two leave open (both applications reach `FOR_INTERVIEW` unlinked *before* either is scored), a self-healing repair pass in `PanelEvaluationsRepository.findQueueForPanelUser()` plus a live re-check in `reconcileScoreSource()` (called from `submit()` right before recording a score) - see [decisions.md](./decisions.md)'s "duplicate interviews" entry. Every reader of "this application's panel evaluations" (`findApplicationsForTabulation`, `findApplicationsWithScores`) resolves the pointer via a batched lookup before returning, and the panel queue (`findQueueForPanelUser`) excludes inheriting applications outright so no panelist is ever asked to redundantly score someone already scored elsewhere; `PanelEvaluationsService.submit()` also refuses to score an inheriting application directly (defensive backstop, now backed by the live re-check above rather than only the possibly-stale stored field). `ApplicationsService.submit()` separately gates *new* applications on the applicant's own HIRED status (409 if they already have one `HIRED` application, regardless of `scoreSourceApplicationId`) - once hired anywhere, no further applications at all. The inverse side of the self-relation, `scoreInheritingApplications` (declared alongside the forward field, no separate migration), is included in `GET /api/applications/me` so `MyApplicationsPage.tsx` can tell an applicant on the canonical application that a sibling exists and how far along it is - added 2026-08-21, since each application's pipeline `status` still advances independently per posting even though the interview score is shared (Compliance/Oath-Taking stay a per-posting admin decision). See [decisions.md](./decisions.md) for why this is a pointer rather than physically copying `panel_scores` rows.

### `categories` / `criteria`
The admin-editable interview rubric (domain spec: "administrator can edit/update evaluation forms"), renamed 2026-08-19 from `evaluation_criteria`/`evaluation_criterion_questions` into an explicit two-level structure - see `docs/decisions.md` for the full rationale and the data migration this required. `categories` is the top-level grouping (`name`, `weightPercent`, `sortOrder`, `isActive`). `weightPercent` (added same day, migration `20260819130950_add_category_weight_percent`, per client request) is the category's admin-set, authoritative share of the overall evaluation (e.g. `25` = 25%) - it is a **real stored column**, unlike the category's `maxScore` shown in API responses, which stays a purely-derived, purely-internal number: the sum of the category's own active `criteria` rows' `maxScore`, computed at read time (`CategoriesRepository`) rather than stored, so it can never drift out of sync with its children. The two are deliberately independent: a category worth 25% contributes exactly 25% to the overall evaluation whether its criteria sum to 10 raw points or 1000 - see [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation)'s "Weighted scoring" for the normalization math. `criteria` is the individually-scored rubric line within a category (`categoryId`, `name`, `maxScore`, `sortOrder`, `isActive`) - a panelist scores *this*, one `panel_scores` row per criterion, never the category as a whole. `isActive: false` retires a category or a criterion without deleting it; removing a criterion (via `PATCH /api/categories/:id`'s diffed `criteria` array) is blocked (409) once any `panel_scores` row references it, the same shape as the `job_postings` delete-guard - deactivate it instead. Deleting a whole category is likewise blocked (409) if *any* of its criteria has a recorded score. The app never enforces that active categories' `weightPercent` sum to 100 - a soft "usually expected to add up to 100%" hint on `CategoriesPage` only.

### `panel_assignments`
Which `PANEL` users sit on which job posting's interview board, unique on `(jobPostingId, panelUserId)`. Pure assignment metadata — both FKs `onDelete: Cascade`, since dropping the assignment when a posting or panel user is deleted has no data-loss implications (unlike `job_postings.createdByUserId`, there's nothing else referencing the assignment row). Determines both what a panelist can see (`GET /panel-evaluations/my-queue`) and score (`PATCH /panel-evaluations/:applicationId` 403s if not assigned) — and, as of the panel document-viewing feature, whether a panelist may view an assigned applicant's PDS (`GET /applicants/:id/documents` / `GET /applicants/documents/:id/file`, via the new `isPanelUserAssignedToApplicant()` repository method: true only if the applicant has an active `FOR_INTERVIEW` application on a posting this panelist is assigned to).

### `panel_evaluations` / `panel_scores`
One panelist's scoring of one application. `panel_evaluations` is the header row (`applicationId`, `panelUserId` — unique together, `remarks`, timestamps); `panel_scores` holds the per-**criterion** raw values (`panelEvaluationId`, `criterionId` — unique together, `score`), cascade-deleted with the evaluation. `criterionId` references `criteria.id` (the leaf rubric line, not the parent category) — a category is never scored as one number, only reported as the sum of its own criteria's scores, normalized to the category's `weightPercent` before it counts toward anything (see below). Re-submitting a panelist's scores for the same application upserts the header and replaces every score row in one transaction (`PanelEvaluationsRepository.upsertEvaluation`), mirroring how `applications.evaluate` overwrites a prior admin evaluation rather than versioning it. `GET /panel-evaluations/tabulation/:jobPostingId` and `GET /panel-evaluations/applicant-scores` both read these raw `score` values at read time (application code, not SQL) and run them through the same weighted-scoring normalization - a category's raw subtotal here is never reported or ranked on directly - see [architecture.md § Interview panel & CompAss tabulation](./architecture.md#interview-panel--compass-tabulation)'s "Weighted scoring".

### `applicant_groups` / `applicant_group_members`
Admin-defined ad hoc groupings of applicants for Group Dynamics Evaluation (admin request: "Admin can Group applicants ... for Group dynamics Evaluation") - a distinct, non-scored assessment activity, unrelated to the interview rubric (`categories`/`criteria`) above. `applicant_groups` is just `name`, optional `description` (`@db.Text`), and timestamps - it carries no `jobPostingId` of its own, since one group exercise can mix applicants from different postings (unlike `panel_assignments`, which is keyed to a single posting's board). `applicant_group_members` is the join to `applications` (not to `applicants` directly - the same scoping `panel_evaluations` uses), unique on `(groupId, applicationId)`, both FKs `onDelete: Cascade`. Created via `POST /api/applicant-groups` (`{ name, description?, applicationIds: string[] }`, `applicationIds` requires at least 2 - a "group" of one applicant isn't a group) from the admin's checkbox selection on `GroupsPage` (`/admin/groups`, "Group" in the sidebar) - the same select-then-bulk-act UI shape as Interview Panel's "Assign Panel to Selected", with a "Group" button opening a name+description modal in place of the panel picker. `PATCH /api/applicant-groups/:id` (`{ name?, description?, applicationIds?: string[] }`) renames/redescribes an existing group and/or replaces its membership - `applicationIds`, when present, is the group's new full member list (min 2), diffed by `ApplicantGroupsRepository.update()` against what's on file (remove what's missing, add what's new) inside one transaction, the same add/remove-by-diff shape `CategoriesRepository.update()` uses for a category's criteria array. `DELETE /api/applicant-groups/:id` removes the group and cascade-deletes its members outright (no soft-delete/`isActive` guard, unlike `categories`/`compliance_requirements`) since a group carries no historical scores or other referencing rows to protect.

### `compliance_requirements`
Admin-managed global catalog of CSC-mandated documentary requirements (domain spec: Compliance to Requirements). `name`, `description` (nullable), `sortOrder`, `isActive`. `isActive: false` retires a requirement without breaking historical `application_compliance_items` rows; `DELETE` is blocked (409) once any item references it, the same shape as the `categories` delete-guard. Global, not per-posting - same simplification already accepted for `categories` (see project-memory.md Known Limitations).

### `application_compliance_items`
One requirement's checklist row for one application, unique on `(applicationId, requirementId)`. Rows arrive two ways: automatically, via `ApplicationsService.moveToCompliance()` bulk-creating one `PENDING`, `SOFTCOPY` row per currently-active `compliance_requirements` row the moment an application enters `FOR_COMPLIANCE` (a snapshot, not a live join - a requirement added to the catalog afterward won't retroactively appear); or manually, via `POST /api/applications/:id/compliance-items` (`ApplicationsService.addComplianceItem()`), which lets an admin attach one more requirement from the catalog to a single application already `FOR_COMPLIANCE` - the escape hatch for when the automatic snapshot came up short (e.g. the catalog had nothing active yet) and the admin needs to pick a requirement to review instead of the checklist staying permanently empty. `status` (`ComplianceItemStatus`: `PENDING`/`VERIFIED`/`REJECTED`) starts `PENDING` regardless of whether a proof document exists yet - the applicant's `Document(type=COMPLIANCE_PROOF, complianceItemId=...)` upload and the admin's review are two independent facts, not two different stored statuses (whether a proof exists is derived from the `documents` join, not a column here). `submissionType` (`ComplianceSubmissionType`: `SOFTCOPY`/`HARDCOPY`, defaults `SOFTCOPY`) is what the applicant is expected to submit this requirement as - `SOFTCOPY` means through the existing online `Document(type=COMPLIANCE_PROOF)` upload, `HARDCOPY` means handed over physically outside the system, with nothing to upload. An admin sets it per item via `PATCH /api/applications/:id/compliance-items/:itemId/submission-type` (`ApplicationsService.setComplianceItemSubmissionType()`); it's never chosen by the applicant, since a hardcopy submission by definition never touches the system for them to declare. `remarks`/`reviewedAt`/`reviewedByUserId` are set together by `PATCH /api/applications/:id/compliance-items/:itemId` - `VERIFIED` requires both the applicant's submission and the admin's approval of it: for `SOFTCOPY` this means an uploaded `COMPLIANCE_PROOF` document must already exist (400 otherwise - "nothing to verify"); for `HARDCOPY` there's no online counterpart to check, so the admin's `VERIFIED` is itself the record that the physical copy was received and approved. `REJECTED` has no such precondition either way. `requirementId` has no `onDelete` override (defaults to Restrict) - same convention as `panel_scores.criterionId` - the service-level delete guard above is the real protection, this is defense in depth.

### `audit_logs`
Append-only history of admin/panel write actions: `USER_CREATED/UPDATED/DELETED`, `JOB_POSTING_CREATED/UPDATED/DELETED`, `APPLICATION_SIFTED`, `APPLICATION_EXAM_SCORES_IMPORTED`, `APPLICATION_SCHEDULED_INTERVIEW`, `APPLICATION_MOVED_TO_COMPLIANCE`, `APPLICATION_COMPLIANCE_ITEM_ADDED`, `APPLICATION_COMPLIANCE_ITEM_SUBMISSION_TYPE_SET`, `APPLICATION_COMPLIANCE_ITEM_REVIEWED`, `APPLICATION_OATH_TAKING_SCHEDULED`, `APPLICATION_HIRED`, `CATEGORY_CREATED/UPDATED/DELETED`, `COMPLIANCE_REQUIREMENT_CREATED/UPDATED/DELETED`, `PANEL_ASSIGNED/UNASSIGNED`, `PANEL_EVALUATION_SUBMITTED`, `APPLICANT_GROUP_CREATED/UPDATED/DELETED`. `action` and `entityType` are plain strings, not DB enums, so new action types don't need a migration (see `backend/src/modules/audit-logs/audit-actions.ts` for the known set). `actorUserId` is nullable with `onDelete: SetNull` — deleting a user preserves the log entries they created, just with the actor link severed rather than the rows disappearing. There is deliberately no `PATCH`/`DELETE` on `/api/audit-logs` — see [decisions.md](./decisions.md).

## Conventions

- All primary keys are `String @id @default(uuid())`.
- All child tables cascade-delete (`onDelete: Cascade`) when their parent (`Applicant`/`Application`) is deleted.
- Timestamps: `createdAt`/`updatedAt` on every table except `documents` and `applications`, which only need `uploadedAt`/`submittedAt` (immutable records — see [decisions.md](./decisions.md)).
- Table names are snake_case (`@@map`); TypeScript-facing model names are PascalCase (Prisma default).
