# Architecture

## Overview

DILGR8RSP is an npm-workspaces monorepo with two deployables:

- **`backend/`** — Express + TypeScript REST API, MySQL via Prisma, JWT auth.
- **`frontend/`** — React + TypeScript SPA (Vite), talks to the API over `fetch`.

Both follow **feature-first** organization: code is grouped by business capability (`auth`, `applicants`, `job-postings`, `applications`, `users`, `audit-logs`, `dashboard`, `categories`, `panel-assignments`, `panel-evaluations`, `compliance-requirements`, and on the frontend `admin` plus `panel`) rather than by technical layer at the top level. Within each backend feature, Clean Architecture layering is still enforced (see below).

## Backend layering

Each backend module in `backend/src/modules/<name>/` is split into:

| Layer | File | Responsibility |
|---|---|---|
| Routes | `*.routes.ts` | Maps HTTP verb+path to a controller method; wires in `authenticate`/`requireRole`/`validate` middleware. |
| Controller | `*.controller.ts` | Translates `Request`/`Response` to/from plain DTOs; no business logic. |
| Service | `*.service.ts` | Business rules and orchestration (e.g. "promotional applications need IPCR + Designation Order uploaded"). Throws `AppError` subclasses on failure. |
| Repository | `*.repository.ts` | Only place that talks to Prisma for that module. Returns Prisma types or thin wrappers. |
| DTO | `*.dto.ts` | Zod schemas (source of truth for validation) + inferred TypeScript types. |

Cross-cutting concerns live in `backend/src/shared/`:

- `errors/AppError.ts` — typed error hierarchy (`ValidationError`, `UnauthorizedError`, `ForbiddenError`, `NotFoundError`, `ConflictError`), each carrying an HTTP status + machine-readable `code`.
- `middleware/errorHandler.ts` — the **only** place that turns a thrown error into an HTTP response (see [patterns.md](./patterns.md#centralized-error-handling)).
- `middleware/authenticate.ts` — JWT verification (`authenticate`) and role gating (`requireRole`).
- `middleware/asyncHandler.ts` — wraps async route handlers so rejected promises reach `errorHandler`.
- `validation/validate.ts` — Express middleware that runs a Zod schema against `body`/`params`/`query` before the controller runs.
- `logging/logger.ts` — Pino logger (pretty-printed in development).
- `db/prismaClient.ts` — single shared `PrismaClient` instance.

### Composition root

`backend/src/container.ts` is the single place that constructs repositories → services → controllers and wires their dependencies together (manual constructor injection — see [patterns.md](./patterns.md#dependency-injection)). `app.ts` only imports `container` and mounts routers; it never constructs a service or repository itself. This keeps every class unit-testable by constructing it directly with fakes, without a DI framework.

### Request flow

```
HTTP request
  → Express router (modules/<x>/<x>.routes.ts)
  → middleware: authenticate (JWT) → validate (Zod) → asyncHandler
  → controller (modules/<x>/<x>.controller.ts)
  → service (modules/<x>/<x>.service.ts)          [business rules, throws AppError]
  → repository (modules/<x>/<x>.repository.ts)    [Prisma]
  ← response JSON
  (errors thrown anywhere above are caught once by shared/middleware/errorHandler.ts)
```

## Frontend layering

`frontend/src/features/<name>/` mirrors the backend's module boundaries:

- `api/` — thin wrappers around `shared/api/apiClient.ts` (one function per backend endpoint).
- `types.ts` — TypeScript types matching the backend's DTO shapes.
- `components/` — presentational + form components scoped to that feature.
- `pages/` — route-level components composed from the above.

`frontend/src/shared/` holds cross-feature concerns: `api/apiClient.ts` (fetch wrapper + JWT header + `ApiError`), `auth/AuthContext.tsx` (session state), `components/` (`Layout`, `ProtectedRoute`, `ErrorBanner`, `Modal`, `ConfirmDialog`, `ToastProvider`, `FieldError`, `LoadingBlock`, `Spinner`).

`Modal` (`shared/components/Modal.tsx`) is the generic dialog primitive - Escape/click-outside-to-close, rendered via `createPortal` so it always sits above page content. `ConfirmDialog` wraps it for destructive-action confirmations (used everywhere a delete happens). The admin CRUD tables (`JobManagementPage`, `UsersManagementPage`) wrap it the same way for create/edit: the page renders a table only (no inline form) with an "Add X" button in a `.page-header` row; the button and each row's "Edit" open the same `Modal`-hosted form, switching title/submit label based on whether an id is being edited. The form's submit button lives in the modal's `footer` and targets the form via the HTML `form="…"` attribute rather than being nested inside it, since `Modal`'s footer is a sibling of `modal-body`, not a child of the form.

### Role-based routing (frontend)

The `admin` feature (`frontend/src/features/admin/`) is a separate section of the app from the applicant-facing features, not just a different set of links on the same pages. `ProtectedRoute` (`shared/components/ProtectedRoute.tsx`) takes an optional `role` prop, `<ProtectedRoute role="ADMIN">` vs `<ProtectedRoute role="APPLICANT">` vs `<ProtectedRoute role="PANEL">` (the prop type is `AppRole | AppRole[]`, checked via array-membership, so a route could allow more than one role if a future page needs it) — and bounces a logged-in user of the wrong role to their own home (`HOME_BY_ROLE`: `/admin/dashboard`, `/jobs`, or `/panel/interviews`) rather than showing them another role's pages. There is no self-serve way to become `ADMIN` or `PANEL` via `/auth/register` (always creates `APPLICANT`), but an existing admin can provision either through Users Management (`POST /api/users` — see [api.md](./api.md)), or one can be seeded via `prisma/seed.ts`.

### Registration gating (frontend)

All applicant data (account, demographic profile, work experience, L&D, awards, documents) is collected in one continuous flow, not split into "sign up" then "fill in your info after logging in." `RegistrationPage` (`frontend/src/features/applicant-registration/pages/RegistrationPage.tsx`) owns the entire flow at `/register` — it renders the account-creation form for unauthenticated visitors and, immediately after `register()` succeeds, continues in place through the same steps the old post-login wizard used, with no route change or "you're now logged in" handoff in between.

`AuthContext` tracks `registrationComplete: boolean | null` for the current session (always `true` for `ADMIN`; fetched from `GET /api/applicants/me` for `APPLICANT` right after login/register and on session restore). `ProtectedRoute` and `HomeRedirect` both redirect an applicant with `registrationComplete === false` to `/register`, regardless of which page they try to reach directly — so browsing job postings or submitting applications is unreachable until `POST /api/applicants/me/complete-registration` has been called. Completing registration is what flips `registrationComplete` to `true` (via `refreshRegistrationStatus()`); `/register` remains reachable afterward too, so applicants can still revisit it to edit their profile (Layout's "My Profile" link), it just no longer blocks anything once complete.

Admin and applicant sections also look structurally different, not just role-gated: `Layout` (`shared/components/Layout.tsx`) renders the applicant-facing top nav ("Job Postings", "My Profile", "My Applications") only for `role === "APPLICANT"`, a single "My Interviews" link for `role === "PANEL"`, and stays minimal (brand + identity) for admins. Every authenticated role gets the same identity control on the right: a `.user-menu` trigger showing the email, opening a small dropdown (`.user-menu-dropdown`, click-outside/Escape-to-close, closes on any route change) with "Change Password" and "Log out" - previously two separate always-visible nav items plus a bare email label, combined into one trigger to keep the header from growing a new top-level item every time an account-level action is added. Every `/admin/*` page instead wraps its content in `AdminShell` (`features/admin/components/AdminShell.tsx`), a left sidebar with links to the admin sections, active-link-highlighted via `useLocation()`. `NAV_ITEMS` is ordered by data dependency rather than alphabetically or by when each section was built (reordered 2026-08-19, per client request - see [decisions.md](./decisions.md)): Dashboard (overview, stays first), Users Management, Positions, Job Management, Categories, Compliance Requirements, Interview Panel, Group, Evaluate Applicants, History of Logs (read-only, stays last) - each section's prerequisite data (e.g. Positions' default panel members need PANEL-role Users to already exist, Job Management postings are optionally created from a Position) exists by the time an admin would reach it top-to-bottom. The `panel` role doesn't get an equivalent sidebar shell — it has exactly one page (`MyInterviewsPage`, `/panel/interviews`), so it renders as a plain page under `Layout` the same way applicant pages do; a `PanelShell` would be pure ceremony at one page. `Layout` detects `pathname.startsWith("/admin")` and swaps `.app-main` for the unconstrained `.app-main--full` so the sidebar can span full width instead of being squeezed into the applicant pages' centered 960px column.

The login page and the registration flow's first (unauthenticated "create an account") step get their own full-bleed branded treatment via a `.auth-page` CSS class, rather than a `Layout`/route-level class swap like the admin sidebar above - it's scoped inside `LoginPage`/`RegistrationPage` themselves (the rest of the registration wizard, once authenticated, stays in the normal centered column). `.auth-page` breaks out of `.app-main`'s max-width via the `left: 50%; margin-left: -50vw;` CSS trick, which - unlike `.app-main--full` - works from inside a normally-constrained parent with no cooperation needed from `Layout`. `html`/`body` carry `overflow-x: clip` (not `hidden`) specifically to absorb the few px of horizontal overflow that trick introduces (`100vw` includes the scrollbar's own width, `100%` doesn't) - `.table-wrap`'s own `overflow-x: auto` is an independent scroll region and is unaffected. `clip` rather than `hidden` matters here: per the CSS Overflow spec, setting only `overflow-x` to a non-`visible` value forces the *computed* `overflow-y` to `auto` too (the "both axes must be a scroll mechanism or neither" pairing rule), so `overflow-x: hidden` alone silently turned `html`/`body` into their own independent scroll containers - breaking `position: sticky` for `.app-header`, which needs to stick relative to the real document scroll. `overflow: clip` clips without establishing a scrollable region, sidestepping the pairing rule entirely while still hiding the same overflow (see [decisions.md](./decisions.md)). `.app-main:has(.auth-page)` (descendant, not direct-child - `RegistrationPage` nests `.auth-page` one level inside its own wrapper `<div>`, `LoginPage` renders it as the top-level element, so a `>` combinator would only catch one of the two) zeroes `.app-main`'s vertical padding specifically on these pages so `.auth-page`'s `min-height: 100vh` fills the viewport with no grey gap top or bottom; an earlier attempt used negative margins to cancel that padding instead, but the negative margins fed back into `.app-main`'s own flex-computed height and overshot the viewport, so `:has()` replaced it. The real DILG seal (`frontend/public/dilg-logo.webp`, user-supplied - not fabricated) appears crisp and small atop the login/account card, and twice more, large and blurred, in opposite corners as background texture - positioned off-center since a single centered copy would just sit directly behind the card and be invisible (an intermediate version tiled it across the whole panel instead, which read as busy/repetitive and was reverted to two big copies).

`Layout` also drops the top nav bar entirely on these same two screens (`hideHeader` in `Layout.tsx`, keyed on `pathname === "/login"` or `pathname === "/register" && !isAuthenticated`) for a fully immersive full-page look - the nav there would only ever offer "Log in"/"Register" links pointing at wherever the visitor already is. Since that removes the only way to get from one to the other, `LoginPage`/`RegistrationPage` each carry their own small `.auth-switch` cross-link ("Don't have an account? Register" / "Already have an account? Log in") inside the card itself. `.auth-form` also needed an explicit `width: 100%` (not just `max-width: 400px`) - as a flex item of `.auth-page` (a flex container) it otherwise shrinks to fit its own content rather than filling up to the max-width, which visibly under-sized the login card (shorter copy) relative to the registration card (longer copy) even though both shared the same CSS rule.

Routing (`App.tsx`) uses `react-router-dom`; `ProtectedRoute` redirects unauthenticated users to `/login`, and `HomeRedirect` sends `/` to the right role-specific landing page.

`ProtectedRoute` and `HomeRedirect` also gate on `AuthUser.mustChangePassword`, the same "no other page is reachable until this is resolved" pattern as `registrationComplete` above, but role-agnostic and unconditional (any role, no false/null distinction - it's a plain boolean returned directly on the `user` object from `/login`/`/register`, no extra fetch needed unlike `registrationComplete`, which requires `GET /api/applicants/me`). Both redirect to `/account/password`; `ProtectedRoute` additionally checks `useLocation().pathname !== "/account/password"` first, since without that exemption the gate would redirect the change-password page to itself. See "Forgot password (applicants)" below.

### Forgot password (applicants)

`POST /api/auth/forgot-password` (`AuthService.forgotPassword`, `backend/src/modules/auth/`) issues a random 12-character temporary password (`generateTemporaryPassword()`, `shared/utils/password.ts` - `crypto.randomInt`, excludes visually ambiguous characters since it's read off an email and retyped), hashes it the same way a normal password is hashed, saves it, sets `User.mustChangePassword = true`, and emails it (`temporaryPasswordEmail`, a new `authEmailTemplates.ts` alongside the existing `applicationEmailTemplates.ts`). Scoped to `APPLICANT` accounts only and always returns 204 regardless of outcome - unknown emails and non-applicant accounts are silent no-ops - so the endpoint can't be used to enumerate registered emails or to force-reset an admin/panel account (see [decisions.md](./decisions.md)).

Logging in with the temporary password works exactly like a normal login (`PATCH /me/password`'s `currentPassword` check doesn't care whether the "current" password was applicant-chosen or system-issued) - the only difference is `AuthResponseDto.user.mustChangePassword` comes back `true`, which `ProtectedRoute`/`HomeRedirect` (see above) use to force a redirect straight to `/account/password` before anything else in the app is reachable. `ChangePasswordPage` reads `user.mustChangePassword` to swap its "Current password" label to "Temporary password" and show a short explanatory line, and - only in the forced case - calls `clearMustChangePassword()` (a local `AuthContext` state update, not a server round trip; there's no `GET /me` to re-fetch from) and navigates to `/` on success, letting `HomeRedirect` route to the applicant's actual home. `AuthRepository.updatePassword()` (used by both the forced and voluntary change paths) always clears `mustChangePassword` server-side too, so the flag can't survive a completed change even if the frontend's local clear were somehow skipped.

## Database

See [database.md](./database.md) for the full schema. Summary: `User` (auth) 1:1 `Applicant` (profile) 1:N `WorkExperience`/`LdIntervention`/`Award`/`Document`; `Applicant` N:M `JobPosting` through `Application`; `User` also 1:N `JobPosting` (creator), `Application` (evaluator), and `AuditLog` (actor) — all three nullable/`SetNull` so deleting a user never blocks on, or cascades into, those records.

## Dashboard (cross-cutting)

`DashboardRepository` (`backend/src/modules/dashboard/dashboard.repository.ts`) queries `User`/`Applicant`/`JobPosting`/`Application` directly via Prisma `groupBy`/`count` rather than going through each feature's own repository - it's a read-only reporting concern, not a write path any other service depends on, the same reasoning that keeps `AuditLogsRepository` a direct Prisma consumer. `DashboardService`'s `tally()` helper fills every status key with 0 before overlaying `groupBy`'s results (which only emit rows for combinations that actually exist), keyed off three hand-maintained lists in `dashboard.dto.ts` (`APPLICATION_STATUSES`/`JOB_POSTING_STATUSES`/`USER_ROLES`) that must stay in sync with their Prisma enum - `dashboard.dto.test.ts` asserts each list's value set matches `Object.values()` of the corresponding Prisma-generated enum object, a regression test for a real 2026-08-19 bug where `APPLICATION_STATUSES` had silently fallen 5 statuses behind `ApplicationStatus` (missing every status the Compliance to Requirements/Oath-Taking phases added, `HIRED` included) - see [decisions.md](./decisions.md). `DashboardService` additionally takes `AuditLogsRepository` as a second constructor dependency purely to reuse its existing `findMany` for the "recent activity" feed, rather than duplicating that query. The frontend (`DashboardPage`, `/admin/dashboard`, now the admin role's landing page in place of `/admin/jobs`) renders the single `GET /api/dashboard/summary` response as a stat-tile row, two inline-SVG pie charts (applications by status; top job postings by application count - both built by hand, no charting library, sharing one `PieChart` component), and a recent-activity table reusing `AuditLogsPage`'s row shape. `PieChart` (`DashboardPage.tsx`, takes a required `ariaLabel` prop since it's now reused for two differently-titled charts) only renders a slice per row with at least one application (most of the applications-by-status chart's 11 possible statuses are empty at any given time - rendering zero-width slices would only add legend clutter), direct-labels a slice's percentage only past an 8%-share threshold to avoid label collisions on a chart that can have several thin slices, and always renders a legend below it (swatch + label + exact count) as both the ≥2-series identity source and the exact-numbers fallback. The applications-by-status chart's slice colors reuse the same hues as the `.badge` classes elsewhere in the app (success/warning/info/danger/muted) rather than a separate chart palette, so a status reads the same color whether it's a badge or a pie slice; the top-job-postings chart has no such semantic identity per posting, so it cycles a fixed 5-hue categorical palette (`CATEGORICAL_CHART_COLORS`, validated colorblind-safe per the `dataviz` skill) instead - the always-shown text legend covers the "relief rule" gap since the backend caps `topJobPostings` at 5 entries (`TOP_JOB_POSTINGS_LIMIT`, `dashboard.service.ts`) but the palette itself only guarantees adjacent-pair CVD-safety for 3.

## Interview panel & CompAss tabulation

Three modules implement the real multi-evaluator Evaluation phase the spec describes, replacing the single-admin-score stand-in flagged as deferred scope in [decisions.md](./decisions.md)'s 2026-08-07 entry:

- **`categories`** (was `evaluation-criteria`, renamed 2026-08-19 - see [decisions.md](./decisions.md)) — admin-editable interview rubric, two levels deep: `Category` (top-level grouping, e.g. "Communication Skills") has many `Criterion` rows (the individually-scored rubric lines within it, e.g. "Clarity of response", each with its own `maxScore`). A panelist scores every `Criterion`, never the `Category` as a whole. `Category.weightPercent` (added same day as a same-day follow-up, per client request - see [decisions.md](./decisions.md)) is the category's admin-set, authoritative share of the overall evaluation (e.g. `25` = 25%) - **independent of `maxScore`**, which stays a purely-derived, purely-internal number: the sum of the category's own active criteria's `maxScore`, computed at read time (`CategoriesRepository`) so it can never drift out of sync with its children. A category worth 25% contributes exactly 25% whether it has one criterion or ten, whether they sum to 10 raw points or 1000 - see "Weighted scoring" below. `CategoriesRepository.update()` diffs an incoming criteria array against what's on file (update-in-place for entries with an `id`, create for those without, remove anything missing) instead of the old questions convention's blind delete+recreate - a `Criterion` can carry real historical `PanelScore` rows now, so removing one that already has scores is blocked (409), directing the admin to set `isActive: false` instead, the same "deactivate instead" shape `Category`'s own delete guard already used.
- **`panel-assignments`** — pure M:N metadata (`PanelAssignment`: `jobPostingId` × `panelUserId`) admin manages per posting. No cascading write side-effects; deleting a posting or a panel user just drops the row. `POST .../bulk` (`{ jobPostingIds, panelUserIds }`) assigns every listed panelist to every listed posting in one call, add-only (skips pairs already assigned, never removes) — backs `PanelAssignmentsPage`'s row-multi-select "Assign Panel to Selected" action, since each selected applicant resolves to its posting and the actual write target is always a posting's roster, not the applicant row itself. See [decisions.md](./decisions.md)'s 2026-08-11 "Bulk panel assignment" entry.
- **`panel-evaluations`** — the scoring itself. `PanelEvaluation` (one row per panelist per application, unique on `[applicationId, panelUserId]`) has child `PanelScore` rows - one per **criterion** (the leaf, not the category); `PanelEvaluationsRepository.upsertEvaluation` wraps the upsert-header + delete-and-recreate-children in a `$transaction`. The service cross-checks against `PanelAssignmentsRepository` (is this panelist assigned to this application's posting?) and `CategoriesRepository` (every active category's every active criterion scored, no score over its own `maxScore`) — both injected directly, the same cross-module-repository-reuse pattern `ApplicationsService` already uses for `DocumentsRepository`/`JobPostingsRepository`.

**Status flow**: `Application.status` runs `SUBMITTED` → `UNDER_SIFTING` (automatic, the instant an application is created) → `QUALIFIED`/`NOT_QUALIFIED` (the Sifting phase's pass/fail call, `PATCH /applications/:id/sift`, gated to `UNDER_SIFTING`) → PQE score recorded on a `QUALIFIED` application via `POST /applications/import-exam-scores` (an Excel import matched by name, doesn't move `status`) → `FOR_INTERVIEW` (`PATCH /applications/:id/schedule-interview`, gated to `status === QUALIFIED` **and** a recorded `examinationScore`). This reworks what was originally a single free-standing `PATCH /applications/:id/evaluate` action (any status → `QUALIFIED`/`NOT_QUALIFIED`, no gating) into the actual Sifting/PQE/Interview sequence the domain spec describes - see [decisions.md](./decisions.md)'s 2026-08-08 "Sifting/PQE/Interview pipeline" entry. Panel-scoring completeness still isn't a precondition anywhere in this chain (an admin can schedule an interview before every assigned panelist has scored a *previous* application) - `EvaluateApplicantsPage` fetches `GET /panel-evaluations/tabulation/:jobPostingId` alongside the applications list and shows a `panelistsSubmitted < panelistsAssigned` warning inside `EvaluationRow`'s details modal's panel-score summary.

**Weighted scoring**: `PanelEvaluationsService`'s `weightedCategoryScore(rawSubtotal, rawMax, weightPercent)` and `weightedTotalScore(evaluation, categories, criterionIdsByCategory)` (both exported for unit testing, `panel-evaluations.service.test.ts`) are the arithmetic core of everything below. For one panelist's evaluation, a category's raw subtotal (the sum of just that panelist's scores across the category's own criteria) is normalized against the category's raw max (`category.maxScore`) and scaled to `weightPercent`: `rawMax > 0 ? (rawSubtotal / rawMax) * weightPercent : 0`. A panelist's overall score for an application is the sum of every category's weighted contribution, not a flat sum of raw `PanelScore`s - a category with many high-point criteria no longer outweighs one with a single low-point criterion, as long as both carry the same `weightPercent`. If every active category's weights sum to 100, this total is out of 100; the app never enforces that sum (a soft-check UI hint on `CategoriesPage` only, not a hard gate), so keeping weights meaningful together is on the admin.

**Tabulation (CompAss)**: `PanelEvaluationsService.tabulation()` computes the ranked matrix in application code rather than SQL — each panelist's *weighted* total per application (see above), averaged across panelists who've submitted, sorted descending, rank assigned (unscored applications rank `null`, sort last). A missing panelist simply means fewer values feed that average, never a blocker - the average is always over however many panelists actually submitted, not a fixed denominator, so one missing score never prevents a total from being reported. `EvaluateApplicantsPage` renders this as two extra table columns ("Panel Avg", "Rank") rather than a separate matrix view, so the tabulation always sits next to the finalize action it's meant to inform.

**Applicant Scores (cross-posting, per-category)**: `CategoriesPage` has an "Applicant Scores" button opening `ApplicantScoresModal` (`frontend/src/features/admin/components/ApplicantScoresModal.tsx`), backed by `GET /panel-evaluations/applicant-scores`. Where `tabulation()` is scoped to one posting and computes a rank server-side, `PanelEvaluationsService.applicantScoresOverview()` scans every posting at once (`PanelEvaluationsRepository.findApplicationsWithScores()` — same `TABULATION_STATUSES` set, plus `panelEvaluations: { some: {} }` to exclude unscored applications) and returns each applicant's average *weighted* score per active **category** (each panelist's weighted contribution to that category, averaged across panelists) and average weighted total, unranked. Column headers show `weightPercent` (e.g. "Battery Test (0-25)"), not the raw `maxScore`, since that's the actual ceiling the weighted number in each row can reach. Ranking is entirely client-side: a "Rank by" `<select>` (overall total, or any one active category) drives `rankRows()`, a `useMemo`'d sort recomputed on every selection change, paginated 10/page via the existing `usePagination` hook and rendered in the shared `Modal`'s existing `extraWide` variant. This is a deliberate split from `tabulation()` — see [decisions.md](./decisions.md)'s 2026-08-11 "Applicant Scores overview" entry for why ranking moved to the frontend here specifically.

**Report Summary (cross-posting, per-category and per-criterion, table only)**: added 2026-08-21, per client request that an admin see interview results "combined from all the panels" broken down by Category *and* Criterion, with no per-panelist visibility anywhere and no prose/expand-based presentation - "the wordings" (per-row descriptive text like "Category: 20 of 25" / "Criterion: 8 (0-10)") were the thing the client didn't want, not the underlying data. `ReportSummaryPage` (`frontend/src/features/admin/pages/ReportSummaryPage.tsx`, `/admin/report-summary`) reuses the exact same `GET /panel-evaluations/applicant-scores` endpoint `ApplicantScoresModal` does - `applicantScoresOverview()` computes `perCriterion` per row (each active criterion's raw, unweighted score, averaged across submitted panelists the same way `perCategory` already was) and a top-level `criteria` list (`{ id, categoryId, name, maxScore }`) alongside the existing `categories` list. The page itself is a full admin page, not a modal (unlike `ApplicantScoresModal`), with no ranking control - it's a report, not a leaderboard: a single wide table, one row per scored application, one column per active category *and* one column per active criterion (both combined/averaged figures), plus an overall combined total - no expand/collapse, no nested cards, no per-item sentences, just table cells. Went through several false starts before settling here, all same-day: a per-row "Criteria" expand button revealing prose per criterion; that same prose always-visible with no button; the whole breakdown dropped to category-only; then the client clarified none of those were what they meant - they wanted the criterion data, just as table columns rather than any prose form. `.table-wrap`'s existing horizontal scroll (already relied on elsewhere for wide tables) handles the resulting column count, which scales with however many criteria are currently active. Deliberately never surfaces `tabulation()`'s per-panelist `perPanelist` map anywhere in this page's data path - an admin who needs that specific breakdown already has it in Evaluate Applicants' CompAss tabulation view, which this page doesn't replace.

**Report Summary: grouped two-row header + sticky Applicant column** - added same day, per follow-up client request to make the flat category-then-criterion column layout above scale to "all the criteria" without losing which criterion belongs to which category, and to keep the applicant identifiable while scrolling. `ReportSummaryPage.tsx` groups `overview.criteria` by `categoryId` client-side (`groupCriteriaByCategory()` - the array already arrives grouped/ordered by category from `applicantScoresOverview()`, this just buckets it into a `Map` for rendering) and renders a two-row `<thead>`: row one has one `<th>` per category, `colSpan`'d over that category's own criterion columns plus a trailing "Score" column (the existing weighted `perCategory` figure, now nested under its category instead of standing alone); row two has the actual per-criterion `<th>`s, abbreviated `CR1`, `CR2`, ... **numbered per category** (each category's first criterion is `CR1`), with the criterion's full name and raw max (e.g. "Panel Poise (0-10)") as a native `title` tooltip rather than in visible text - keeps the header compact while the full wording is still one hover away. The Applicant column (`th`/`td.sticky-col`, `frontend/src/shared/styles/index.css`) is `position: sticky; left: 0`, opaque against both the default and `:hover` row backgrounds so it doesn't show scrolled-past columns bleeding through, with a drop-shadow standing in for a border (plain `border` doesn't render reliably on a sticky cell under `border-collapse: collapse`). No other cell is sticky - Job posting, Total, and Panelists submitted scroll away with the rest, by design, since only "who does this row belong to" needs to stay pinned.

**Report Summary: color** - added same day, per client feedback that the plain black-on-white table was hard to read at a glance ("put color not just plain... currently doesn't like how it looks"). ## Multi-posting applications & panel score inheritance (Phase 1)

Added 2026-08-21 per client request: "Applicants can Apply Multiple Job posting as long as Applicant is not hired and the Panel points will automatically counted in all the Applicants applied jobs so that the applicant will not be evaluated in each job." (The hierarchy/auto-hire-recommendation half of that request is Phase 2, below, built the same day.) Before this, nothing in the codebase actually blocked multiple applications or applying after being hired - it "worked" only by omission, and `docs/rsp-domain-spec.md` line 79 already says applicants "may apply for different positions at once." What was missing was: (1) an explicit gate once an applicant is actually hired somewhere, and (2) not making a multi-posting applicant sit through a separate interview per posting.

**Why a pointer, not copied rows**: `Category`/`Criterion` (the rubric) are global, not per-posting (see Known Limitations below), so a score computed once is numerically valid anywhere - nothing rubric-specific differs by posting. But `PanelAssignment` *is* per-posting, so a sibling posting's actual assigned panel never scored this applicant; physically duplicating `panel_scores` rows under a borrowed panelist id would misattribute authorship in audit logs and that panelist's own history. Instead, `Application.scoreSourceApplicationId` (nullable self-relation, migration `20260821000001_add_application_score_inheritance`) points at whichever of the applicant's applications actually holds the real `PanelEvaluation` rows - see `docs/database.md`'s `applications` section for the full column writeup, and `docs/decisions.md`'s 2026-08-21 entry for the alternatives considered.

**Where it's set**: `ApplicationsRepository.createWithApplicationLetter()` resolves and sets it *at creation time* for a brand-new application (via a new private `resolveScoreSourceForApplicant()`, inside the existing create transaction) if the applicant already has a scored or already-inheriting application - so a second/third application never even reaches a panel's queue needing its own interview. `PanelEvaluationsRepository.linkSiblingScoreSources()` does the mirror case: called from `PanelEvaluationsService.submit()` right after a real `upsertEvaluation()` succeeds, it propagates that score to every *existing* open sibling application that doesn't already have its own evaluation or an existing link. Both paths converge on the same invariant: the pointer always references a canonical (never-inheriting) application directly, never chained through another inheriting one.

**Where it's read**: every consumer of "this application's panel evaluations" resolves the pointer before returning - `PanelEvaluationsRepository.findApplicationsForTabulation()` and `findApplicationsWithScores()` both call a new private `resolveInherited()`, which does exactly one extra batched query (`panelEvaluation.findMany({ where: { applicationId: { in: sourceIds } } })`) regardless of how many applications in the result set are inheriting - no N+1. The batching/merging logic is split into two exported pure functions, `collectScoreSourceIds()`/`mergeInheritedEvaluations()` (`panel-evaluations.repository.ts`), unit-tested without a database in `panel-evaluations.repository.test.ts`, matching this file's existing `assignCompetitionRanks`/`weightedTotalScore` pure-function convention. `findQueueForPanelUser()` excludes inheriting applications outright (`scoreSourceApplicationId: null` in its `where`) so no panelist is ever shown one to score; `PanelEvaluationsService.submit()` also refuses (400) to score an inheriting application directly, a defensive backstop for a stale client reference to an applicationId that's since been linked.

**The HIRED gate**: `ApplicationsService.submit()` now 409s if the applicant already has any `HIRED` application (`ApplicationsRepository.hasHiredApplication()`) - checked before the posting/eligibility checks, since it's an applicant-scoped rule, not a posting-scoped one. `WITHDRAWABLE_STATUSES` (service-local) became `OPEN_APPLICATION_STATUSES`, moved to and exported from `applications.repository.ts` - same six statuses, now the single source of truth both this gate's sibling-repository code and the withdraw guard use, rather than two independently-maintained lists that could drift.

**Frontend**: `JobPostingsListPage.tsx` tracks `hasHiredApplication` from the applicant's own fetched application list and gates the Apply button ("Already Hired") plus a page-level hint banner, the same shape as the existing `alreadyApplied`/`appliedJobPostingIds` guard. `MyApplicationsPage.tsx` shows a `field-hint` line ("Interview score carried over from your application to \"X\"") when `application.scoreSourceApplication` is set (added to `applicationWithPostingInclude`/`ApplicationWithPosting` so `GET /applications/me` carries it for free).

**Verified**: end-to-end against the real local database using a temporary second applicant + two temporary job postings (deleted after) exercising the actual repository/service classes directly - creation-time inheritance, existing-sibling propagation via `linkSiblingScoreSources`, the `submit()` guard on an inheriting application, panel queue exclusion (plus an unlink/relink sanity check to confirm the exclusion is the filter doing something, not coincidence), and `findApplicationsForTabulation`/`findApplicationsWithScores` correctly resolving inherited scores - 15/15 assertions passed. The HIRED gate and "Already Hired" UI were also confirmed live in the browser against the one real HIRED applicant in this environment (a minted JWT was used to view the applicant-facing pages without touching their actual password).

**Phase 2 - hierarchy hire recommendation + auto-close on hire**: also added 2026-08-21, same day. Client requirement: "if applicant passed in all the Job Posting he applied he will be hired in the Higher position or Higher SG level." "Higher position" resolves to the highest numeric `JobPosting.salaryGrade` - the only structurally comparable field on `JobPosting`/`Position` (`positionNextInRank` is free-text, not a rank). New pure `computeHireRecommendations()` (`frontend/src/features/admin/utils/hireRecommendation.ts`, unit-tested in `hireRecommendation.test.ts` - including a regression test for `"9"` vs `"10"` as strings vs. `parseInt()`) groups an applicant's applications, and for any applicant with 2+ currently at `FOR_OATH_TAKING`, flags the highest-SG one as recommended and every other as "a higher one exists elsewhere." Computed purely client-side (`useMemo` in `EvaluateApplicantsPage.tsx`) from data that page already fetches unfiltered across every posting - no new endpoint. `EvaluationRow.tsx` shows a `field-hint` recommendation banner (with the SG value) on the recommended row's Details modal, a `field-warning` caution on every other affected row's Details modal, and the same caution inside the Mark Hired `ConfirmDialog`'s description for a non-recommended row, so the warning is visible at the moment of the actual (irreversible) action, not just earlier on the page.

This stays a **recommendation only** - per the earlier confirmed decision, the system never auto-flips a status; the admin still clicks Mark Hired themselves, on whichever posting they choose (the recommendation doesn't block hiring a lower-SG one if there's a business reason to). Once they do, `ApplicationsService.markHired()` (extended, not a new method) fetches the applicant's other still-open applications (`ApplicationsRepository.findOpenSiblings()`, scoped to `OPEN_APPLICATION_STATUSES`) and closes every one of them to `NOT_SELECTED` in one transaction (`bulkRejectNotSelected()`), each with a system-generated `rejectionRemarks` naming the posting they lost to and its Salary Grade, an `APPLICATION_NOT_SELECTED` audit log entry, and a `regretEmail()` - reusing the existing status/audit-action/email machinery rather than adding new ones, consistent with the "no new `ApplicationStatus`" decision. An application already in a terminal status (e.g. `WITHDRAWN`) is left untouched, since it's outside `OPEN_APPLICATION_STATUSES`. `EvaluationRow`'s `handleMarkHired()` now also calls a new `onHired()` prop (wired to `EvaluateApplicantsPage`'s `loadAll()`) after a successful hire, since the auto-closed siblings may live on entirely different postings/pagination pages that this one row's local state patch can't reach.

**Verified (Phase 2)**: backend - a second temporary-data script exercising `ApplicationsService.markHired()` directly (two open siblings at different Salary Grades, one already-`WITHDRAWN` sibling as a negative control) confirmed the hired application reaches `HIRED`, the open sibling auto-closes to `NOT_SELECTED` with remarks naming the correct posting/SG, the `WITHDRAWN` one is left untouched, and both relevant audit log entries are recorded - 6/6 assertions passed. Frontend - `computeHireRecommendations()` unit tests, 5/5 passed. Full flow also confirmed live in the browser end-to-end (admin session via a minted JWT, temporary applicant + two postings at SG 8/18 both reached `FOR_OATH_TAKING`): the recommendation banner correctly named the SG 18 posting, clicking Mark Hired on it flipped its row to `HIRED` and the SG 8 sibling row to `NOT_SELECTED` in the same table with no page reload, confirming `onHired()`'s refetch works as designed. All temporary data deleted afterward.

**Follow-up (2026-08-21): two bugs found in manual testing after Phase 1 shipped.**

*"Duplicate interviews."* The two linking points above (`resolveScoreSourceForApplicant()` at creation time, `linkSiblingScoreSources()` at scoring time) both fire on an *event* - neither retroactively repairs a pair of applications that both reached `FOR_INTERVIEW` *before either was scored*, since at that moment neither creation nor scoring had anything to link to. Two different panels could then independently score the same applicant. Fixed with a repair pass rather than a third event hook (an event-hook approach would just move the same race to a different pair of moments): `PanelEvaluationsRepository.findQueueForPanelUser()` now runs a private `repairAndExcludeAlreadyScoredElsewhere()` after its existing `scoreSourceApplicationId: null` filter - one batched query (`applicantId IN (...)`, grouped to the earliest-submitted scored application per applicant) checks every remaining queue candidate for a sibling that's since been scored, links (`scoreSourceApplicationId`) and excludes any match instead of leaving it open to be scored again. The link/exclude decision itself is a new exported pure function, `partitionQueueCandidatesToRepair()`, unit-tested the same way as `collectScoreSourceIds`/`mergeInheritedEvaluations`. A second, symmetric fix closes the write-side of the same race (two panelists submitting around the same moment): `PanelEvaluationsService.submit()` now calls a new `PanelEvaluationsRepository.reconcileScoreSource()` right before writing a score - a fresh query (not the possibly-stale stored field) that links and refuses if the applicant has since been scored elsewhere.

*Confusing `MyApplicationsPage`.* Reported as "I'm in Compliance to Requirements but I only see Evaluation of Applicants details, no upload." This turned out not to be a rendering bug - `MyApplicationsPage.tsx`'s `COMPLIANCE_VISIBLE_STATUSES` gate was already working correctly per-application. The actual gap: score inheritance only ever shares the *interview score*, never the pipeline `status` itself - Compliance/Oath-Taking still advance one posting at a time, by admin action on that specific application, so an applicant with two open postings sharing one interview score can genuinely have one card at `FOR_COMPLIANCE` and the other still at `FOR_INTERVIEW`. The still-`FOR_INTERVIEW` card gave no hint that a sibling existed and had moved further along, so it read as broken rather than "check your other application." Fixed by surfacing the self-relation's inverse side - `Application.scoreInheritingApplications` (declared alongside the forward field already, no new migration) - through `GET /applications/me`, and adding a matching hint on the canonical card: "This interview score is also being used for your application to "X" (currently \<status\>)", mirroring the inheriting side's existing "carried over from" hint.

**Verified (follow-up)**: race-condition fix - a temporary-data script exercising the actual repository methods directly (4 temporary postings/panelists across two applicant scenarios, deleted after) reproduced the exact race and confirmed both the queue repair and the write-time reconciliation correctly link and exclude/refuse - 5/5 assertions passed; also covered by 4 new unit tests for `partitionQueueCandidatesToRepair()`. `MyApplicationsPage` fix - confirmed live in the browser (minted-JWT session, temporary applicant with one `FOR_INTERVIEW` and one `FOR_COMPLIANCE` application sharing an inherited score, deleted after): the `FOR_COMPLIANCE` card's checklist/upload UI was already correct, and the `FOR_INTERVIEW` card now shows the new hint naming the sibling posting and its live status. All temporary data deleted afterward.

**Same-day follow-up: consolidate a multi-posting applicant into one row/card everywhere, and replace the automatic hire recommendation with a manual pick.** Client feedback after using the feature above: "I should only see one Application status in My Application page and for Admin I should only see one Applicant data, one to evaluate and one to score in Panel... in selecting the position the admin wants for the Applicant other job posting that the applicant applied will be free for others to apply... this is manual from Admin no need to assign the highest SG automatically." Deliberately kept the data model exactly as-is (still one `Application` row per applicant-posting pair) - this is a view-layer consolidation across four screens plus one small backend field addition, not a schema change.

*Design call: default-collapsed grouped rows, not a redesigned per-posting action model.* Sifting, PQE entry, Schedule Interview, and Compliance review are genuinely per-posting actions (different postings can have different qualification standards and compliance checklists) - flattening them into one button per applicant isn't viable. Instead, `EvaluateApplicantsPage.tsx` groups its already-fetched cross-posting application list by applicant (new generic `groupByApplicant()`, `frontend/src/shared/utils/groupByApplicant.ts`, unit-tested) *before* paginating - a single-posting applicant's row is untouched, a multi-posting applicant collapses into a new `ApplicantGroupSummaryRow` (collapsed by default, expand-on-click reveals the unchanged per-posting `EvaluationRow`s). When the admin narrows the Job Title filter to one specific posting, every group is naturally a singleton (`@@unique([applicantId, jobPostingId])` guarantees at most one application per posting per applicant), so the table reads identically to the old flat view with no special-casing required - filtering to "I want to do this posting's Sifting" and the new grouped "how is this applicant doing overall" view are simply the same code path at different filter states.

*The automatic highest-Salary-Grade recommendation is removed, not just hidden.* `hireRecommendation.ts`'s `computeHireRecommendations()` (ranked candidates, picked a "recommended" winner) is deleted outright and replaced by a neutral `oathTakingCandidates.ts`'s `findOathTakingCandidates()` - groups+filters only (2+ of an applicant's applications at `FOR_OATH_TAKING`), never ranks. A new `AssignPositionModal` (opened from the summary row's "Assign Position" button, shown only when that 2+ condition holds) lists every qualifying posting with **no default selection** - Confirm stays disabled until the admin makes an explicit choice, and the options are shown in whatever order the applications happen to be in, deliberately not sorted by Salary Grade. No new backend endpoint was needed: `ApplicationsService.markHired()` (built in the Phase 2 work above) was already exactly "hire this one application, auto-close every other of the applicant's still-open applications to `NOT_SELECTED`" - the modal just lets the admin pick *which* application id to call it with, instead of that choice being implicit in whichever row they happened to have open. Individual `EvaluationRow`s caught in a 2+-way group have their own Mark Hired button hidden (with an explanatory note) so the consolidated modal is the only path once there's a real choice - this closes a gap the pure-recommendation design left open, where an admin could still click Mark Hired directly on a non-recommended row and bypass the hint entirely.

*`MyApplicationsPage`* needed no new grouping key (an applicant viewing their own applications is already scoped to one person) - `applications.length <= 1` is unchanged; 2+ renders one outer card ("You've applied to N job postings") containing one `.posting-subsection` per application (new CSS: a left-accent-bordered block, chosen over reusing `.card-inset` again to avoid a double-boxed look, since the existing interview/compliance/oath-taking detail blocks already use `.card-inset` and now nest one level deeper). This directly supersedes today's earlier "keep separate cards, add a cross-reference hint" decision (see `docs/decisions.md`) - the two hint lines that decision added are replaced by one "Your interview score is shared across all the applications below" line at the top of the unified card, since the redundancy those hints existed to bridge no longer exists once everything's visibly in one place.

## Group Dynamics Evaluation

`applicant-groups` is a small standalone module (not part of the three interview-panel modules above, and not covered by `docs/rsp-domain-spec.md`) admin-created ad hoc groupings of applicants for the "Group Dynamics Evaluation" activity - per client request: "Admin can Group applicants ... same setup with Interview Panel page where we have checkbox and instead of Assign Panel button it will be Group and it will open a modal for the name of group and description." `ApplicantGroup` (`name`, `description?`) has many `ApplicantGroupMember` rows, each pointing at one `Application` - a group carries no `jobPostingId` of its own (unlike `PanelAssignment`), since a single group exercise can mix applicants from different postings.

`GroupsPage` (`frontend/src/features/admin/pages/GroupsPage.tsx`, `/admin/groups`, "Group" in the sidebar) deliberately mirrors `PanelAssignmentsPage`'s applicant table and checkbox-selection mechanics (search/job-posting/publication filters, header "select all," a bulk action bar) rather than introducing a new selection pattern - the one behavioral difference is the bulk action itself: instead of opening a panel-member picker, the "Group" button (disabled until at least 2 applicants are selected - a group of one isn't a group) opens a two-field modal (name, description) and `POST /api/applicant-groups` creates the group directly from the current selection, no intermediate confirmation screen. A "Group(s)" column on the applicant table shows which group(s) (by name) each applicant already belongs to, the same role `PanelAssignmentsPage`'s "Assigned Panel" column plays. Below the applicant table, a second table lists every created group (name, description, member names, created date) with Edit/Members/Delete actions - `PATCH /api/applicant-groups/:id` renames/redescribes a group (reusing the same create modal in edit mode), `DELETE` removes it and cascade-deletes its members.

**Membership editing** repurposes the same applicant table/checkbox mechanism rather than a separate member-picker widget: clicking a group's "Members" action seeds `selectedApplicationIds` with that group's current member application ids and sets a `membershipEditingGroup` state, which swaps the bulk action bar's contents (selection-count text becomes `Editing members of "<name>"`, the "Group"/"Clear selection" buttons become "Save Members"/"Cancel") without changing the table itself - the admin checks/unchecks the same rows they'd use to build a new group, and "Save Members" sends the resulting full `applicationIds` list to `PATCH /api/applicant-groups/:id`, which diffs it against what's on file (add what's new, remove what's missing) the same way `CategoriesRepository.update()` diffs a category's criteria array. Renaming (`Edit`) and membership editing (`Members`) are deliberately two separate actions/buttons rather than one combined form, since the roster editor needs the full-width applicant table below it, not a compact modal field.

## Compliance to Requirements & Oath-Taking

Two more `ApplicationStatus` values continue the pipeline past `FOR_INTERVIEW`: `FOR_COMPLIANCE` and `FOR_OATH_TAKING`, ending in a terminal `HIRED`. There is no separate "Deliberation" status - the RD's decision to advance an applicant is a single admin action (`PATCH /applications/:id/move-to-compliance`), the same shape every other phase transition (`sift`, `scheduleInterview`) already is. See [decisions.md](./decisions.md)'s 2026-08-11 "Compliance to Requirements & Oath-Taking" entry.

## Regret letters (rejection past Sifting)

`FOR_INTERVIEW` and `FOR_COMPLIANCE` each have a rejection exit alongside their forward one, mirroring how `UNDER_SIFTING` already had `QUALIFIED`/`NOT_QUALIFIED`: `PATCH /applications/:id/not-selected` (`FOR_INTERVIEW` → `NOT_SELECTED`) and `PATCH /applications/:id/disqualify` (`FOR_COMPLIANCE` → `DISQUALIFIED`, no "every compliance item verified" precondition unlike `oath-taking`). Both stamp a shared `Application.rejectedAt`/`rejectionRemarks` pair and send `regretEmail()` — a template `applicationEmailTemplates.ts` also uses from `decisionEmail()`'s `NOT_QUALIFIED` branch, so all three rejection points (Sifting, Evaluation, Compliance) send the applicant the same voice, just with stage-specific wording.

These are separate statuses from `NOT_QUALIFIED` rather than a reused one, specifically so `ApplicationStageTracker.tsx` resolves the rejection on the stage node it actually happened at — its rejection check is a `REJECTION_STATUS_BY_STAGE` lookup keyed by stage rather than one hardcoded Sifting-only condition. See [decisions.md](./decisions.md)'s 2026-08-12 "Regret letters need their own statuses per stage" entry for the full rationale.

## Qualification-match hint (Sifting)

`JobPosting.qualificationEducation`/`qualificationTraining`/`qualificationExperience`/`qualificationEligibility` are free text with no applicant-side structured counterpart to compare against - only eligibility had one (`requiredEligibilityTypes`, a hard *submission* gate, unrelated to Sifting itself). Three optional structured minimums close that gap for Sifting specifically: `JobPosting.minEducationLevel` (an ordered `EducationLevel` enum), `minYearsExperience`, and `minTrainingHours` - each `null` by default, meaning "no automatic check," never a hard block. They're compared against the matching `Applicant` fields (`educationLevel`, a self-reported `yearsOfExperience`, and the sum of `LdIntervention.numberOfHours`) plus the existing `eligibilityType`/`hasEligibility`.

The comparison itself (`frontend/src/shared/utils/qualificationMatch.ts`'s `computeQualificationMatch()`) runs **client-side**, not on the server, and is never persisted or returned as its own API field - it's derived fresh, every render, from data `GET /api/applications` (and every sift/schedule/etc. response) already carries. This is deliberate: a server-computed field attached only by `listForAdmin()` would silently disappear from a row the instant any other endpoint (`sift`, `scheduleInterview`, …) replaced that row in the frontend's local state with a response that never computed it. Client-side computation can't go stale that way. `EvaluationRow`'s Sift modal renders the result as a "Qualification Standards" card - one line per free-text QS field, a "Meets"/"Below minimum"/"No automatic check" badge (reusing the existing `.badge.qualified`/`.badge.rejected`/`.badge.withdrawn` color classes), and, where a minimum is set, the applicant's actual value next to it. The badge is explicitly a decision aid: Sifting itself stays a human `QUALIFIED`/`NOT_QUALIFIED` judgment call against the free text, exactly as before this feature.

`Applicant.yearsOfExperience` is a single self-reported number, not a revived `WorkExperience` entries list - that table exists in the schema but is deliberately never collected (see `RegistrationPage.tsx`'s comment: it would duplicate the required PDS upload). See [decisions.md](./decisions.md)'s 2026-08-19 entry for the full rationale, including why the original "compute experience from `WorkExperience`" idea turned out to be unimplementable as first proposed.

- **`compliance-requirements`** — a new module holding two concerns: `ComplianceRequirementsRepository`/`Service`/`Controller`/`Routes` manage the admin-editable global catalog (`ComplianceRequirement`: `name`, `description`, `sortOrder`, `isActive` - mirrors `categories` minus scoring, `GET/POST/PATCH/DELETE /api/compliance-requirements`, `ADMIN`-only), and `ComplianceItemsRepository` (no service of its own - consumed directly by `ApplicationsService`) manages `ApplicationComplianceItem`, the per-application checklist row.
- **Snapshot, not live join, plus a manual escape hatch**: `ApplicationsService.moveToCompliance()` bulk-creates one `ApplicationComplianceItem` (status `PENDING`, submissionType `SOFTCOPY`) per currently-active `ComplianceRequirement` at the moment an application enters `FOR_COMPLIANCE` - a requirement added afterward won't retroactively appear on an already-in-progress applicant's checklist (documented limitation, not engineered around). If that snapshot comes up short (e.g. the catalog was empty, or missing a requirement that turns out to apply), `ApplicationsService.addComplianceItem()` (`POST /applications/:id/compliance-items`, `ADMIN`-only, body `{ requirementId, submissionType? }`) lets an admin attach one more catalog requirement directly to that one application - 400 unless the application is `FOR_COMPLIANCE`, 404 if the requirement doesn't exist, 409 if it's already on the checklist. This is what keeps an applicant from getting stuck at `FOR_COMPLIANCE` forever when the catalog had nothing active for them.
- **Submission type (Softcopy vs. Hardcopy)**: every item carries a `submissionType` (`ComplianceSubmissionType`: `SOFTCOPY` default, `HARDCOPY`) declaring how that one requirement is expected to reach the admin for this applicant - `SOFTCOPY` means the online proof-upload flow below, `HARDCOPY` means the applicant hands over a physical copy outside the system, so there's nothing to upload. An admin sets or changes it per item via `ApplicationsService.setComplianceItemSubmissionType()` (`PATCH /applications/:id/compliance-items/:itemId/submission-type`, `ADMIN`-only) - never the applicant, since a hardcopy submission by definition never touches the system for them to declare.
- **Proof upload**: applicants upload a `Document(type=COMPLIANCE_PROOF, complianceItemId=...)` per item via the existing generic `POST /applicants/me/documents` endpoint - the same one-slot-per-parent-entity pattern `LD_PROOF`/`AWARD_PROOF` already use, just keyed by `complianceItemId` instead of `ldInterventionId`/`awardId`. `DocumentsService.upload()` only allows this while the item's application is still `FOR_COMPLIANCE`. Only meaningful for `SOFTCOPY` items - a `HARDCOPY` item is never expected to get one.
- **Review**: `ApplicationsService.reviewComplianceItem()` (`PATCH /applications/:id/compliance-items/:itemId`, `ADMIN`-only) sets an item `VERIFIED`/`REJECTED`. `VERIFIED` requires both the applicant's submission and the admin's approval, never the admin's judgment alone: for a `SOFTCOPY` item, 400 unless a `COMPLIANCE_PROOF` document already exists ("nothing to verify yet" - flip it to `HARDCOPY` first if it was actually submitted physically); for a `HARDCOPY` item there's no online counterpart to check, so the admin's `VERIFIED` here is itself the record that the physical copy was received and approved. `REJECTED` carries no such precondition either way. `GET /applications/:id/compliance-items` (any authenticated role, ownership enforced for `APPLICANT` callers) is the one endpoint both the admin's `ComplianceReviewModal` and the applicant's `ComplianceChecklistSection` read from.
- **Oath-taking**: `ApplicationsService.scheduleOathTaking()` (`PATCH /applications/:id/oath-taking`) bundles the `FOR_COMPLIANCE` → `FOR_OATH_TAKING` transition with the ceremony's date/venue/notes in one action (mirrors `scheduleInterview()`), gated on every compliance item being `VERIFIED` (`ComplianceItemsRepository.countUnverified()`). `ApplicationsService.markHired()` (`PATCH /applications/:id/hire`) is the final, terminal transition for this pipeline segment - Onboarding itself (videos, pre/post evaluations) remains future work.
- **Frontend**: `EvaluationRow` gained "Move to Compliance"/"Manage Compliance"/"Schedule Oath-Taking"/"Mark Hired" actions alongside its existing sift/schedule-interview ones, following the same derived-boolean-per-status pattern. `ComplianceReviewModal` (admin) and `ComplianceChecklistSection` (applicant) are new, separate components rather than extensions of `ApplicantDocumentsModal`/`LdInterventionSection` - see [decisions.md](./decisions.md). `ComplianceReviewModal` renders an "Add a requirement" picker (sourced from `GET /compliance-requirements`, filtered to requirements not already on the checklist, paired with a Softcopy/Hardcopy selector for the new item) above the table to unblock the empty-checklist case, and a per-row "Submission" `<select>` (calling `setComplianceItemSubmissionType()`) letting the admin flip an item between Softcopy and Hardcopy at any time; the Verify button is disabled with an explanatory `title` for a Softcopy item with no uploaded proof yet. `ApplicationStageTracker` gained three more stage nodes; `ApplicationStatus`'s withdraw-eligibility list on both frontend and backend now includes `FOR_COMPLIANCE`/`FOR_OATH_TAKING` (an applicant can still withdraw up until actually hired).

## Audit logging (cross-cutting)

`AuditLogsRepository` (`backend/src/modules/audit-logs/audit-logs.repository.ts`) is injected into `UsersService`, `JobPostingsService`, `ApplicationsService`, `CategoriesService`, `PanelAssignmentsService`, `PanelEvaluationsService`, and `ApplicantGroupsService` the same way `DocumentsRepository` is injected into `ApplicationsService` — a repository consumed directly by another module's service, not wrapped in its own service layer for the write side. Each service calls `.record()` after a successful write (user/job-posting create-update-delete, application sift/exam-score-import/schedule-interview, category create-update-delete, panel assign/unassign, panel evaluation submit, applicant group create/update/delete) to append one `AuditLog` row. The read side (`GET /api/audit-logs`) goes through a thin `AuditLogsService` for query shaping. See [patterns.md](./patterns.md) and [decisions.md](./decisions.md) for why this is deliberately append-only with no update/delete path.

## What's implemented vs. planned

The **Application phase** (Applicant Registration + job posting browsing + application submission), **Sifting** (automatic `UNDER_SIFTING` on submit, admin pass/fail call against the qualification standards), **PQE score recording** (Excel import matched by applicant name - the exam itself is conducted outside the system, per the domain spec), a real multi-evaluator **Evaluation** capability (admin schedules a Qualified-with-PQE-score application for interview, an assigned interview board scores it against an admin-editable rubric, admin sees the ranked CompAss matrix), **Compliance to Requirements** (admin-managed documentary checklist, applicant proof upload, admin verify/reject) and **Oath-Taking** (scheduled, terminal `HIRED` status), a **Group Dynamics Evaluation** grouping tool (admin-created ad hoc applicant groups, outside the domain spec), and an **admin panel** (sidebar-navigated Dashboard, Users Management, Positions, Job Management, Categories, Compliance Requirements, Interview Panel, Group, Evaluate Applicants, History of Logs, ordered by data dependency — all full CRUD except the intentionally read-only logs) are implemented. Not implemented: letter/notice generation, the spec's 1:5 auto-shortlisting ratio, Deliberation's PDC-approval step as a distinct system state, Onboarding, L&D, and PDC/Permit-to-Study. See [project-memory.md](./project-memory.md) for the full status against the [RSP domain spec](./rsp-domain-spec.md).
