# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added
- Initial project scaffold: npm workspaces monorepo (`backend`, `frontend`).
- `CLAUDE.md` governance/workflow rules and `docs/` structure (architecture, api, database, patterns, decisions, project-memory, troubleshooting, rsp-domain-spec).
- Backend: Express + TypeScript API with feature-first Clean Architecture (`modules/{auth,applicants,job-postings,applications}`), Prisma ORM against MySQL, JWT authentication, centralized error handling, request validation (Zod), Pino logging.
- Frontend: React + TypeScript (Vite) SPA with feature-first structure, JWT-aware API client.
- Applicant Registration feature (Application phase of the RSP pipeline): account registration/login, demographic profile, work experience, learning & development interventions, eligibility checklist with proof upload, awards, IPCR/Designation-to-Higher-Position upload for promotional applications, job posting listing, and application submission.
- Local MySQL database provisioned (via XAMPP's bundled MariaDB) and initial Prisma migration applied, creating all tables per `docs/database.md`. Seed data adds one admin user and two sample job postings.
- Applicant Registration wizard now auto-advances to the next step when the demographic profile is first created, and every step has Back/Next navigation (`frontend/src/features/applicant-registration/pages/RegistrationWizardPage.tsx`).
- Admin panel, separated from the applicant experience by role-gated routing (`/admin/*` vs `/jobs`, `/registration`, `/applications`): a "Post a Job" page and an "Evaluate Applicants" page (score 0-100, qualified/not-qualified decision, remarks per application). Backend: `evaluationScore`/`evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` added to `Application`, plus `GET /api/applications` (admin listing, optionally filtered by job posting) and `PATCH /api/applications/:id/evaluate` (both `ADMIN`-only). Frontend: new `admin` feature, and `ProtectedRoute` gained a `role` prop enforced on both the admin and applicant route groups.
- Fixed an auth race condition where an already-logged-in user landing on `/` was bounced to `/login` and stuck there (session hydration from `localStorage` happened after route guards had already decided). `AuthContext` now exposes `isLoading`; `ProtectedRoute`/`HomeRedirect` wait on it.
- Admin panel redesigned around a sidebar shell (`AdminShell`) with four sections, and full CRUD added for Job Management and (new) Users Management, plus a new read-only History of Logs section:
  - **Job Management**: `JobManagementPage` replaces the old create-only "Post a Job" page with a data table (Edit/Delete per row, inline delete confirmation, no native browser dialogs). Backend: `PATCH`/`DELETE /api/job-postings/:id` (`ADMIN`-only); deleting a posting with existing applications is blocked (409) to prevent silent data loss via cascade.
  - **Users Management** (new): `UsersManagementPage` - admin-provisioned account creation (including new admins), role/email editing, deletion with a self-delete guard. Backend: new `users` module (`GET/POST /api/users`, `PATCH/DELETE /api/users/:id`, all `ADMIN`-only).
  - **History of Logs** (new): `AuditLogsPage`, read-only, filterable by entity type. Backend: new `audit_logs` table and `audit-logs` module (`GET /api/audit-logs`, `ADMIN`-only, no write endpoints by design). Wired into Users/Job Postings/Application-evaluation services to record `USER_*`, `JOB_POSTING_*`, and `APPLICATION_EVALUATED` entries.
  - Schema: `JobPosting.createdByUserId` and the new `AuditLog.actorUserId` are nullable with `onDelete: SetNull`, so deleting a user never blocks on, or cascades into deleting, their past job postings/log entries.
- Unified applicant registration into a single continuous flow instead of "sign up, then fill in your info after logging in": `RegisterPage` and `RegistrationWizardPage` were merged into one `RegistrationPage` (`/register`) that carries an unauthenticated visitor through account creation and straight into demographic profile, work experience, L&D, awards, and documents with no route change in between. Backend: added `Applicant.registrationCompletedAt` and `POST /api/applicants/me/complete-registration` (validates an eligibility-proof upload exists if `hasEligibility` is true). Frontend: `AuthContext` now resolves `registrationComplete` for the session; `ProtectedRoute` and `HomeRedirect` redirect any applicant who hasn't finished registration to `/register` regardless of which page they try to reach directly, so browsing job postings or applying is unreachable until every step is done. See `docs/decisions.md` for the full rationale.
- `JobManagementPage` and `UsersManagementPage` switched from an always-visible inline create/edit form above the table to a table-only layout with an "Add Job"/"Add User" button that opens the same form in a `Modal` (also reused for editing an existing row). `EvaluateApplicantsPage`'s applicants table now always renders once a job posting is selected, showing an in-table "No applications for this posting yet." row instead of hiding the table when the list is empty - consistent with `AuditLogsPage`'s existing empty-state pattern. Added shared `.page-header` (title + action button row) and `.table-empty` (centered empty-state cell) styles in `frontend/src/shared/styles/index.css`.
- Admin **Dashboard** (new, `/admin/dashboard` - now the admin role's landing page in place of `/admin/jobs`): stat tiles for applicants/job postings/applications/users, a horizontal bar chart of applications by status (reusing the same status colors as the app's `.badge`s) and top job postings by application count, plus a recent-activity feed reusing `AuditLogsPage`'s row shape. Backend: new `dashboard` module, `GET /api/dashboard/summary` (`ADMIN`-only) aggregating counts directly off `User`/`Applicant`/`JobPosting`/`Application` via Prisma `groupBy`, plus the 8 most recent audit log entries. No new tables. Extracted `AuditLogsPage`'s action-formatting helper into `shared/utils/formatAuditAction.ts` so both pages use it.
- Dashboard branding pass: a navy-to-navy-hover gradient hero banner with a gold bottom border (`.dashboard-hero`, reusing the same gradient recipe as the header's brand mark), branded icon chips per stat tile (navy gradient tile, gold glyph - inline SVG, no icon library), a gold top border on the stat tiles and chart cards, and stat-tile values recolored to the brand navy. The top-job-postings bars switched from navy to gold (`--color-accent-hover`) so they read distinctly from the status-colored applications-by-status bars next to them.
- `JobManagementPage` gained client-side search-by-title and a position-level filter, shown above the table only once postings exist. Distinguishes "no postings yet" from "no postings match your search/filter" in the table's empty state. New shared `.filters-row` style for this search+filter toolbar layout.
- **Interview panel accounts & CompAss tabulation** — replaces the single-admin-score evaluation stand-in with the real multi-evaluator Evaluation phase from the RSP spec:
  - New `PANEL` role (provisioned the same way as `ADMIN`, via Users Management's existing role dropdown) and `Application` status `FOR_INTERVIEW`.
  - **Evaluation Criteria** (new admin page, `/admin/criteria`): admin-editable interview rubric (`EvaluationCriterion`: name + max score, deactivate instead of delete once scored). Backend: new `evaluation-criteria` module, `GET /api/evaluation-criteria` (`ADMIN`/`PANEL`), `POST`/`PATCH`/`DELETE` (`ADMIN`-only, 409 if the criterion has recorded scores).
  - **Interview Panel** (new admin page, `/admin/panel-interviews`): assign/unassign `PANEL` users to a job posting's interview board, per posting. Backend: new `panel-assignments` module (`ADMIN`-only CRUD on `PanelAssignment`, unique per posting+panelist).
  - **My Interviews** (new panel-only page, `/panel/interviews`, new `panel` frontend feature): a panelist's queue of `FOR_INTERVIEW` applications across their assigned postings, each scored against every active criterion + remarks. Backend: new `panel-evaluations` module — `GET /my-queue` and `PATCH /:applicationId` (both `PANEL`-only; upserts `PanelEvaluation` + child `PanelScore` rows in one transaction, validates every active criterion is scored and no score exceeds its max).
  - `EvaluateApplicantsPage` extended: a "Schedule Interview" action moves an eligible application to `FOR_INTERVIEW` (new `PATCH /api/applications/:id/schedule-interview`, `ADMIN`-only); two new columns, "Panel Avg" and "Rank", show the live CompAss matrix (`GET /api/panel-evaluations/tabulation/:jobPostingId` — sums/averages/ranks panelists' scores per application); the expanded evaluate form shows each panelist's score and warns if not everyone assigned has submitted yet, since finalizing early is still allowed.
  - Frontend role/routing: `ProtectedRoute`'s `role` prop now accepts an array (`AppRole | AppRole[]`), `Layout` gained a `PANEL` nav branch, `HomeRedirect`/`HOME_BY_ROLE` route `PANEL` to `/panel/interviews`.
  - Fixed two related gaps while adding the role: `backend/src/modules/auth/auth.service.ts`/`auth.dto.ts` had a hardcoded `"APPLICANT" | "ADMIN"` literal union instead of Prisma's `Role` type (would have broken panel login); the `dashboard` module's role/status tallies didn't know about `PANEL`/`FOR_INTERVIEW` and would have silently undercounted them.
  - Schema: four new tables (`evaluation_criteria`, `panel_assignments`, `panel_evaluations`, `panel_scores`) in one migration alongside the two enum additions. See `docs/decisions.md` for the scope calls (multi-criteria rubric over one overall score; admin-assigned panelists over global visibility; `evaluate` left without a completeness guard).
- Applicant Registration: validation is now specific to the exact field that's missing, shown inline under that field, and (where it blocks progress) checked client-side before the network round trip:
  - Account step (email/password) and Demographic Profile (all required fields) now validate client-side with plain messages ("First name is required.", "Contact number is required.", etc.) instead of relying solely on a generic error banner plus whatever wording the backend's Zod validator happened to produce.
  - The Work Experience / Learning & Development / Awards "Add entry" mini-forms gained the same per-field required checks (these steps themselves stay optional — an applicant can legitimately have none of one — only the individual "Add" action is validated when used).
  - The Documents step now disables "Finish registration" with an inline explanation ("You indicated you have a civil service eligibility — upload proof of it above...") when eligibility proof is required but missing, instead of only surfacing that as a generic banner after a failed submit attempt.
- Job postings gained a `description` field (free-text role/duties overview, distinct from the existing `qualification*` QS fields): required in the admin Add/Edit Job modal (`JobManagementPage`), and shown to applicants only inside a new "View Details" modal on `JobPostingsListPage` rather than on the list itself. The applicant-facing card is now a minimal summary (title, status, level, closing date) plus "View Details" and "Apply" buttons; the modal carries the description, all four qualification standards, and the promotional-documents notice. Backend: `description` added to `JobPosting` (migration backfills the 3 seeded postings with a placeholder, since MySQL `TEXT` columns can't carry a schema-level default), `createJobPostingSchema`/`updateJobPostingSchema` updated accordingly.
- **Application stage tracker + stage-change emails**:
  - `MyApplicationsPage` now renders a 4-node stepper (Submitted → Sifting → Interview → Decision) per application (new `ApplicationStageTracker` component), replacing the raw status badge as the primary at-a-glance view - the badge stays alongside it as the precise label. Colors reuse the app's existing status language (the same tokens already used for `.badge`s and the Dashboard's bars) rather than a new palette. `WITHDRAWN` bypasses the linear stepper for a distinct muted state, since it can happen from any prior stage.
  - New email infrastructure (none existed before): `nodemailer` added to the backend; `EmailService` (`backend/src/shared/email/emailService.ts`) sends via real SMTP when `SMTP_HOST` is configured, otherwise logs the full message to the console prefixed `[DEV EMAIL]` - so the feature works and is verifiable in local dev with no mail server. A send failure is always caught and logged, never thrown; a notification is a side effect of a status change, not a precondition for it.
  - `ApplicationsService` emails the applicant after each real status-changing action: `submit()` (application received), `scheduleInterview()` (scheduled for interview), `evaluate()` (qualified/not qualified). Copy lives in `backend/src/shared/email/applicationEmailTemplates.ts`, separate from the service logic. No hook exists for `UNDER_SIFTING`/`WITHDRAWN` - nothing in the codebase sets either status yet.
  - New optional `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_SECURE`/`SMTP_FROM` env vars (see `.env.example`).
- Job postings gained `monthlySalary`, `placeOfAssignment`, and `duties` fields (all free-text, required), bringing them up to the level of detail on typical DILG job-posting flyers: `monthlySalary` shows on both the admin table and the applicant-facing list card (a new "Salary" column / meta row); `placeOfAssignment` and `duties` show only in the admin Add/Edit Job modal and the applicant "View Details" modal, alongside `description` and the qualification standards. `duties` is entered as one duty per line and rendered as a numbered list (split on `\n`). Backend: migration `20260808044639_add_salary_place_duties_to_job_posting` follows the same add-nullable → backfill → enforce-NOT-NULL pattern used for `description`, since MySQL `TEXT`/`VARCHAR` columns can't carry a schema-level default; the 3 seeded postings were backfilled with realistic values. `createJobPostingSchema`/`updateJobPostingSchema` updated accordingly.
- **Sifting / PQE / Interview pipeline** — fills in the previously-nonfunctional `UNDER_SIFTING` status and repurposes the old free-standing "Evaluate Applicants" action into the actual RSP pipeline order (Submitted → Sifting → Qualified → PQE score → Interview → panel tabulation):
  - Applications now move to `UNDER_SIFTING` automatically the instant they're submitted (`ApplicationsRepository.create()` sets it directly) - no manual "start sifting" step.
  - `PATCH /applications/:id/evaluate` (any status → `QUALIFIED`/`NOT_QUALIFIED`, with a 0-100 score) is now `PATCH /applications/:id/sift` (`UNDER_SIFTING` only → `QUALIFIED`/`NOT_QUALIFIED` + optional remarks, no score - sifting is pass/fail against the posting's qualification standards, not a scored evaluation). `EvaluationRow`'s form and button label updated to match ("Sift"/"Sift Applicant" instead of "Evaluate"/"Re-evaluate"); re-sifting after a decision is no longer offered.
  - New PQE score import: `POST /applications/import-exam-scores` (admin, multipart `.xlsx`/`.xls` + `jobPostingId`) parses an Excel file (new `exceljs` dependency) with "Name"/"Score" header columns, matches each row by normalized full name against that posting's `QUALIFIED` applicants, and records `Application.examinationScore`/`examinationScoredAt` on matches - unmatched rows come back in the response (not an error) for the admin to review and re-upload. `EvaluateApplicantsPage` gained an "Import PQE Scores" file upload control with an inline unmatched-rows list, and an "Exam Score" table column.
  - `PATCH /applications/:id/schedule-interview`'s guard changed from "status is `SUBMITTED` or `UNDER_SIFTING`" to "status is `QUALIFIED` **and** `examinationScore` is recorded" - interview scheduling now enforces sifting-then-PQE order. `EvaluationRow` shows an "Awaiting PQE score" hint on Qualified applications without a score yet, in place of the (disabled) button.
  - Schema: `Application.evaluationScore` dropped; `evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` renamed `siftingRemarks`/`siftedAt`/`siftedByUserId`; added `examinationScore`/`examinationScoredAt`. New audit actions `APPLICATION_SIFTED`/`APPLICATION_EXAM_SCORES_IMPORTED` replace `APPLICATION_EVALUATED`.
  - `ApplicationStageTracker`'s 4-node stepper is now Submitted → Sifting → Examination → Interview (previously Submitted → Sifting → Interview → Decision) - the Qualified/Not-Qualified resolve-in-place styling moved from the old terminal "Decision" node onto the Sifting node itself, since sifting is now mid-pipeline rather than a final call; a recorded PQE score shows as a line of text under the tracker on `MyApplicationsPage`.
  - Email copy updated: the Qualified sifting email now invites the applicant to the PQE instead of vaguely promising "next steps"; new `examScoreEmail` notifies the applicant of their recorded PQE score (sent regardless of score, per the domain spec).
  - See `docs/decisions.md`'s 2026-08-08 "Sifting/PQE/Interview pipeline" entry for the full rationale and trade-offs (notably: name-only PQE matching, no enforced pass/fail threshold on the exam score, and the pipeline still stopping at `FOR_INTERVIEW`/tabulation since Deliberation remains future work).
- Learning & Development entries can now have proof file(s) attached directly on `LdInterventionSection` (PDF/JPEG/PNG, ≤5MB, reusing the existing upload infrastructure) - each intervention shows its attached proof(s) with a per-file "Remove", plus a file input to attach another. Backend: new `DocumentType.LD_PROOF` and `Document.ldInterventionId` (nullable FK to `LdIntervention`, `onDelete: Cascade`); `POST /api/applicants/me/documents` accepts an optional `ldInterventionId` field (validated as belonging to the caller, same pattern as the existing `applicationId` field) alongside the existing `type`/`file`. The generic `DocumentsSection` (eligibility/IPCR/designation) no longer offers `LD_PROOF` in its type dropdown, since that upload is per-claim and lives in the L&D section instead.
- **Fix:** PQE score import (`POST /applications/import-exam-scores`) failed to match applicants who have a middle name on file, because the lookup only ever built a `firstName lastName` key while a real exam sheet naturally includes the middle name/initial (e.g. "Gibo R. Ormeneta" vs. the applicant's own `firstName`/`lastName` "Gibo"/"Ormeneta") - every row for such an applicant came back "unmatched" even though the name was, to a human, obviously the same. `normalizeName()` now also strips `.`/`,`, and a new `buildNameVariants()` indexes each Qualified applicant under every plausible spelling (with/without middle name, middle initial, suffix) instead of one fixed key.
- **Interview scheduling now captures date/venue/attire/notes, and the notification email actually contains them.** Previously "Schedule Interview" was a single button ("the panel will be in touch with further details") and no interview date was ever recorded anywhere. `PATCH /applications/:id/schedule-interview` now takes a `ScheduleInterviewDto` (`scheduledAt`, `venue`, optional `attire`/`notes`; 400 if `scheduledAt` isn't in the future), and `EvaluationRow`'s "Schedule Interview" action opens a form for these instead of firing immediately. Schema: `Application` gained `interviewScheduledAt`/`interviewVenue`/`interviewAttire`/`interviewNotes`. `forInterviewEmail` renders a When/Where/What-to-wear/Additional-instructions list instead of the old vague one-liner; the same details are shown to the applicant under their stage tracker on `MyApplicationsPage` once scheduled, and to the admin in `EvaluationRow`'s expanded panel.
- **Fix:** `SMTP_SECURE` was parsed with `z.coerce.boolean()` in `backend/src/config/env.ts`, which is just `Boolean(value)` under the hood - since any non-empty string is truthy in JS, `SMTP_SECURE=false` in `.env` was silently coerced to `true`, causing real SMTP delivery to fail with a TLS handshake error ("wrong version number") the moment real credentials were configured. Changed to `z.enum(["true", "false"]).transform(v => v === "true")`, which parses the string correctly. Real Gmail SMTP delivery (App Password) is now configured and verified working in this environment's `backend/.env` (gitignored, not committed).
- **Login page and the registration flow's account-creation step got a branded visual treatment**: a full-bleed navy-gradient panel (new `.auth-page` class, breaks out of `.app-main`'s centered column via a `left: 50%; margin-left: -50vw;` CSS trick) framed with gold top/bottom borders, the real DILG seal (`frontend/public/dilg-logo.webp`, provided by the user - not fabricated) shown crisply atop the login/account card and again, tiled and blurred, across the entire panel as background texture. `html`/`body` gained `overflow-x: hidden` to absorb the few px of horizontal overflow that breakout technique introduces (`100vw` counts the scrollbar's own width) - verified `.table-wrap`'s independent `overflow-x: auto` scroll regions are unaffected. Only these two screens changed; the rest of the registration wizard (once authenticated) keeps its normal centered-column layout.
  - Follow-up polish: the top nav is now hidden on both screens (`Layout.tsx`'s new `hideHeader`) for a fully immersive full-page look, with a small in-card "Don't have an account? Register" / "Already have an account? Log in" cross-link added to each so navigating between them still works without it. **Fix:** the login card rendered visibly narrower than the registration card despite sharing the same `.auth-form` CSS rule - both are flex items of `.auth-page`, and a flex item with only `max-width` set (no `width`) shrinks to fit its own content rather than filling up to that max, so the page with shorter copy (login) ended up narrower. Added `width: 100%` alongside `max-width: 400px` to fix it.
  - Second follow-up: removed the grey gap `.app-main`'s own padding left above/below the panel now that the header (and its vertical space) is gone - `.app-main:has(.auth-page)` zeroes that padding specifically on these two pages, and `.auth-page` uses `min-height: 100vh` to fill exactly the viewport (verified via `scrollHeight === clientHeight`, no scroll). Background watermark reverted from a full `background-repeat: repeat` tile (read as busy) back to two large blurred copies in opposite corners (720px, blur 24px) - bigger and softer than the original pass.
- **Fix: applicants without the eligibility a job posting requires could apply anyway.** `ApplicationsService.submit()` previously only checked that a self-declared-eligible applicant had uploaded *some* proof document, never that their eligibility type actually matched what the posting needed - and an applicant with no eligibility on file wasn't blocked at all. Job postings can now specify `requiredEligibilityTypes` (checkboxes on the admin Job Management form: RA 1080 / CSC Professional / CSC Sub-Professional / Barangay Eligibility, alongside the existing free-text qualification field, which stays as applicant-facing context only); submitting an application 400s unless the applicant's own `eligibilityType` is one of them, and `JobPostingsListPage` disables/relabels the "Apply" button using the same check so the applicant learns why before clicking, not after. A posting with none checked requires no eligibility, matching prior behavior. Schema: new `JobPostingRequiredEligibility` join table (MySQL has no native scalar-list column) - see `docs/decisions.md`'s 2026-08-08 "Eligibility gate at application submission" entry.
- **Applicants can now withdraw their own application.** `WITHDRAWN` has existed in the `ApplicationStatus` enum since the pipeline's first migration but nothing ever set it. New `PATCH /api/applications/:id/withdraw` (applicant-only, no admin equivalent): 404s if the application isn't the caller's own (can't distinguish "not found" from "not yours"), 400s if the application is already `NOT_QUALIFIED`/`WITHDRAWN` (both terminal) - otherwise allowed from `SUBMITTED`/`UNDER_SIFTING`/`QUALIFIED`/`FOR_INTERVIEW`. Sets `status: WITHDRAWN`, stamps new `withdrawnAt`, and sends a new `withdrawnEmail` notification (same pattern as every other stage-change email). `MyApplicationsPage` gained a "Withdraw" button (only shown while withdrawable) behind a `ConfirmDialog`, reusing the same confirm-before-destructive-action pattern as `JobManagementPage`'s delete. Consistent with `submit()`, this applicant-initiated action is not written to the audit log (that trail has only ever covered admin/panel writes) - see `docs/decisions.md`'s 2026-08-08 "Applicant-initiated application withdrawal" entry for the full rationale, including why there's no spec-mandated cutoff for which statuses allow it.
