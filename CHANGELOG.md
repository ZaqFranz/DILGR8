# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added
- Initial project scaffold: npm workspaces monorepo (`backend`, `frontend`).
- `CLAUDE.md` governance/workflow rules and `docs/` structure (architecture, api, database, patterns, decisions, project-memory, troubleshooting, rsp-domain-spec).
- Backend: Express + TypeScript API with feature-first Clean Architecture (`modules/{auth,applicants,job-postings,applications}`), Prisma ORM against MySQL, JWT authentication, centralized error handling, request validation (Zod), Pino logging.
- Frontend: React + TypeScript (Vite) SPA with feature-first structure, JWT-aware API client.
- Applicant Registration feature (Application phase of the RSP pipeline): account registration/login, demographic profile, work experience, learning & development interventions, eligibility checklist with proof upload, awards, IPCR/Designation-to-Higher-Position upload for promotional applications, job posting listing, and application submission.
- Local MySQL database provisioned (via XAMPP's bundled MariaDB) and initial Prisma migration applied, creating all tables per `docs/database.md`. Seed data adds one admin user and two sample job postings.
- Applicant Registration wizard now auto-advances to the next step when the demographic profile is first created, and every step has Back/Next navigation (`frontend/src/features/applicant-registration/pages/RegistrationWizardPage.tsx`).
- Admin panel, separated from the applicant experience by role-gated routing (`/admin/*` vs `/jobs`, `/registration`, `/applications`): a "Post a Job" page and an "Evaluate Applicants" page (score 0-100, qualified/not-qualified decision, remarks per application). Backend: `evaluationScore`/`evaluationRemarks`/`evaluatedAt`/`evaluatedByUserId` added to `Application`, plus `GET /api/applications` (admin listing, optionally filtered by job posting) and `PATCH /api/applications/:id/evaluate` (both `ADMIN`-only). Frontend: new `admin` feature, and `ProtectedRoute` gained a `role` prop enforced on both the admin and applicant route groups.
- Fixed an auth race condition where an already-logged-in user landing on `/` was bounced to `/login` and stuck there (session hydration from `localStorage` happened after route guards had already decided). `AuthContext` now exposes `isLoading`; `ProtectedRoute`/`HomeRedirect` wait on it.
- Admin panel redesigned around a sidebar shell (`AdminShell`) with four sections, and full CRUD added for Job Management and (new) Users Management, plus a new read-only History of Logs section:
  - **Job Management**: `JobManagementPage` replaces the old create-only "Post a Job" page with a data table (Edit/Delete per row, inline delete confirmation, no native browser dialogs). Backend: `PATCH`/`DELETE /api/job-postings/:id` (`ADMIN`-only); deleting a posting with existing applications is blocked (409) to prevent silent data loss via cascade.
  - **Users Management** (new): `UsersManagementPage` - admin-provisioned account creation (including new admins), role/email editing, deletion with a self-delete guard. Backend: new `users` module (`GET/POST /api/users`, `PATCH/DELETE /api/users/:id`, all `ADMIN`-only).
  - **History of Logs** (new): `AuditLogsPage`, read-only, filterable by entity type. Backend: new `audit_logs` table and `audit-logs` module (`GET /api/audit-logs`, `ADMIN`-only, no write endpoints by design). Wired into Users/Job Postings/Application-evaluation services to record `USER_*`, `JOB_POSTING_*`, and `APPLICATION_EVALUATED` entries.
  - Schema: `JobPosting.createdByUserId` and the new `AuditLog.actorUserId` are nullable with `onDelete: SetNull`, so deleting a user never blocks on, or cascades into deleting, their past job postings/log entries.
- Unified applicant registration into a single continuous flow instead of "sign up, then fill in your info after logging in": `RegisterPage` and `RegistrationWizardPage` were merged into one `RegistrationPage` (`/register`) that carries an unauthenticated visitor through account creation and straight into demographic profile, work experience, L&D, awards, and documents with no route change in between. Backend: added `Applicant.registrationCompletedAt` and `POST /api/applicants/me/complete-registration` (validates an eligibility-proof upload exists if `hasEligibility` is true). Frontend: `AuthContext` now resolves `registrationComplete` for the session; `ProtectedRoute` and `HomeRedirect` redirect any applicant who hasn't finished registration to `/register` regardless of which page they try to reach directly, so browsing job postings or applying is unreachable until every step is done. See `docs/decisions.md` for the full rationale.
- `JobManagementPage` and `UsersManagementPage` switched from an always-visible inline create/edit form above the table to a table-only layout with an "Add Job"/"Add User" button that opens the same form in a `Modal` (also reused for editing an existing row). `EvaluateApplicantsPage`'s applicants table now always renders once a job posting is selected, showing an in-table "No applications for this posting yet." row instead of hiding the table when the list is empty - consistent with `AuditLogsPage`'s existing empty-state pattern. Added shared `.page-header` (title + action button row) and `.table-empty` (centered empty-state cell) styles in `frontend/src/shared/styles/index.css`.
- Admin **Dashboard** (new, `/admin/dashboard` - now the admin role's landing page in place of `/admin/jobs`): stat tiles for applicants/job postings/applications/users, a horizontal bar chart of applications by status (reusing the same status colors as the app's `.badge`s) and top job postings by application count, plus a recent-activity feed reusing `AuditLogsPage`'s row shape. Backend: new `dashboard` module, `GET /api/dashboard/summary` (`ADMIN`-only) aggregating counts directly off `User`/`Applicant`/`JobPosting`/`Application` via Prisma `groupBy`, plus the 8 most recent audit log entries. No new tables. Extracted `AuditLogsPage`'s action-formatting helper into `shared/utils/formatAuditAction.ts` so both pages use it.
- Dashboard branding pass: a navy-to-navy-hover gradient hero banner with a gold bottom border (`.dashboard-hero`, reusing the same gradient recipe as the header's brand mark), branded icon chips per stat tile (navy gradient tile, gold glyph - inline SVG, no icon library), a gold top border on the stat tiles and chart cards, and stat-tile values recolored to the brand navy. The top-job-postings bars switched from navy to gold (`--color-accent-hover`) so they read distinctly from the status-colored applications-by-status bars next to them.
- `JobManagementPage` gained client-side search-by-title and a position-level filter, shown above the table only once postings exist. Distinguishes "no postings yet" from "no postings match your search/filter" in the table's empty state. New shared `.filters-row` style for this search+filter toolbar layout.
- **Interview panel accounts & CompAss tabulation** — replaces the single-admin-score evaluation stand-in with the real multi-evaluator Evaluation phase from the RSP spec:
  - New `PANEL` role (provisioned the same way as `ADMIN`, via Users Management's existing role dropdown) and `Application` status `FOR_INTERVIEW`.
  - **Evaluation Criteria** (new admin page, `/admin/criteria`): admin-editable interview rubric (`EvaluationCriterion`: name + max score, deactivate instead of delete once scored). Backend: new `evaluation-criteria` module, `GET /api/evaluation-criteria` (`ADMIN`/`PANEL`), `POST`/`PATCH`/`DELETE` (`ADMIN`-only, 409 if the criterion has recorded scores).
  - **Interview Panel** (new admin page, `/admin/panel-interviews`): assign/unassign `PANEL` users to a job posting's interview board, per posting. Backend: new `panel-assignments` module (`ADMIN`-only CRUD on `PanelAssignment`, unique per posting+panelist).
  - **My Interviews** (new panel-only page, `/panel/interviews`, new `panel` frontend feature): a panelist's queue of `FOR_INTERVIEW` applications across their assigned postings, each scored against every active criterion + remarks. Backend: new `panel-evaluations` module — `GET /my-queue` and `PATCH /:applicationId` (both `PANEL`-only; upserts `PanelEvaluation` + child `PanelScore` rows in one transaction, validates every active criterion is scored and no score exceeds its max).
  - `EvaluateApplicantsPage` extended: a "Schedule Interview" action moves an eligible application to `FOR_INTERVIEW` (new `PATCH /api/applications/:id/schedule-interview`, `ADMIN`-only); two new columns, "Panel Avg" and "Rank", show the live CompAss matrix (`GET /api/panel-evaluations/tabulation/:jobPostingId` — sums/averages/ranks panelists' scores per application); the expanded evaluate form shows each panelist's score and warns if not everyone assigned has submitted yet, since finalizing early is still allowed.
  - Frontend role/routing: `ProtectedRoute`'s `role` prop now accepts an array (`AppRole | AppRole[]`), `Layout` gained a `PANEL` nav branch, `HomeRedirect`/`HOME_BY_ROLE` route `PANEL` to `/panel/interviews`.
  - Fixed two related gaps while adding the role: `backend/src/modules/auth/auth.service.ts`/`auth.dto.ts` had a hardcoded `"APPLICANT" | "ADMIN"` literal union instead of Prisma's `Role` type (would have broken panel login); the `dashboard` module's role/status tallies didn't know about `PANEL`/`FOR_INTERVIEW` and would have silently undercounted them.
  - Schema: four new tables (`evaluation_criteria`, `panel_assignments`, `panel_evaluations`, `panel_scores`) in one migration alongside the two enum additions. See `docs/decisions.md` for the scope calls (multi-criteria rubric over one overall score; admin-assigned panelists over global visibility; `evaluate` left without a completeness guard).
